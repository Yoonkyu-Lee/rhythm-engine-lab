## 요약 — 계획 결정과 근거

질문은 "리소스를 프로세서가 적은 수고로 받을 형태로 미리 바꾸고 형식을 통일하면, 할 일 자체가 줄어 일정하고 적은 연산·낮은 지연·백엔드 영향 최소를 얻는가"였다. 측정의 답은 **그렇다**이고, 차이는 대부분 몇 배~열 배 단위였다.

| 결정 | 근거 (이 리포트의 수치) |
|---|---|
| **렌더러 = Direct3D 11 직접 + 일괄 그리기**(아틀라스 + 인스턴싱, 그리기 호출 최소). Direct2D·D3D12·wgpu는 쓰지 않음 | 같은 장면에서 CPU가 Direct2D의 1/9(4.7% vs 42.5%)다. Direct2D는 사각형 2만 개부터 240 Hz를 놓친다. D3D12는 제출이 오히려 길고(0.2 vs 0.05 ms) 얻는 것이 없다. D3D11은 6만 개에서도 240 Hz다(A4) |
| **출력 = 테두리 없는 전체 화면 + 플립 + 대기 가능 + 프레임 지연 1**. 창 모드는 선택지. tearing은 "화면 시각 측정 불가" 선택지 | 전체 화면이 창보다 입력을 1.85 ms 늦게 읽고도 같은 갱신에 나간다. tearing에서는 프레임 통계가 화면 시각을 주지 못한다(A1·A2) |
| **화면 시계 = DXGI 프레임 통계**(PresentCount ↔ SyncQPCTime). 물리 검증(A3)은 장비가 생기면 | 모든 vsync 구성에서 프레임마다 짝지어졌다(A1) |
| **글자 = 글리프 아틀라스**(DirectWrite로 굽는 캐시 + 스프라이트) | 8천 자에서 DrawText 25 ms(35 fps)이고, 아틀라스는 0.05 ms다(A5) |
| **BGA 영상 = 컨버터가 H.264 MP4(1초 키프레임)로 통일 → 게임은 Media Foundation + DXVA 하나** | 원본은 91%만 GPU 디코딩이고, 나머지는 CPU 프레임당 최대 15 ms, 탐색 최대 2.1초, 0.6%는 안 열린다. 통일하면 27/27이 GPU 디코딩되고 탐색 최대 92 ms, 늦은 프레임 0이다(B2·B3) |
| **일러스트 = 컨버터가 BC7로 저장 → 게임은 디코딩 없이 올림**(PSNR 기준 미달 그림만 무압축) | 800장 로딩 10.6배 빠르고 CPU 13배 적고 VRAM 4배 적다. 큰 그림 하나의 디코딩이 프레임 4~7개 분량이다(F1·E1) |
| **`session → scene` 경계 = 상태는 삼중 버퍼, 사건은 SPSC 링**(CP3의 Mutex try_lock 대체) | Mutex는 오디오 스레드를 최대 0.37 ms 세우고, try_lock은 바쁠 때 게시의 26~71%를 버린다. 삼중 버퍼는 평소 최대 1.9 µs이고 버림이 없다(D1) |
| **스킨 = 선언형 + 작은 순수 식 + 로드 시 펼치기, 스크립트 없음**. 도메인에 상태 시계·박자 시계·사용자 조정·펼치기 추가 | 선례 75개 개념 중 불가 9개는 입력 위젯·스크립트 부작용뿐이다. 시안 셋에서 못 적은 것이 18개에서 3개로 준다(C) |

- **백엔드 영향.** 렌더링·디코딩이 무거워도 1 ms 오디오 스레드의 늦음 p99는 기준선과 같았다(A4·B2). 이 기계에서 "백엔드에 주는 영향"의 차이는 **CPU 사용률**, 곧 발열·전력·저사양 기계의 여유로 나타났다. 위 결정은 모두 그 사용률을 가장 낮추는 쪽이다. 일을 GPU의 고정 기능(DXVA 디코더, BC 텍스처 샘플러, 인스턴싱)과 컨버터(오프라인)로 옮긴 결과다.
- **사용자 판단 ⚑**
  1. BC7 화질 재측정용 인코더(DirectXTex) 내려받기.
  2. 스킨에 입력 위젯(버튼·슬라이더·텍스트 입력)을 넣을지.
  3. 오디오 시각화를 넣을지.
  4. 기존 스킨 변환기 시기.
  5. A3 물리 검증 장비.

## A1·A2. 화면에 나간 시각과 출력 방식

- **무엇을**: 같은 장면(16레인 바탕 + 움직이는 노트 2천 개(50개마다 큰 반투명 폭발) + 글자 2천 자)을 세 렌더러로 그렸다. ① Direct2D(CP3 방식: 그림마다 `DrawBitmap`) ② Direct3D 11 직접(모든 사각형을 인스턴스 버퍼 하나 + 그리기 호출 하나) ③ Direct3D 12 직접(같은 그리기를 명령 목록으로). 세 렌더러 모두 같은 DXGI 스왑체인(플립 모델, 대기 가능, 최대 프레임 지연 1)을 썼다. 출력 방식은 창(1280×720), 테두리 없는 전체 화면, 전체 화면 + vsync 끔 + tearing 세 가지다. 프레임마다 "프레임 시작(대기 가능 객체가 풀린 순간 = 입력을 읽을 순간) → DXGI 프레임 통계가 알려 준 그 프레임의 화면 갱신 시각"을 쟀다. 구성마다 새 프로세스에서 1초 예열 후 5초 측정.
- **게임으로 치면**: 노트가 판정선에 닿는 순간이 화면에 언제 나가는지 프레임마다 알 수 있는지, 그리고 어떤 출력 방식이 그 시각을 가장 앞당기는지 본 것이다.
- **결과** (240 Hz, 장면 gear, p50 / p99):

  | 출력 방식 | 프레임 시작 → 화면 (D3D11) | 프레임 시작 → 화면 (D3D12) | 프레임 통계 |
  |---|---|---|---|
  | 창 (DWM 합성) | 2.74 / 7.81 ms | 2.74 / 6.91 ms | 매 프레임 받음 |
  | 테두리 없는 전체 화면 | **0.88 / 5.57 ms** | 0.89 / 5.46 ms | 매 프레임 받음 |
  | 전체 화면 + tearing | −1.67 ms (음수 = 의미 없음) | −1.69 ms | 값은 오지만 tearing present에는 "갱신 시각"이 정의되지 않음 |

  - 세 렌더러 모두 프레임 통계를 매 프레임 받았다. 측정한 프레임 수와 짝지은 수가 같다(예: 1,184 / 1,184).
  - 전체 화면은 창보다 약 1.9 ms 빠르다. 창 모드는 DWM이 한 번 더 합성하기 때문이다. 이 값은 OS가 보고한 것이고, 모니터 자체 지연은 포함하지 않는다(A3).
  - tearing은 화면 시각을 잴 수 없다. 렌더러가 비교적 가벼운 장면에서 2,300 fps를 냈지만, 스캔 도중에 바꿔 끼우므로 "그 프레임이 언제 화면에 나갔나"가 한 값이 아니다.
  - 두 모드 모두 "프레임 시작 → 바로 다음 화면 갱신"에 나간다. 차이는 프레임이 언제 시작하느냐다. 대기 가능 객체가 풀리는 시점이 창 모드는 갱신 후 1.43 ms, 전체 화면은 3.28 ms다(`실험/data/a_phase.csv`). 창 모드는 DWM 합성 마감 때문에 더 일찍 그리기 시작해야 한다. 그래서 같은 화면 갱신에 나가더라도 입력을 1.85 ms 더 일찍 읽은 그림이 된다(1.43 + 2.74 = 3.28 + 0.89 = 4.17 ms = 한 주기).
- **결론**: 화면 시계는 **DXGI 프레임 통계(PresentCount ↔ SyncQPCTime)**로 정한다. API(D3D11·D3D12)와 무관하게 같은 값을 준다. 기본 출력은 **테두리 없는 전체 화면 + 플립 모델 + 대기 가능 + 프레임 지연 1**이다. 창 모드는 선택지로 두고 지연이 약 2 ms 더 있다고 표시한다. tearing은 "측정 불가" 표시를 붙인 선택지로만 둔다. 화면 싱크 보정(오프셋 B)과 측정은 vsync 모드를 기준으로 한다. wgpu는 재지 않았다. D3D12 위의 한 층이라 D3D12 직접보다 빠를 수 없고, D3D12 직접도 D3D11보다 나은 점이 없었기 때문이다(A4).

## A3. 화면 시각의 물리 검증 🧑

- 보류. 광센서 + 오디오 입력 또는 고속 촬영이 필요하다. A1의 값은 OS·드라이버가 보고한 시각이라, 모니터 처리 지연(수 ms~수십 ms)은 이 방법으로 볼 수 없다. 화면 싱크의 최종 확인은 사람 보정(화면으로 맞추기)으로 하고, 장비가 생기면 이 항목을 연다.

## A4. 스킨이 요구할 그리기 양

- **무엇을**: A1과 같은 장면을 사각형 수만 바꿔 그렸다. gear는 노트 2천 + 글자 2천, heavy는 2만 + 2천, stress는 6만 + 2천이다. 렌더러마다 프레임 유지율, 프레임당 CPU 제출 시간, 프로세스 CPU 사용률(코어 하나 = 100%)을 쟀다. 동시에 1 ms마다 깨어나 믹싱 흉내를 내는 가짜 오디오 스레드(MMCSS Pro Audio)를 돌려, 렌더링이 오디오 스레드를 얼마나 늦추는지도 쟀다. 출력은 테두리 없는 전체 화면, vsync 240 Hz다.
- **게임으로 치면**: 화려한 스킨(노트 수백 + 폭발 이펙트 + 숫자 + 글자)을 그릴 때, 어떤 그리기 방식이 240 Hz를 지키면서 CPU를 덜 쓰고 오디오를 방해하지 않는지 본 것이다.
- **결과** (fps / 제출 p50 / CPU 사용률):

  | 장면 | Direct2D | Direct3D 11 직접 | Direct3D 12 직접 |
  |---|---|---|---|
  | gear (4천) | 235 / 1.32 ms / 42.5% | **237 / 0.04 ms / 4.7%** | 237 / 0.22 ms / 9.1% |
  | heavy (2.2만) | **86** / 7.36 ms / 72.1% | 238 / 0.07 ms / 18.4% | 238 / 0.24 ms / 15.9% |
  | stress (6.2만) | **41** / 21.3 ms / 104.5% | 236 / 0.15 ms / 32.8% | 238 / 0.30 ms / 26.6% |

  - Direct2D는 heavy부터 240 Hz를 못 지킨다. 프레임 시작에서 화면까지 4~16 ms로 늘어난다.
  - D3D11 직접은 6만 개에서도 240 Hz를 지킨다. 남는 CPU 사용률은 대부분 장면 만들기(사각형 6만 개 계산 0.9 ms/프레임)이고, 그리기 자체는 0.15 ms다.
  - D3D12는 제출이 D3D11보다 오히려 길다(0.2~0.3 ms). 그리기 호출이 하나뿐이라 D3D12가 줄여 주는 "호출당 드라이버 비용"이 애초에 없다.
  - vsync를 끄면 D3D11 gear가 2,278 fps까지 올라간다. 즉 240 Hz에 필요한 일의 약 10%만 쓰는 셈이다. stress는 vsync를 꺼도 약 240 fps다. 반투명 큰 사각형 1,200개의 채우기 때문에 GPU가 한계라는 뜻이다.
  - 가짜 오디오 스레드의 늦음은 모든 구성에서 기준선(그리기 없음)과 같았다. p99는 0.7~0.96 ms(기준선 0.78~0.89 ms, 타이머 해상도 수준)다. 최대값만 CPU를 꽉 쓰는 구성(Direct2D 글자, vsync 끔)에서 가끔 2~3 ms였다(기준선 최대 1.1~1.5 ms).
- **결론**: 렌더러는 **Direct3D 11 직접 + 일괄 그리기**(그림을 한 장 또는 몇 장의 아틀라스에 모으고, 사각형을 인스턴스로 한 번에)로 정한다. Direct2D는 CP3처럼 사각형 수백 개일 때만 충분하고, 그림·이펙트 양이 늘면 CPU를 9배 넘게 쓰다가 프레임을 놓친다. D3D12는 이 규모에서 얻는 것 없이 복잡도(펜스·힙·장벽 수동 관리)만 늘어난다. 오디오 방해는 이 기계(22스레드)에서 어느 렌더러든 측정되지 않았다. 따라서 "백엔드에 주는 영향"의 실제 차이는 **CPU 사용률(= 발열·전력·저사양 기계에서의 여유)**이고, 여기서 D3D11 직접이 가장 적다. 스킨 그리기 목록의 상한은 CPU가 아니라 GPU 채우기 양이 정한다(큰 반투명 사각형 수).

## A5. 다국어 글자

- **무엇을**: 글자 8천 자(한글·가나·한자·라틴, 40자 줄 200개)를 두 방식으로 그렸다. ① Direct2D `DrawText`로 줄마다 매 프레임 그리기(DirectWrite가 매번 줄 배치) ② 글리프 아틀라스 방식: 시작할 때 DirectWrite로 글자를 텍스처에 한 번 굽고, 이후 글자를 사각형 스프라이트로 그리기(D3D11 직접).
- **게임으로 치면**: 선곡 목록 수백 줄의 일본어 곡 제목이나 결과 화면의 숫자를 그릴 때, 글자가 프레임을 잡아먹지 않게 하는 방법을 본 것이다.
- **결과** (전체 화면, 240 Hz):

  | 방식 | fps | 제출 p50 | CPU |
  |---|---|---|---|
  | DrawText 매 프레임 | **35** | 25.3 ms | 93% |
  | 글리프 스프라이트 (Direct2D `DrawBitmap`) | 232 | 2.3 ms | 69% |
  | 글리프 스프라이트 (D3D11 직접) | **234** | **0.05 ms** | 11% |

  - 글리프 아틀라스는 2048×1024에 32 px 칸 2,048개(이번 표본 1,500자)이며 8 MB다.
- **결론**: 글자는 **글리프 아틀라스(DirectWrite로 굽고 스프라이트로 그림)**로 한다. 바뀌지 않는 문자열을 매 프레임 `DrawText`로 그리는 것은 CP3처럼 몇 줄일 때만 된다. 한자는 수천 자라 미리 다 구울 수 없다. 그래서 아틀라스를 "처음 나온 글자를 그때 구워 넣는 캐시"로 만들고, 곡 목록처럼 미리 아는 글자는 화면에 들어가기 전에 굽는다. 참고로 이번 비교의 DrawText 쪽은 줄 배치를 매 프레임 다시 했다. 줄 배치를 캐시하면(`IDWriteTextLayout`) 그보다 빨라지지만, 스프라이트 0.05 ms와는 자릿수가 다르다(추정).

## B1·B4. 영상·그림 BGA 형식 통계

- **무엇을**: `D:\Games\BMS` 전체(883만 파일, 1,178 GiB)와 IIDX 영상 폴더를 열거했다. 영상은 (묶음, 확장자)별로 최대 200개씩 ffprobe로 머리를 읽었다(1,508개). 그림 BGA는 BMS 채보 2,000개에서 `#BMP` 수·크기·형식·교체 빈도를 셌다. 상세는 `실험/B_영상_이미지_형식.md`.
- **게임으로 치면**: 우리 라이브러리의 BGA가 실제로 어떤 영상·그림 파일로 되어 있는지, 디코더가 얼마나 많은 형식을 감당해야 하는지 센 것이다.
- **결과**:
  - 영상. 일반 BMS 영상 3,049개는 **MPEG-1 64%**, WMV 계열(VC-1·WMV3·WMV2·WMV1) 24%, H.264 9%, 나머지 16종이 3%다. 해상도는 작고(세로 480 이하 60%) 정사각이 78%다.
    - IIDX 영상은 98%가 H.264(1024×768 30 fps가 78%)다. 우리가 만든 IIDX·DJMAX 변환 BMS 영상 6,074개는 100% H.264다.
  - 그림 BGA. 일반 BMS 채보의 50%가 그림 BGA를 쓴다. 채보 하나의 고유 그림은 **p50 6장, p95 513장, 최대 1,295장**이다.
    - 83%가 256×256이고 77%가 BMP다.
    - 교체가 p90 이상 채보에서 초당 30~40회다(그림을 넘겨 영상처럼 씀).
    - 크기가 4의 배수가 아닌 그림이 7.4%다.
- **결론**: 영상의 통일 형식 후보는 **H.264(yuv420p, MP4)**다. 라이브러리의 바이트 기준 83%가 이미 H.264이고, 다시 인코딩할 것은 일반 BMS 영상 약 2,770개(저해상도)다. 그림 BGA는 "필요할 때 디코딩"으로는 초당 30~40장 교체를 감당하기 어렵다. 그래서 곡 시작 전에 전부 GPU에 올리는 쪽이 맞다(F1에서 형식 결정). 4의 배수가 아닌 그림은 변환 때 채워 넣는다.

## B2·B3. 영상 디코딩과 BGA 싱크

- **무엇을**: B1 표본에서 코덱마다 최대 6개씩 77개를 골랐다. 이것을 Media Foundation 소스 리더(D3D11 장치 관리자 연결, 하드웨어 변환 허용, 출력 NV12)로 열어 다음을 쟀다.
  1. 열기·첫 프레임 시간.
  2. 최대 속도 디코딩(실시간 대비 배수).
  3. 탐색 8번(seek → 그 시각의 첫 프레임까지).
  4. 곡 시계(QPC)에 맞춘 5초 실시간 재생: 프레임마다 "디코딩이 끝난 시각 vs 그 프레임의 제시각".
  5. 그동안 가짜 오디오 스레드의 늦음.

  디코더가 GPU(DXVA)로 디코딩했는지는 출력 텍스처가 디코더 출력용(`D3D11_BIND_DECODER`)인지로 판정했다. 그다음 코덱마다 2개(실패한 것은 3개), 모두 27개를 ffmpeg로 **H.264(yuv420p, MP4, CRF 20, 1초마다 키프레임)**로 다시 인코딩하고 같은 측정을 했다.
- **게임으로 치면**: 지금 라이브러리의 BGA를 그대로 틀면 어떤 곡은 GPU가 공짜로 풀고, 어떤 곡은 CPU가 땀 흘려 풀고, 어떤 곡은 아예 안 열린다. 컨버터에서 한 형식으로 바꿔 두면 이것이 모두 "GPU가 공짜로"가 되는지 본 것이다.
- **결과** (원본, `실험/data/b2_decode_orig.csv`):

  | 코덱 (일반 BMS 비율) | 열림 | GPU 디코딩 | 실시간 대비 (최소) | 탐색 p50 / 최대 | 프레임 디코딩 p99 최대 |
  |---|---|---|---|---|---|
  | MPEG-1 (64.2%) | 6/6 | 6/6 | 38× | 5 / 136 ms | 1.8 ms |
  | VC-1·WMV3 (17.0%) | 12/12 | 12/12 | 18× | 37~78 / 282 ms | 1.0 ms |
  | H.264 (9.0%) | 12/12 | 12/12 | 17× | 55 / 327 ms | 0.8 ms |
  | WMV2·WMV1 (6.7%) | 12/12 | **0** | 2.6× | 354~602 / **2,126 ms** | 11.8 ms |
  | MS-MPEG4·MPEG-4 Part 2 (1.4%) | 14/14 | **0** | **1.4×** | 186~360 / 1,862 ms | 15.2 ms |
  | VP8 (0.3%) | 6/6 | **0** | 4.0× | 359 / 1,088 ms | 15.4 ms |
  | MPEG-2 (0.7%) | 3/5 | 3/3 | 48× | 7 / 36 ms | 0.8 ms |
  | HEVC (0.1%) | 2/2 | 2/2 | 46× | 57 / 366 ms | 0.7 ms |
  | Cinepak·MS Video 1 (0.1%) | **0/5** | — | — | — | — |
  | 영상 확장자를 단 그림 (0.5%) | **0/3** | — | — | — | — |

  - 실시간 재생에서 늦은 프레임은 첫 프레임(재생 시작과 동시에 제시각인 것)을 빼면 77개 파일에서 3개 프레임이다(MPEG-4 Part 2·MPEG-1 50 fps·VP8 1080p 각 1). 하드웨어 디코딩 코덱은 프레임 여유 p01이 모두 15 ms 이상이었다.
  - 가짜 오디오 스레드의 늦음 p99는 모든 파일에서 0.69~0.97 ms로, 기준선과 같았다.
  - 일반 BMS 비율로 가중하면 **약 91%가 GPU 디코딩**, 약 8%가 CPU 디코딩(최대 1080p에서 실시간의 1.4배, 아슬아슬)이다. 약 0.6%는 Media Foundation으로 열리지 않는다(Cinepak·MS Video 1, 머리 없는 MPEG-2 스트림, 그림 파일).
- **결과** (H.264로 다시 인코딩한 27개, `실험/data/b2_decode_h264.csv`):
  - **27/27 열림, 27/27 GPU 디코딩**이다. Media Foundation이 못 열던 Cinepak·MS Video 1·그림 파일도 포함한다.
  - 탐색은 p50 13~30 ms, **최대 92 ms**다(원본 최대 2,126 ms). 1초마다 키프레임을 넣었기 때문이다.
  - 프레임 디코딩 p99 최대는 2.1 ms(원본 최대 15.4 ms), 늦은 프레임은 0이다. 1080p·2560×1080도 실시간의 9배 이상이다.
  - 다시 인코딩 비용(CPU libx264 medium): 영상 59분을 413초에 처리해 **실시간의 8.6배**(480p 이하는 20배)다. 크기는 합계 0.97배(480p 이하는 0.48배)다. 일반 BMS 영상 약 2,770개(p50 136초)를 이 설정으로 바꾸면 약 12시간이다(추정). GPU 인코더(NVENC)나 더 빠른 설정이면 줄어든다.
- **결론**: BGA 영상은 **컨버터가 H.264(yuv420p, MP4, 짝수 크기, 1초마다 키프레임, 소리 트랙 없음)로 통일**한다. 게임은 **Media Foundation + D3D11 장치 관리자(DXVA)** 하나만 쓰고 FFmpeg 디코더는 넣지 않는다. 통일하면 디코더 코드 경로가 하나가 되고, CPU 디코딩(프레임당 최대 15 ms)과 수백 ms~2초짜리 탐색과 "안 열림"이 모두 사라진다. 원본이 이미 H.264라도 키프레임 간격이 길면 탐색이 327 ms까지 걸리므로, 키프레임 간격만 다시 맞추는 재인코딩 여부는 컨버터에서 정한다. BGA 재생 정책은 다음과 같다. 프레임은 곡 시계로 "지금 보일 프레임"을 골라 GPU 텍스처(NV12)를 그대로 그린다(복사 없음). 탐색 뒤에는 키프레임부터 목표 시각까지 디코딩하고, 1초 키프레임에서 최대 92 ms 걸린다. 디코딩이 늦으면 직전 프레임을 유지하고 시계를 따라잡는다(프레임 버림). FFmpeg 디코더 비교는 하지 않았다. 통일 형식이 모두 하드웨어로 풀리므로 더 필요하지 않다고 봤다.


## C1·C2·C3. 화면 도메인 대응과 스킨 표현

- **무엇을**: beatoraja(로더 코드·기본 스킨), LR2(LunaticVibesF 로더), Qwilight(설치본 스킨 YAML·Lua), IIDX·DJMAX(CP0 문서)의 화면 개념 75개를 `화면_도메인.md`의 이름으로 하나씩 대응시켰다. 가장 복잡한 화면 셋(플레이 기어 연출, beatoraja 선곡, 결과)을 선언형 시안으로 적어 보고, 못 적는 것을 셌다. 상세는 `실험/C_화면도메인_대응.md`. 코드·파일은 읽기만 했다.
- **게임으로 치면**: 다른 게임들의 스킨이 하는 일을 우리 화면 용어로 전부 적을 수 있는지, 사용자가 자리마다 그림을 연결하는 방식이 실제 스킨의 요구를 덮는지 확인한 것이다.
- **결과**:
  - 75개 중 대응 가능 31, 부분 35, 불가 9다. 부분의 대부분은 요소 종류가 아니라 속성·값·사건 목록이 모자란 것이다.
  - 빠진 큰 개념은 넷이다.
    1. **상태 시계**: 켜진 순간부터 흐르고 꺼지면 숨는 타이머다. 우리 사건은 순간뿐이다.
    2. **박자 시계**: 곡 시각에서 계산하는 박자 위상이다.
    3. **사용자 조정**: 판정선·기어 위치, 요소 끄기·투명도를 사용자가 바꾸는 것이다.
    4. **레인 틀 펼치기·로드 시 조건**.
  - 불가는 입력 위젯(버튼·슬라이더·텍스트 입력)과 Lua의 부작용(파일·HTTP·소리·볼륨·상태 있는 타이머)이다. 셰이더·마스크·파티클은 선례 스킨 형식에도 없다.

- **결론**: 스킨 표현은 **선언형 배치 + 작은 순수 식(읽기 전용 값·사칙·비교·`?:`·min/max/clamp·표 찾기) + 로드 시 펼치기**로 하고, 스크립트는 넣지 않는다. 스크립트로만 되는 것은 상태와 부작용뿐이고, 이는 "화면은 읽기만, 결정성" 원칙과 부딪힌다. `화면_도메인.md`에 위 네 개념과 사건·값·자리 추가분(문서 6장)을 반영한다. 기존 스킨 변환기는 CP4 본 범위 밖에 둔다. 입력 위젯을 스킨 요소로 둘지, 오디오 시각화를 넣을지, 변환기를 언제 할지는 사용자 판단으로 남긴다.

## D1. 판정·오디오 → 화면 상태를 무잠금으로 넘기는 비용

- **무엇을**: 쓰는 쪽은 1 ms마다 4 KiB 상태(판정·점수·레인 불빛 흉내)를 게시하는 스레드(MMCSS Pro Audio)이고, 읽는 쪽은 최신 상태를 통째로 복사하는 화면 스레드다. 읽는 쪽은 두 조건으로 돌렸다. ① 실제처럼 240 Hz ② 쉬지 않고(최악). 방식은 넷이다.
  1. Mutex(쓰는 쪽이 기다림).
  2. **CP3 방식** try_lock(쓰는 쪽이 기다리지 않고 못 잡으면 그 게시를 건너뜀).
  3. 삼중 버퍼(원자 교환).
  4. seqlock(읽는 쪽이 재시도).

  쓰는 쪽 한 번 게시의 시간 분포와 건너뛴 수, 찢어진(일관되지 않은) 읽기 수를 쟀다. 각 5초, 세 번 반복한 범위다.
- **게임으로 치면**: 화면이 점수판을 읽는 동안 판정·오디오 스레드가 줄을 서서 기다리거나, 판정 결과를 화면에 못 넘기고 버리는 일이 생기는지 본 것이다.
- **결과** (`실험/data/d1_snapshot.csv`, 쓰는 쪽 게시 시간):

  | 방식 | 240 Hz 읽기: p99.9 / 최대 | 쉬지 않고 읽기(1개): p99.9 / 최대 / 건너뜀 | 쉬지 않고 읽기(3개): 최대 / 건너뜀 |
  |---|---|---|---|
  | Mutex | 0.8~1.1 / 1.4~2.4 µs | **49~148 / 152~273 µs** / 0 | **227~373 µs** / 0 |
  | try_lock (CP3) | 0.9~1.5 / 2.0~3.9 µs, 건너뜀 0 | 1.0~7.9 / 1.9~21 µs / **1,297~1,354 (26~27%)** | 4~16 µs / **3,255~3,544 (65~71%)** |
  | 삼중 버퍼 | 0.5~1.4 / 0.7~1.9 µs | 0.7~1.0 / 1.2~97 µs(97은 한 번, 선점 추정) / 0 | (읽는 쪽 하나 전용) |
  | seqlock | 0.5~1.0 / 1.2~8.2 µs | 1.3~1.9 / 1.6~8.0 µs / 0 | 1.9~75 µs / 0 |

  - 찢어진 읽기는 모든 방식에서 0이다.
- **결론**: 240 Hz로 한 번씩 읽는 평소 조건에서는 네 방식 모두 문제가 없다. 차이는 화면이 바쁘거나 멈칫할 때 드러난다.
  - Mutex는 오디오 주기(1 ms)의 최대 1/3 남짓을 기다리게 한다.
  - CP3의 try_lock은 기다리지 않는 대신 게시를 버린다. "최신 상태"는 다음 게시가 덮어서 괜찮지만, "이번에 일어난 판정" 같은 순간 사건은 사라질 수 있다.

  그래서 `session → scene` 경계는 둘로 나눈다.
  - **상태(점수·게이지·레인 불빛)**: 삼중 버퍼로 넘긴다. 쓰는 쪽은 늘 상수 시간이고 건너뜀이 없다.
  - **사건(판정·폭발·콤보 끊김)**: 단일 생산자·단일 소비자 링으로 넘긴다. 차이만 보내고 놓치지 않으며, 넘치면 개수만 센다.

  seqlock도 성능은 같다. 다만 읽는 쪽이 재시도하므로 화면 프레임 시간이 쓰는 쪽에 묶이고, Rust에서 안전하게 쓰기가 더 까다롭다. 그래서 삼중 버퍼를 기본으로 한다.


## D2. 화면이 멈춰도 판정·소리가 그대로인가

- 아직 잴 구조가 없다(새 `scene` 모듈). CP4 각 단계에서 회귀 시험으로 넣는다. 렌더 정지·스킨 다시 읽기·영상 디코더 정지를 주입하고, 3-5 싱크 분석기로 잔차 ±0.02 ms가 유지되는지 확인한다.

## F1·E1. 일러스트를 GPU 압축 텍스처(BC7)로

- **무엇을**: B4 표본에서 그림 800장을 골랐다. 머리 그림(STAGEFILE·BANNER·BACKBMP) 406장과 BGA 394장이고, BMP 374·PNG 368·JPEG 58장이다. 그림마다 다음을 쟀다.
  - WIC 디코딩 시간.
  - BC7로 바꾼 뒤의 화질(RGB PSNR)과 크기.

  그다음 800장 전부를 두 길로 GPU에 올려 끝날 때까지의 벽시계·CPU 시간을 쟀다. 세 번 중 최소다.
  - (가) 원본 파일 → WIC 디코딩 → RGBA 텍스처.
  - (나) BC7 파일 → BC7 텍스처(디코딩 없음).

  BC7 인코더는 직접 쓴 간이판이다. 7개 모드 중 모드 6 하나만 쓰므로 **화질은 하한**이다. 크기와 불러오기 시간은 형식의 성질이라 인코더와 무관하다.
- **게임으로 치면**: 곡에 들어갈 때 그림 BGA 수백 장과 재킷·배경을 "압축 풀기" 없이 GPU에 바로 붓는 것이다. 로딩이 짧아지고, CPU가 쉬고, 그래픽 메모리를 4분의 1만 쓰는지 본 것이다.
- **결과** (`실험/data/f1_bc7.csv`, `실험/data/e1_batch_load.csv`):

  | 항목 | 원본 → RGBA | BC7 |
  |---|---|---|
  | 800장 불러오기 (벽시계) | 2,580 ms | **242 ms** (10.6배 빠름) |
  | 그동안 CPU 시간 | 2,531 ms | **188 ms** (13배 적음) |
  | GPU 메모리 | 999 MB | **250 MB** (4배 적음) |
  | 파일 크기 합계 | 283 MB | 250 MB |

  - 디코딩 시간은 그림 크기에 따라 갈린다. 256×256 BGA는 p50 0.49 ms로 원래 싸고, 640×480 넘는 큰 그림(108장)은 **p50 16.4 ms, p95 27.8 ms**다. 큰 그림 하나가 240 Hz 한 프레임(4.17 ms)의 4~7배다.
  - 화질(간이 인코더): PSNR p50 41.5 dB, p25 36.5 dB, p05 30.7 dB이고, 35 dB 미만이 145장(18%)이다. 글자가 많은 배너(높이 100 이하 131장)가 가장 나빠서 p50 36.3 dB다. 큰 그림은 p50 43.3 dB다.
- **결론**: 일러스트(재킷·머리 그림·그림 BGA·스킨 그림)는 **컨버터가 BC7로 바꿔 저장**한다(4의 배수로 채워 넣음, B4). 게임은 디코딩 없이 파일을 그대로 GPU에 올린다. 이것이 "형식을 통일해 할 일 자체를 줄인다"의 가장 큰 사례다. 로딩 10배, CPU 13배, VRAM 4배가 줄고, 곡 중 그림 교체(초당 30~40장)도 이미 올라간 텍스처를 바꿔 고르는 일이 된다. B4의 p95 곡(그림 513장, RGBA 127 MB)도 BC7이면 32 MB다.

  화질은 간이 인코더로 하한만 확인했다. 실제 컨버터는 모드 전체를 쓰는 인코더(예: DirectXTex의 BC7 압축기)를 써야 한다. 또 "BC7 뒤 PSNR이 기준(예: 40 dB) 미만이면 그 그림만 무압축 RGBA로 둔다"는 규칙을 둔다. 배너처럼 작고 글자가 많은 그림이 여기에 걸리고, 작아서 메모리 부담은 적다. 인코더를 내려받아 화질을 다시 재는 것은 사용자 허락이 필요하다(⚑).
- **E2(스킨 다시 읽기)**: 스킨이 아직 없어 추정한다. 스킨 그림 수백 장이 BC7이면 E1 비율로 0.1~0.3초, 원본 PNG면 1~3초다. 다시 읽기는 선곡·설정 화면에서만 허용하고 플레이 중에는 막는다.
