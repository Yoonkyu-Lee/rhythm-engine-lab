# Checkpoint 2 — 플레이 코어와 정책 시험장

> 상태: **범위 확정 (2026-10-15)**. 단계별 진행은 `REPORT.md`에 적는다.
> 근거: CP0 결론([../cp0/REPORT.md](../cp0/REPORT.md), [BMS 구동기 정책 공간](../cp0/BMS_player_timing_policy.md) §11), 설계안([만약 리듬게임을 개발한다면](../design/만약%20리듬게임을%20개발한다면.md) 3·6–12·15장), CP1 실측([../cp1/REPORT.md](../cp1/REPORT.md)).

CP1 싱크로나이저 위에 **건반 하나짜리 리듬게임**을 올린다. 목적은 게임이 아니라 시험장이다.
일부러 오류(렉)를 일으키고, 구동 정책을 바꿔 가며 **게임이 렉을 어떻게 감지하고, 기록하고, 대처하는지** 관측한다.

원칙
- **기존 게임(BMS·IIDX·DJMAX)은 게임 디자인 참고와 시험 콘텐츠일 뿐이다.** 실행 데이터와 처리 구조는 실시간 경로가 필요로 하는 모양에서 거꾸로 정한다.
- **하드코딩은 게임 디자인 쪽만.** 건반 수(1), 판정 창 값, 화면 모양, 노트 노출 시간은 CP3의 기본형을 임시로 고정한 것이다.
- **코어는 진짜로 만든다.** 정규 시간(ns), 자동재생·키음 오디오 경로, 입력 도장, 판정 함수, 렉 감지, 개발자 로그, 고장 주입은 CP3 이후에도 그대로 쓴다. 데이터는 레인 번호가 있는 배열(N=1)로 둬서 건반을 늘릴 때 다시 짜지 않는다.

## 범위

| 부품 | 하는 일 |
|---|---|
| 실행 데이터 | 코어가 읽는 채보·소리 뱅크. 정규 시간 i64 ns, 소비자별(오디오 콜백·판정·화면) 정렬 배열, 미리 디코딩한 PCM, 컴파일 때 계산한 보이스 예산, 해시. BMS 개념(채널, 소절, WAV ID)은 코어에 없다 |
| 오프라인 믹서 | 실행 데이터 → 샘플 정확한 정답 렌더. 실시간 출력을 재는 자(M1) |
| 자동재생 | 건반에 없는 소리 전부. 정책에 따라 오디오 콜백 예약 또는 프레임 즉시 재생 |
| 입력·판정·키음 | 건반 하나. 판정은 순수 함수(정수 ns 창), MISS 확정은 정책에 따라 watermark 또는 프레임 |
| 리플레이 | 입력 기록 + 채보 해시 + 창 + 정책 + 엔진 버전 → 같은 판정 |
| 화면 | 레인 1개, 노트, 판정선, 판정 표시, 렉 감지 HUD |
| 렉 감지 | 게임 스스로 알아챔: 프레임 공백, 오디오 마감 실패·언더런, 시계 점프, 입력 watermark 정체, 키음 지각. 상태 머신(Running / Suspect / Resyncing)과 연결 |
| 개발자 로그 | 경계를 지나는 모든 사건(입력, 판정, 발음 예약·실제 배치, 렉 감지, 정책 행동)을 시각과 함께 기록. 실행 뒤 분석 도구로 표·그래프 |
| 고장 주입 | CP1 지점(오디오 콜백 정지·건너뛰기, 게임 루프 정지, 입력 스레드 굶기기, 시계 점프) + 렌더만 정지, 판정 스레드만 정지 |

### 구동 프로필 (비교 대상)

정책 축 P1–P12를 하나씩 바꾸면 조합이 너무 많아서, 비교는 프로필 넷으로 고정하고 축은 프로필 안에서 개별로도 바꿀 수 있게 한다.

| 프로필 | 시계 (P1·P2) | 소리 (P3·P9) | 로직·입력·판정 (P4·P5) |
|---|---|---|---|
| **우리 방식** | 오디오 장치 시계, 점프 감지 | 오디오 콜백 샘플 예약, 겹치기 | 입력 도장 (c) + watermark |
| **IIDX 개량형** | 프레임 틱 + 오디오 위치로 slew (양방향, 문턱·속도 제한, 정지 구간은 진행률 추정에서 제외) | 틱에서 발음 | 틱 처리 |
| **DJMAX식** | 프레임 시계, 프레임당 0.333초 상한 | 프레임 즉시 재생, 트랙당 프레임당 1개, 겹치기 | 200 Hz 고정 스텝 판정 |
| **BMS식** | OS 단조 시계, 개방 루프 | 프레임 즉시 재생, 다시 울리면 끊기 | 1 kHz 폴링 입력, 미스·발음은 프레임 |

### 시험 콘텐츠

- **합성 곡**: 반주 + 4비트 축연타 클릭. 자동 플레이어가 완벽하게 치면 오차가 곧 엔진 오차라 분석이 깨끗하다.
- **실제 곡**: 변환곡에서 트랙 하나를 건반으로 뽑고 나머지는 자동재생. 실제 키음 밀도, 겹침, 긴 반주를 본다. 변환은 코어 밖 어댑터가 한다.
- **자동 플레이어**: CP1의 SendInput 봇. 사람 없이 "고장 시나리오 × 프로필" 표를 채운다. 사람 플레이는 체감 확인용.

**빼는 것 (CP3 이후)**: 건반 수 매개변수화, 노트 노출 시간과 속도 설정, 노트·기어 스킨, 기어 표기 구조(예: DJMAX 사이드·트리거가 다른 노트의 공간을 공유하는 방식), 그래픽 애셋 연결, 환경설정 체계, 작성용 곡 형식과 정식 가져오기, 곡 목록. 그 밖에 광센서 측정, 장치 타임스탬프 입력, 일정 지연 키음 모드, 절전 복구.

## 단계

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| 2-0 | 실행 데이터와 시험 곡 | 실행 데이터 타입·배치 확정. 합성 곡과 실제 곡 1개를 실행 데이터로 만들고, 발음 목록이 독립 렌더러와 1 ms 안에서 일치 |
| 2-1 | 오프라인 믹서 | 같은 실행 데이터 → 비트 단위로 같은 PCM. 표본 곡 렌더가 기존 렌더와 일치 |
| 2-2 | 게임 뼈대 + 우리 방식 | 창·레인·노트·판정·자동재생·키음이 돌고, 개발자 로그가 남음. 무입력 재생의 루프백 = 오프라인 렌더 (예정 프레임 배치 오차 ≤ 1프레임) |
| 2-3 | 렉 감지와 상태 머신 | 고장 주입마다 게임이 스스로 감지해 HUD·로그에 남기고, 정책대로 대처(판정 보류, 재동기화) |
| 2-4 | 다른 세 프로필 | IIDX 개량형·DJMAX식·BMS식이 같은 게임에서 바꿔 끼워짐. 각 프로필의 알려진 동작(빨리 떨어짐, 0.333초 손실, 밀린 소리 몰림)이 재현됨 |
| 2-5 | 비교 실험 | "고장 시나리오 × 프로필" 표: 발음 오차(M1), 판정 시각 오차(M2), 렉 복구(M3), 화면 불연속(M4), 판정 결정성(M7), 입력→키음 지연(M8). 늦은 짧은 키음 정책(밀기/버리기)도 여기서 결정 |
| 2-6 | 마무리 | 리플레이 재현 100%. 결론을 리포트로 남기고 CP3 기본형에 넘길 결정 사항 정리 |

## 정할 것

1. **화면 기술**: `wgpu`(실제 스왑체인이라 화면 쪽 정책·프레임 시각까지 관측 가능) 추천. 설계안 14장의 "측정 전 교체 금지"와도 맞다.
2. **실제 곡**: 어느 곡의 어느 트랙을 건반으로 뽑을지 (2-0에서 후보를 골라 제안).
