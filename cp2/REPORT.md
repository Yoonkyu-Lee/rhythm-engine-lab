## 2-0. 실행 데이터와 시험 곡 (2026-10-15)

- **무엇을**: 코어가 읽는 유일한 곡 표현을 정했다(`crates/rcore`). 시간은 정규 i64 ns이고, 소비자별 정렬 배열(자동재생은 오디오 콜백이 한 번 훑음, 노트는 레인별, 스크롤 지도는 화면용)과 곡 소리 전부를 이어 붙인 PCM 뱅크 하나로 이뤄진다. 볼륨은 이벤트마다 선형 이득이고, 화음은 노트 하나가 소리 여러 개를 가리킨다. 컴파일 단계가 순서·범위를 검증하고 동시 발음 최댓값에서 보이스 예산을 잡고 해시를 붙인다. 파일 형식 `.rtc`(고정 순서 바이너리)는 외부 크레이트 없이 읽고 쓴다. 시험 곡은 합성 곡(120 BPM 4비트 축연타)과 DJMAX 곡에서 트랙 하나를 건반으로 뽑은 곡 둘(BlythE, 템포가 바뀌는 Negative Nature)이다. 어댑터는 코어 밖 Python(`tools/`)이다.
- **게임으로 치면**: 게임이 플레이 중 읽을 악보·소리를 "기존 형식의 흔적 없이, 실시간 처리가 바로 쓸 수 있는 모양"으로 미리 만들어 두는 것. 렉에 강한 구조의 첫 조건이다(플레이 중 파일 읽기·디코딩·할당이 없음).
- **결과**: 바이트 왕복(쓰기 → 읽기 → 쓰기)이 Rust·Python 모두 같다. 어댑터가 만든 발음 목록을 변환기와 코드를 공유하지 않는 BMS 렌더러로 읽은 같은 채보와 대조하니 BlythE 2,424개, Negative Nature 1,635개 모두 1 ms 반올림에서 빠짐 0 · 남음 0. 보이스 예산은 합성 곡 13(최대 4), BlythE 39(최대 25), Negative Nature 26(최대 15). 곡당 PCM 뱅크는 약 80 MB(44.1 kHz 스테레오 f32).
- **결론**: 실행 데이터 형식이 정해졌고 시험 곡 3개가 준비됐다. 기준 BPM은 데이터에 명시해서(DJMAX 곡은 곡 정보 BPM) 구동기가 추정하지 않는다. 남은 제약: 뱅크는 44.1 kHz만(리샘플링 없음), f32라 곡당 80 MB 수준이다(메모리 배치 최적화는 측정 뒤에).

## 2-1. 오프라인 믹서 (2026-10-15)

- **무엇을**: 실행 데이터를 출력 스트림에 섞는 믹서를 만들었다(`crates/rcore/src/mixer.rs`). 오프라인 렌더와 실시간 오디오 콜백이 **같은 코드**를 쓴다. 자동재생과 플레이어 키음을 예정 프레임 순으로 올리고, 보이스는 고정 크기 풀에서 들어온 순서를 유지하며, 늦은 소리는 긴 소리·짧은 소리 각각 정책(자르기 / 처음부터 / 버리기)을 따른다. 무슨 일이 있었는지(발음, 늦음, 버림, 풀 넘침)는 사건 로그로 남긴다. `render` 도구가 "모든 노트를 제때 친" 정답 렌더를 WAV로 쓴다.
- **게임으로 치면**: 렉이 전혀 없을 때 이 곡이 "들려야 하는 정답 소리"를 미리 만들어 두는 것. 이후 실시간 재생과 렉 실험은 모두 이 정답과 비교해서 "얼마나 틀렸나"를 잰다.
- **결과**: 블록 크기를 1·64·441·4,096으로 바꿔도 세 곡 모두 **비트 단위로 같은** 소리가 나왔다(실시간 콜백의 들쭉날쭉한 블록 크기에도 결과가 변하지 않는다는 뜻). 믹서 코드와 무관한 numpy 렌더와의 최대 차이는 3×10⁻⁷(float 반올림 수준). 기존 BMS 렌더러와는 상관 0.9999, 배율을 맞춘 뒤 잔차 −37~−38 dB, 위치 어긋남 0프레임(남은 차이는 BMS 쪽이 볼륨을 0.5 dB 단위 사본으로 묶은 탓). 렌더 속도는 실시간의 3,500~12,600배.
- **결론**: 정답 렌더라는 자가 생겼다. 새로 드러난 과제 하나: DJMAX 곡은 섞은 결과의 최댓값이 1.76~2.15라 그대로 내면 장치에서 잘린다(클리핑). 마스터 이득(헤드룸) 정책이 필요하며, 실시간 출력을 붙이는 2-2에서 정한다.

## 2-2. 게임 뼈대 + 우리 방식 (2026-10-15)

- **무엇을**: 건반 하나짜리 게임(`cp2game run`)을 만들었다. 스레드는 화면·오디오·입력·판정·자동 플레이어·녹음·기록 일곱 개이고, 실시간 스레드끼리는 잠금 없는 SPSC 링과 원자 변수만 쓴다. "우리 방식" 프로필: 오디오 콜백이 곡을 직접 섞고(자동재생은 프레임을 기다리지 않음), 판정은 입력 시각을 장치 시계로 곡 시간에 바꿔 순수 함수로 하며, MISS는 입력 스레드의 watermark가 지난 뒤에만 확정한다. 화면은 D3D11 + DXGI flip 모델(대기 가능 스왑체인, 최대 지연 1) 위의 Direct2D이고 렌더러 인터페이스 뒤에 있다. 장치가 48 kHz라 곡을 불러올 때 소리 뱅크를 윈도 sinc로 리샘플링한다(설계안 8-1). 측정 도구: 노트가 "들리는 순간"에 OS 입력을 넣는 자동 플레이어, 믹서 사건 로그로 실제 출력 스트림을 재구성해 루프백과 맞추는 분석기, 판정·입력 경로·키음·프레임 분석기.
- **게임으로 치면**: 처음으로 "치는 게임"이 됐다. 렉이 없을 때 판정이 얼마나 정확한지, 버튼을 누르고 키음이 나오기까지 얼마나 걸리는지, 화면이 얼마나 고르게 나오는지를 재는 기준 상태다.
- **결과** (자동 플레이어, 고장 없음): 합성 곡 256노트·BlythE 103노트(롱노트 11) 모두 PERFECT. 판정 오차 평균 +0.46~0.52 ms, p99 0.7~0.9 ms (SendInput → Raw Input 전달 지연 0.45~0.52 ms와 같은 크기라 엔진 자체 오차는 거의 0). 판정 처리 지연 p99 1.1~1.3 ms. 키음: 누름 → 장치 출력 34~42 ms(평균 38, 공유 모드 출력 버퍼에 이미 쌓인 소리 뒤에 놓이는 고정 지연). 화면 239 fps(240 Hz), 프레임 간격 p99 5 ms·p99.9 16 ms, DXGI 프레임 통계 99.99%. 오디오: 재구성한 출력 스트림과 루프백이 밀림 0, 출력 경로 필터 보정 뒤 잔차 −56~−66 dB. 무입력 자동 연주 모드도 정답 렌더와 0프레임 차이. 언더런 주입(50·150·300 ms)은 스트림 전체를 +38/+176/+464 ms 밀었고 장치 위치 보고도 1 ms 이내로 같이 밀렸다(CP1 결론 재현).
- **결론**: 기준 상태가 생겼다. 만들며 고친 것 셋: (1) 입력 도장 (c)는 틱 경계를 넘으면 거의 안 기다린 입력도 16 ms 과거로 보냈다 → "큐가 비었다고 확인한 마지막 순간"보다 앞으로 가지 않게 잘랐다(watermark 위반 0). (2) 2초 넘는 플레이어 키음이 "긴 소리는 앞부분 자르기" 정책을 타서 어택이 잘렸다 → 늦음 정책을 출처별(플레이어·자동 짧은 소리·자동 긴 소리)로 나눴다. (3) DJMAX 곡은 섞으면 최댓값이 1.76~2.15라 곡마다 마스터 이득으로 −1 dBFS에 맞춘다. 출력 경로(장치 또는 OS)에 고음 +1 dB 정도의 선형 EQ가 있어 비트 일치는 불가능하지만 타이밍에는 영향이 없다. 키음 38 ms는 공유 모드의 구조적 하한이라 저지연 모드(IAudioClient3)·ASIO가 정책 후보다.
