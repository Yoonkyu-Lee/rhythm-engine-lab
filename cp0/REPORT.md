# CP0 리포트 (번외편: 기존 게임 분석)

엔진을 만들기 전에, 기존 리듬게임(IIDX, BMS 구동기)이 채보와 시간을 어떻게 다루는지 분석한 기록입니다.
단계마다 네 줄: **무엇을**(기술적으로 무엇을 했나) · **게임으로 치면**(플레이 입장에서 무엇을 보는가) · **결과** · **결론**.
자세한 표와 도구 사용법은 [README.md](README.md)에 있습니다. IIDX 역공학 상세 문서와 도구는 비공개(로컬 전용)라서, 여기에는 결론만 적습니다.

## 0-1. IIDX 채보(.1)와 BMS 구조 비교 (2026-10-09)

- **무엇을**: IIDX `.1` 채보 하나(33131 Ex-Otogibanashi)를 바이트 단위로 풀었다. BMS 팩의 차분 2,984개에 대해 인코딩, 채널, 헤더 명령 사용 빈도를 전수 집계해 두 형식을 비교했다 (`dot1_peek.py`, `bms_peek.py`, `bms_stats.py`).
- **게임으로 치면**: 같은 곡을 IIDX와 BMS가 각각 어떻게 적어 두는지 보는 것이다. "언제 어떤 소리를 울리고, 어떤 노트를 치는가"를 비교한다.
- **결과**:
  - IIDX: 8바이트 고정 이벤트에 **절대 시각(ms)**을 적는다. 레인에 소리를 걸어 두고, 노트는 레인만 가리킨다. 파일 하나에 난이도 칸 12개가 빈틈없이 이어진다.
  - BMS: 텍스트로 **악보 위치(소절 + 격자)**를 적고, 노트가 소리 ID를 직접 가진다. 인코딩 선언이 없어서 팩이 cp932 1,536개와 UTF-8 1,444개로 갈린다.
  - 차분당 키음은 중앙값 749개, 최대 2,844개다. 36진 ID 한계 1,295개를 넘는 차분은 `#BASE 62`를 쓴다.
- **결론**: 둘 다 짧은 소리를 조립하는 "키음 조립식"이라 변환할 수 있다. 다만 IIDX→BMS는 시각을 격자에 맞춰 양자화해야 하고, "레인 소리 교체"를 노트별 소리 ID로 펼쳐야 한다. 엔진의 곡 형식은 절대 시각과 악보 위치를 둘 다 가져야 한다.

## 0-2. IIDX 데이터 전수 조사 (2026-10-10)

- **무엇을**: 모든 `.1` 채보와 곡 DB를 훑어 변환기에 필요한 사실을 숫자로 확인했다 (`iidx_survey.py`, `type8_survey.py`, `scene_export.py`).
- **게임으로 치면**: 곡 하나가 아니라 전곡에서 확인하는 것이다. 어느 칸이 SP ANOTHER인지, 키음 번호가 0부터인지 1부터인지, 판정 폭 값이 무슨 단위인지를 본다.
- **결과**:
  - 칸 0~4 = SP H/N/A/B/L, 6~10 = DP H/N/A/B/L
  - 소리 번호는 1부터다 (0 = 소리 없음).
  - 노트 값 = 롱노트 길이(ms)
  - type 8 = 판정 창 (1/60초 단위)
  - 차분별 소리 묶음은 곡 DB에 적힌 접미사로 고른다.
- **결론**: 커뮤니티 기준으로만 알려져 있던 내용을 전곡 데이터로 확정했고, 이를 컨버터의 근거로 썼다.

## 0-3. IIDX 타이밍 정책 (2026-10-09)

- **무엇을**: IIDX 실행 파일을 정적으로 역어셈블해 채보 진행, 오디오 동기화, 주사율 처리를 추적했다. 실행 환경(spice2x)이 시간이나 오디오를 건드리는지는 소스로 확인했다. 실행해서 확인하지는 않았다.
- **게임으로 치면**: IIDX에서 렉이 걸린 뒤 노트가 빨리 떨어지며 반주를 따라잡는 현상이 어디서 나오는지 보는 것이다.
- **결과**:
  - 채보는 "화면 프레임 1개 = 틱 1개"인 고정 틱으로 진행한다.
  - 두 프레임마다 반주 트랙의 재생 위치와 비교한다. 채보가 17 ms 넘게 늦으면 틱을 하나 더 돌린다. 그래서 약 1.5배속으로 따라잡고, 300 ms 지연은 약 0.6초에 해소된다(계산).
  - 채보가 34 ms 넘게 앞서면 늦추지 않고 기록만 한다.
  - 곡이 끝나면 누적 보정량으로 주사율 추정치를 다시 맞춘다.
  - spice2x는 시간이나 오디오 위치를 건드리지 않는다.
- **결론**:
  - IIDX는 프레임 시계를 기본으로 두고, 오디오 쪽으로 천천히 당겨 맞추는(slew) 폐루프 방식이다.
  - 키음은 틱에서 울리므로 렉 동안 늦게 난다.
  - 화면이 계속 80 FPS 아래로 떨어지면 따라잡지 못한다(계산).

## 0-4. BMS 구동기 타이밍 정책 (2026-10-11)

- **무엇을**: 공개 소스 BMS 구동기 두 개를 읽었다. beatoraja(`8320241`)와 Lunatic Vibes F(`3e8a655`, LR2 클론)다. "시계·오디오·입력"과 "판정·믹싱·렌더" 두 축으로 나눠 축별 보고서 4개를 썼다. 실행은 하지 않았다.
- **게임으로 치면**: LR2·beatoraja 계열에서 렉이 걸리면 소리와 판정이 어떻게 되는지, 판정 오프셋이 실제로 무엇을 옮기는지 보는 것이다.
- **결과**:
  - **오디오:** 둘 다 오디오 장치의 재생 위치를 한 번도 읽지 않는 개방 루프다. 렉 뒤에는 밀린 소리를 한꺼번에, 처음부터 울린다.
  - **시계:** OS 벽시계를 쓴다.
  - **판정 오프셋:** 둘 다 화면에만 적용된다.
  - **입력:** 1 kHz 폴링으로 시각을 찍어서, 판정 오차는 FPS와 분리했다. 하지만 미스 판정, LN 완료, 발음은 프레임이 올 때 처리한다.
  - **같은 소리 다시 울리기:** 둘 다 앞 소리를 끊는다.
  - **판정 창:** LVF는 LR2 표를 쓴다(NORMAL PG ±18 ms, 실제로는 −18~+17). beatoraja는 µs 표에 #RANK 비율을 곱한다(NORMAL PG ±15 ms).
- **결론**: BMS에는 IIDX처럼 기준이 되는 반주 트랙이 없는 경우가 많다. 그래서 정답 오디오 시계는 장치가 실제로 내보낸 샘플 수여야 하는데, 두 구동기 모두 이 방식을 쓰지 않는다. 이 빈칸이 우리 엔진이 메울 자리다.

## 0-5. 정책 공간과 측정 지표 (2026-10-12)

- **무엇을**: 세 게임에서 본 메커니즘을 정리했다. 엔진에서 바꿔 끼울 수 있는 정책 축 12개(P1 기준 시계 ~ P12 화면 속도 모델)와 측정 지표 8개(M1 발음 오차 ~ M8 지연 분포)다.
- **게임으로 치면**: "어느 게임이 옳은가"를 따지는 게 아니다. 같은 플레이 기록과 같은 렉을 넣고 정책만 바꿔 가며 재서 고르자는 것이다. 예를 들면 "소리가 몇 ms 늦나", "렉 뒤 몇 초 만에 돌아오나"를 잰다.
- **결과**: 정책끼리 서로 묶이는 곳도 표시했다. 예를 들어 입력 시각을 프레임 시각으로 찍으면 판정이 FPS에 묶인다. 또 샘플 단위 예약은 오디오 장치 시계가 있어야 의미가 있다.
- **결론**: 정책을 바꿔 끼우는 구조보다 "같은 입력과 같은 오디오를 다시 돌려 재는 장치"가 먼저 있어야 한다. 이것이 CP1(싱크로나이저 + 테스트벤치)의 출발점이 됐다.

## 응용. IIDX → BMS 컨버터 (2026-10-11 완료)

- **무엇을**: 0-1~0-3에서 확인한 사실로 IIDX 곡(채보 + 소리 묶음)을 BMS로 바꾸는 변환기를 만들었다. 검증은 변환기와 코드를 공유하지 않는 독립 BMS 렌더러, 그리고 게임 미리듣기와의 비교로 했다 ([../converter/](../converter/)).
- **게임으로 치면**: IIDX 곡을 BMS 플레이어(beatoraja, LR2, Qwilight)에서 원곡과 같은 소리, 같은 타이밍으로 칠 수 있게 하는 것이다.
- **결과**:
  - 전곡 2,622곡을 변환했고, 노트 시각 양자화 오차는 최대 1.9 ms다.
  - 작품별 난이도 테이블은 SP 8,334차분, DP 7,791차분이다.
- **결론**: 형식 분석이 맞았다는 실증이다. 변환기는 완결됐고, 엔진의 곡 가져오기(CP3)에서 다시 쓸 수 있다.
