# Checkpoint 1 — 싱크로나이저와 테스트벤치

엔진의 맨 밑층입니다. **시계를 읽는 곳은 이 층뿐**이고, 위층은 정규 시간(ns)만 받습니다.

## 범위

| 부품 | 하는 일 |
|---|---|
| 시계 | 오디오 장치가 내보낸 샘플 수 + QPC → 정규 시간 모델 (기준점, 유효성, 불확실성) |
| 예약기 | "정규 시각 t에 소리 X" → 샘플 위치. 늦으면 앞부분을 잘라 냄. 비교용 정책: 즉시 재생 |
| 입력 도장 | Raw Input의 QPC 시각 → 정규 시각, 큐, 넘침 감지 |
| 기록 | 경계를 지나는 모든 순간의 로그 |
| 고장 주입 지점 | 오디오 콜백 지연·건너뛰기, 소비자 스레드 정지, 입력 스레드 굶기기, 시계 점프 흉내 (평소 꺼짐) |

**테스트벤치**(싱크로나이저 옆): 클릭 트랙 재생, 정해진 시각에 고장 주입, `SendInput` 가짜 입력, 루프백 녹음 분석, 보고서.

**빼는 것**: 채보, 판정, 노트, 렌더, ASIO와 WASAPI 배타 모드, 화면 표시 예측, 장치 분리·절전 복구, 하드웨어 기준 입력 측정.

## 완료 기준

1. 평소: 예약한 클릭과 실제 출력의 차이 분포(중앙값, p99)와 고정 출력 지연을 잰다.
2. 고장 A(오디오) · B(화면) · C(연산) · D(시계)를 넣었을 때 실측이 설계대로 나온다.
3. 정책을 "즉시 재생"으로 바꾸면 BMS 구동기식 어긋남이 재현되고, 두 정책의 차이가 숫자로 나온다.

## 측정 장비

TOPPING E2x2 OTG, 노트북 → 썬더볼트 독 → 오인페 연결 (장치 트리: E2x2 → 독의 USB 허브 → 노트북 내장 Intel USB 3.2 xHCI). 스마트 앱 컨트롤은 2026-10-13에 껐다 (직접 빌드한 테스트벤치가 차단되어서). 게임은 **Playback 1/2**로 내보내고, 테스트벤치는 **Loopback 1/2**(제어 앱에서 Loopback 1+2 ← Playback 1/2로 설정)로 녹음합니다.

## 사용법

```powershell
cargo build --release
.\target\release\testbench.exe list                     # 장치와 공유 모드 형식
.\target\release\testbench.exe step0 --secs 600         # 클릭 재생 + 루프백 녹음 → runs\step0-<시각>\
python -I tools\analyze_step0.py runs\step0-<시각>      # 분석 → summary.json
```

## 실험할 때 주의

- 오디오 실험(`step0`, `sched`) 중에는 E2x2로 다른 소리(영상, 게임, Windows 알림음)를 내지 않는다. 공유 모드는 모든 앱 소리를 Playback 1/2에 섞어 루프백에 같이 녹음된다. 방해 금지 모드 권장.
- Playback 1/2의 Windows 볼륨을 0이나 음소거로 두지 않는다 (루프백보다 앞에서 적용). 소리가 듣기 싫으면 제어 앱 Mix B에서 Playback 1/2만 뮤트한다.
- 제어 앱 설정(샘플레이트, 버퍼, 루프백 경로)을 바꾸거나 인터페이스를 뽑지 않는다. ASIO·배타 모드 프로그램(spice2x IIDX, Qwilight ASIO)은 장치를 독점하므로 끈다.
- 무거운 작업(게임, 대형 빌드, 인코딩)은 실제 언더런을 만들어 평상시 값을 오염시킨다. 가벼운 작업은 괜찮다.
- 입력 실험(`input`)은 F24 키를 초당 4번 시스템에 보낸다. 30초 동안 키보드(특히 Ctrl·Shift)를 누르지 않는다.
- `clockeval`, `clockjump`, Python 분석은 기록만 읽으므로 제약 없음.

## 0번 단계 결과 (2026-10-12, 측정 기준 확보: 완료)

WASAPI 공유 모드, 이벤트 구동, 44,100 Hz float32, 버퍼 970프레임, 엔진 주기 10 ms, MMCSS Pro Audio. 클릭: 1초부터 0.5초마다 3샘플 펄스.

| 항목 | 10분 측정 | 재시작 5회 (각 15초) |
|---|---|---|
| 클릭 검출 | 1,198 / 1,198 | 28 / 28 × 5 |
| 프레임 오프셋 (루프백 위치 − 재생 프레임) | 10분 내내 한 값 | 회마다 한 값 (시작 시점 차이) |
| 드리프트 (재생 ↔ 루프백) | 0.000 ppm | 0.000 ppm |
| 캡처 끊김 | 0 | 0 |
| 왕복 (렌더 "재생됨" 보고 → 루프백 "녹음됨" 보고) | 25.42 ms (σ 0.29, p99 25.90) | 25.37–25.50 ms |
| 출력 버퍼 깊이 (쓴 순간 → "재생됨" 보고) | 41.83 ms (σ 0.29) | 41.74–41.77 ms |

결론:
1. 루프백은 샘플 단위로 정확하고 재생과 같은 시계다 → **측정 기준자로 쓴다.**
2. 이 PC 공유 모드 상수: 쓴 순간 → 재생 보고 ≈ 41.8 ms, 재생 보고 → 루프백 녹음 보고 ≈ 25.4 ms (출력·입력 몫 분리는 케이블 실험 필요).
3. 오디오 장치 시계는 QPC보다 7.4 ppm 느리다 (분당 0.44 ms). QPC를 진실로 두면 이만큼 밀린다.
4. **보고 시각의 σ 0.29 ms는 잡음이 아니라 톱니다** (아래 1번 단계에서 밝힘). 15초 창으로 시계 비율이 ±50 ppm까지 틀린 것도 이 때문.

## 1번 단계: 시계 부품 (2026-10-12)

`synchronizer::clock::ClockModel`: (장치 위치, QPC) 보고값으로 `frame = a + b·t` 를 맞춘다. 정책 `ClockPolicy` (창 길이, 기울기를 맞추기 시작하는 구간 길이, 대응 깨짐 판정, 평균/중앙값 절편).
`testbench clockeval <run>`: 기록된 보고값을 시간 순서대로 다시 넣어 정책별 예측 오차를 잰다.

**보고값의 구조** (10분 기록, 확인):
- 이웃한 보고값끼리의 차이는 σ 0.019 ms. 약 1%는 혼자 0.1–0.3 ms 튀었다가 바로 돌아온다.
- **약 135초마다 정확히 +1.0 ms 계단**이 영구적으로 생긴다 (0.6, 133.3, 268.3, 401.4, 538.8초). 계단 사이는 명목 샘플레이트로 평평하다. 녹음 쪽 보고값도 같은 순간에 같은 계단.
- 해석 (추정, 근거 강함): 드라이버가 명목 속도로 위치를 계산하다가, 실제 장치 시계(QPC 대비 −7.4 ppm)와의 차이가 USB 프레임 하나(1 ms)만큼 쌓이면 한 번에 고친다. 7.4 ppm × 135초 ≈ 1 ms로 주기가 맞고, 0–1 ms 톱니의 σ = 1/√12 ≈ 0.289 ms가 0번 단계의 σ 0.288 ms와 같다.
- 따라서 **실제 소리의 시계는 매끄러운 직선**이고, 보고값을 그대로 쓰면 최대 약 0.5 ms 틀린다.

**정책 비교** (정답 = 10분 전체 직선, p50 / p99 ms):

| 정책 | 0–10초 | 10–150초 | 150–300초 | 300초 이후 |
|---|---|---|---|---|
| 원시값 (직전 보고 + 명목 비율) | 0.40 / 0.58 | 0.26 / 0.53 | 0.26 / 0.52 | 0.23 / 0.51 |
| 명목 비율 + 1초 평균 절편 | 0.40 / 0.56 | 0.26 / 0.53 | 0.26 / 0.52 | 0.23 / 0.50 |
| 120초 창, 기울기 30초부터 | 0.29 / 0.56 | 0.24 / 0.53 | 0.21 / 0.52 | 0.23 / 0.50 |
| 300초 창, 기울기 150초부터 | 0.29 / 0.56 | 0.25 / 0.56 | 0.10 / 0.27 | 0.06 / 0.14 |
| **600초 창, 기울기 150초부터 (기본)** | 0.29 / 0.56 | 0.25 / 0.56 | 0.10 / 0.27 | 0.04 / 0.17 |

결론:
- 기본 정책 = 600초 창, 톱니 한 주기(150초)가 쌓인 뒤부터 기울기 맞춤. 5분 뒤부터 0.1 ms 안.
- **처음 2–3분은 약 0.25–0.5 ms가 바닥**이다. 톱니 정보가 계단이 일어날 때만 들어오므로 어떤 정책도 더 빨리 알 수 없다.
- 판정 창(PGREAT ±15–18 ms)에 비하면 작다. 소리 예약은 시각이 아니라 프레임 위치로 하므로 이 오차와 무관하다. 이 오차가 들어가는 곳은 입력 시각(QPC) → 장치 프레임 변환뿐이다.
- 톱니 주기는 장치의 ppm에 달렸다 (1 ms ÷ |ppm|). 다른 장치·ASIO에서는 다시 재야 한다.

## 2번 단계: 예약기 (2026-10-12)

`synchronizer::scheduler::Mixer`: 명령 `At { frame }`(정해진 프레임에서 시작) / `Now`(지금 채우는 블록 맨 앞에서 시작). 늦은 `At`은 `LatePolicy`(앞부분 잘라 내기 / 통째로 밀기)를 따른다.
`testbench sched --mode sample|immediate [--fps N] [--lookahead-ms 100]` + `tools/analyze_sched.py`: 왼쪽 채널은 시험 이벤트(0.5007초 간격), 오른쪽 채널은 정확한 프레임에 직접 쓰는 기준 클릭. 기준 클릭으로 루프백 위치를 재생 프레임 번호로 바꿔 시험 이벤트의 실제 오차를 잰다.

60초씩, 이벤트 117개 (양수 = 늦게 울림):

| 정책 | 평균 | σ | 범위 |
|---|---|---|---|
| **샘플 예약, 100 ms 미리** | **0.00 ms** | **0.000** | 117개 모두 예정 프레임 그대로 |
| 즉시 재생, 게임 루프 60 fps | 44.8 ms | 5.23 ms | 35.1–57.7 ms |
| 즉시 재생, 144 fps | 39.8 ms | 3.46 ms | 32.6–47.6 ms |
| 즉시 재생, 240 fps | 38.8 ms | 3.14 ms | 32.2–45.1 ms |

예약기 내부 기록과 루프백 실측이 모든 이벤트에서 같았다.

결론:
- 샘플 예약은 샘플 단위로 정확하다 (설계안의 바닥이 성립).
- 즉시 재생의 흔들림 = 게임 루프가 알아채는 기다림(0–1프레임) + 오디오 엔진이 다음 블록을 채우는 기다림(0–10 ms). 둘이 고르게 퍼진다고 보면 σ = √(프레임² + 10²)/√12 → 60 fps 5.6 ms(실측 5.23), 240 fps 3.1 ms(실측 3.14).
- **fps를 올려도 σ ≈ 2.9 ms(범위 약 10 ms)가 바닥**이다. 공유 모드 엔진 주기 10 ms 때문. 평균 지연은 사용자 오프셋으로 맞출 수 있지만 흔들림은 못 고친다.
- 아직 안 한 것: 늦은 `At` 처리(앞부분 잘라 내기)는 고장 주입과 함께 시험한다. 3샘플 클릭은 3샘플 넘게 늦으면 통째로 잘려 사라지므로, 그 시험은 긴 소리로 한다.

## 3-1 단계: 고장 A·B (2026-10-12)

`testbench sched ... --sound noise --faults A@10:50,A@20:150,B@30:300,B@40:600` + `tools/analyze_faults.py`.
고장 A = 렌더 스레드가 그 시각에 ms 동안 버퍼를 안 채움(언더런). 고장 B = 게임 스레드가 ms 동안 멈춤.
시험 소리는 50 ms 노이즈 버스트: 예약기 기록 위치 ±30 ms에서 상호상관으로 실제 위치와 남은 비율을 잰다.

| | 샘플 예약 + 앞부분 자르기 | 샘플 예약 + 통째로 밀기 | 즉시 재생 144 fps |
|---|---|---|---|
| 평상시 (84개) | 0.00 ms, 100% | 0.00 ms, 100% | 평균 40.3 ms, σ 3.4 |
| A 50 ms 뒤 스트림 | +38.0 ms 밀림 | +38.0 ms | +38.0 ms |
| A 150 ms 뒤 스트림 | 누적 +176.0 ms | +176.0 ms | +176.0 ms |
| 끊긴 순간의 소리 | 찢어짐 (5.5%, 0%) | 같음 | 같음 |
| B 300 ms | 영향 없음 | 영향 없음 | 그 시점 소리 +305 ms |
| B 600 ms | 늦은 1개 **사라짐 (0%)** | 늦은 1개 **+90.7 ms, 100%** | 2개가 +581, +81 ms로 겹쳐 나옴 |
| 고장 뒤 | 0.00 ms | 0.00 ms | 41.7 ms, σ 3.4 |

재생 위치 보고(IAudioClock) 계단: A 50 ms → +18.7 +9.5 +9.7 = +38.0 ms, A 150 ms → +118.5 +9.8 +9.9 = +138.2 ms. 기준 클릭으로 잰 밀림과 같다.

결론:
- 언더런은 소리를 건너뛰지 않고 그 자리에 무음을 끼워 넣는다. 이후 모든 소리가 같이 밀리고, 재생 위치 보고도 같은 양만큼 밀린다 → 시계 모델이 계단을 보고 새 기준점을 잡으면 판정 시계를 오디오와 함께 밀 수 있다.
- 즉시 재생도 고장 A 뒤에는 상대 위치가 유지됐다(게임이 재생 위치 기반 시계를 써서). BMS 구동기처럼 PC 시계만 쓰면 이 밀림이 판정과 어긋남으로 남는다(도감 고장 A, 추정).
- 게임 멈춤은 미리 보내기가 완충한다: 출력 깊이 약 42 ms를 빼면 미리 100 ms 중 약 58 ms까지는 늦을 일이 없다. 그보다 긴 멈춤에 걸린 이벤트만 늦는다.
- 늦은 짧은 소리: 자르기는 사라지고 밀기는 늦게 난다. 긴 소리는 자르기가 남은 부분을 제자리에 둔다 → 소리 길이에 따른 혼합 정책 후보 (다음 단계에서 긴 소리로 확인).

## 3-2 단계: 입력 도장과 고장 C (2026-10-12)

`synchronizer::input::RawKeyboard`: 전용 스레드가 메시지 전용 창으로 Raw Input 키보드를 받는다 (`RIDEV_INPUTSINK`). 이벤트마다 받은 순간의 QPC, 메시지에 붙은 틱(`GetMessageTime`), 받은 순간의 틱(`GetTickCount`)을 남긴다. `KeyEvent::estimated_qpc()` = 받은 QPC − (받은 틱 − 메시지 틱).
`testbench input --stalls 10:100,20:300` + `tools/analyze_input.py`: 가짜 플레이어가 `SendInput`으로 F24를 250 ms마다 누른다 (누른 길이 5/30/80 ms 반복). 정답 = SendInput 직후 QPC. 고장 C = 그 시각에 폴링 스레드와 Raw Input 스레드를 함께 멈춤.

| 정책 | 평상시 112개 | 100 ms 멈춤 중 5 ms 탭 | 300 ms 멈춤 중 30 ms 탭 | 300 ms 멈춤 끝 50 ms 전 80 ms 탭 |
|---|---|---|---|---|
| (a) 폴링 1 kHz (BMS 구동기 방식) | +0.70 ms (−0.2…+1.4) | 유실 | 유실 | +50.7 ms |
| (b) Raw Input 받은 순간 QPC | +0.04 ms (0.0…+0.1) | +100.2 ms | +299.9 ms | +50.3 ms |
| (c) (b) − 큐에서 기다린 틱 | +0.04 ms | +7.2 ms | +2.9 ms | +3.3 ms |

뗌도 같은 양상 (평상시 (a) +0.62, (b)(c) +0.04 ms; 멈춤 중 (b) 최대 +270 ms, (c) 최대 +4.3 ms). `GetTickCount` 해상도는 15–16 ms (timeBeginPeriod(1)과 무관).

결론:
- 기본 정책은 (c): 평상시에는 받은 순간 QPC 그대로라 µs 수준, 입력 스레드가 멈춰도 오차가 틱 해상도(약 16 ms) 안에 묶인다. 멈춤 길이에 비례해 늦지 않는다.
- 폴링은 평상시에도 약 1 ms 늦고, 멈춘 동안 시작하고 끝난 탭은 아예 사라진다 (상태만 보므로).
- 한계: SendInput은 소프트웨어 주입이라 USB 키보드의 폴링 지연(1–8 ms)과 장치 내부 지연은 재지 않았다. 하드웨어 기준 입력은 CP1 범위 밖.

- **새로 생긴 질문**: 아무 고장도 넣지 않았는데 ASIO 스트림이 10분에 4번 87–113 ms 멈췄다 (장치 재생 위치 자체가 멈춤). 독 연결, 버퍼 64, 그 시간의 다른 시스템 작업 중 무엇 때문인지 아직 모른다.

## CP2 전 정리: 잠금 없는 시계 공유 (2026-10-14)

`synchronizer::shared_clock`: 오디오 스레드 → **관측 링** → 시계 스레드 → **스냅샷** → 게임 스레드.

- 관측 링 (`obs_ring`): 크기를 정한 단일 생산자-단일 소비자 링. 오디오 스레드(WASAPI 렌더, ASIO 콜백)는 잠금·할당·시스템 호출 없이 (프레임, 시각)을 넣는다. 가득 차면 버리고 센다.
- 시계 스레드 (`spawn_clock_thread`): 링에서 꺼내 `ClockModel`을 갱신한다. 다시 맞추는 계산은 여기서만 한다.
- 스냅샷 (`SharedClock`): 맞춘 직선을 seqlock으로 공개한다. 쓰는 쪽은 기다리지 않고, 읽는 쪽은 쓰는 도중이면 다시 읽는다. 게임 스레드는 `load().frame_at(t)`로 잠금 없이 계산한다.
- 이전: 공유 모드는 렌더 스레드가 패킷마다 `Mutex`를 잡고 모델을 다시 맞췄고, ASIO는 콜백이 크기 제한 없는 채널로 보냈다(할당 가능). 샘플레이트도 `Mutex<u32>`로 넘겼다.
- 단위 테스트 5개 추가: 링 순서 보존, 가득 차면 버림, 스냅샷 = 모델, 동시에 읽어도 찢어진 값 없음, 시계 스레드 종료.

검증 (클릭, 60초, 샘플 예약):

| 경로 | 이벤트 | 실제 오차 (루프백) | 비고 |
|---|---|---|---|
| WASAPI 공유 | 117/117 | 0.00 ms (최대 0.00) | |
| ASIO 버퍼 64 | 117/117 | 0.00 ms (최대 0.00) | 관측 41,387개, 버린 관측 0, 콜백 처리 p99 0.009 ms (채널 방식 0.020) |
| ASIO 버퍼 256 (15초) | 모두 | 0.00 ms | |

**ASIO 지연은 버퍼를 만든 뒤에 물어야 한다.** 만들기 전에는 드라이버 기본 버퍼(64) 기준 값을 돌려준다.

| 버퍼 | 만들기 전 | 만든 뒤 (실제) |
|---|---|---|
| 64 | 입력 130, 출력 154 | 입력 130, 출력 154 |
| 256 | 입력 130, 출력 154 | 입력 322, 출력 375 |

입력은 두 경우 모두 버퍼 + 66 샘플. `meta.json`에 `asio_latency`(만들기 전)와 `asio_latency_after_create`(만든 뒤)를 둘 다 남긴다. 이전 버퍼 256 기록의 `asio_latency`는 만들기 전 값이다.

CP1-3 상주 감시: 2026-10-13 21:24 ~ 10-14 01:58 (4시간 반, Ghidra 분석으로 CPU 고부하·온도 92°C 포함) 동안 4 ms 넘는 공백 1번, 87 ms 멈춤 0번. 다만 오디오를 재생하지 않았다. 87 ms 멈춤은 지금까지 모두 오디오 재생 중에 나왔으므로(17:44 대기 기록도 무음), 감시에 `--audio asio|wasapi|none`을 넣었다: 무음을 계속 내보내며 ASIO 콜백 간격(주기 + 4 ms 초과)이나 WASAPI 이벤트 간격(주기 × 2 + 5 ms 초과)·언더런을 `audio_gaps.csv`에 남긴다. wasapi는 공유 모드라 다른 프로그램과 장치를 같이 쓰고, asio는 장치를 잡는다. `--audio both`는 ASIO와 WASAPI를 동시에 돌려 같은 멈춤에 두 경로가 각각 끊겼는지 비교한다. 멈춤이 났던 측정과 조건을 맞추려고 ASIO 입력 4/5도 켜고, 출력 2/3(Playback 3/4, 믹스 B에서 막힘)에만 −60 dBFS 잡음을 내고(Playback 1/2는 윈도우 소리와 겹치지 않게 건드리지 않음), 144 fps로 깨는 게임 루프 흉내 스레드를 함께 돌린다. 지금까지 87 ms 멈춤은 ASIO 측정(10-13 오후)에서만 잡혔고, WASAPI 측정(10-12)에서는 없었지만 날짜가 달라 비교가 안 된다. 2026-10-14 03:19부터 `--audio both`로 상주.

## CP1-4: 기록 시계 (2026-10-15 시작)

CP2 1차 시도(브랜치 `cp2-attempt1`)에서 드러난 결함: 판정·화면의 "현재"를 **출력 위치**(지금 스피커로 나가는 샘플)로 잡아서, 미리 써 둔 음악은 제시간에 나오고 누른 뒤에 쓴 키음만 출력 지연만큼 늦었다(공유 모드 약 38~42 ms). 리듬게임의 본질은 "PERFECT로 친 키음이 반주와 같은 순간에 울린다"이다. 설계 근거: [../design/기록 시계 설계.md](../design/기록%20시계%20설계.md).

### 시간 계약

| 이름 | 정의 | 누가 쓰나 |
|---|---|---|
| 장치 시계 A(q) | QPC q ↔ 장치 샘플 위치의 직선 (기존 `SharedClock`) | Synchronizer 안 |
| **기록 시계 C(q)** | A(q) + D. **게임의 현재** = 지금 결정한 소리가 놓이는 가장 이른 샘플 | 채보·판정·화면·음악 예약·키음 예약 전부 |
| D | 그 경로에서 잰 "요청 → 쓰기 위치" 최대 지연 + 여유. 경로별 측정, 플레이 중 고정 | Synchronizer가 정해 공개 |
| 청취 시점 H(q) | A(q) − 장치 보고 출력 지연 − 교정값 (추정) | 키음 자동 연주 모드 옵션 2만 |
| 콘텐츠 커서 | C 위의 곡 위치. **오디오가 멈추면 멈춘 만큼 건너뛴다**(빠지기) — C는 끊기지 않는다 | 믹서 |

- 음악: 채보 시각 T → C = T인 샘플에 예약. 키음: 누른 시각 q → C(q)인 샘플에 예약. 둘 다 같은 시간축이라 PERFECT면 같은 샘플.
- 예약 시각이 이미 지난 요청(스레드 정지 등)은 늦음으로 기록하고 정책으로 처리한다.

### 단계

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| 4-0 | 시간 계약 (이 절) | 문서 |
| 4-1 | 경로별 D 측정: 공유, 공유 저지연(IAudioClient3), 배타, ASIO | 경로별 "요청 → 쓰기 위치" 지연 분포와 D 규칙 |
| 4-2 | Synchronizer에 기록 시계 C, "C 시각에 예약" API, 오디오 정지 때 콘텐츠 건너뛰기 | 오디오 정지 뒤에도 C가 튀지 않음 |
| 4-3 | 테스트벤치 "PERFECT 누름": SendInput을 C = T에 보내고 루프백에서 키음 시작 vs 반주 시작. 모든 경로 × 고장(화면·소비자·입력·오디오 정지) | 키음 vs 반주 = 0 샘플, D보다 늦은 요청 비율 |
| 4-4 | 누름 → 내 키음 총 지연(입력 시각 → 루프백 시작)과 흔들림, 경로별 | 경로별 표 |
| 4-5 | 청취 시점 H 추정과 교정 방법 (키음 자동 연주 모드 옵션 2) | 교정 절차와 오차 |
