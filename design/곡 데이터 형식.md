# 곡 데이터 형식 — 게임 구상용 중간 형식

> 작성일 2026-10-09. 게임 개발 구상 문서입니다. 이 저장소의 본래 목적(IIDX 곡 데이터 → BMS 변환)과는 별개입니다.
> 전제: `만약 리듬게임을 개발한다면.md`의 타이밍 설계(정규 ns 시간축, 커서 분리, 오디오 백엔드 시간 계약).
> 근거: `../cp0/IIDX_vs_BMS.md` (형식 분석), `../cp0/IIDX_timing_policy.md` (IIDX 실행 구조).
> 표기: **(확인)** 실제 파일·코드로 확인, **(추정)** 검증하지 않은 판단, **(정책)** 정해서 쓰는 규칙.

---

## 0. 원칙

1. **곡에는 곡의 진실만 담는다.** 출력 지연, 버퍼 크기, 사용자 보정 같은 장치의 진실은 넣지 않는다. 같은 곡은 어느 장치에서나 같은 정규 이벤트를 낸다.
2. **원본은 악보, 실행은 절대 시각.** 원본(작성용)은 BMS처럼 박 단위이고, 실행용은 IIDX `.1`처럼 미리 계산한 시각이다. 둘을 버전이 정해진 컴파일러가 잇는다.
3. **플레이어 구현에 기대는 암묵 규칙을 없앤다.** BMS에서 플레이어마다 다른 동작(빈 레인 소리, 롱노트 해석, 같은 소리 재발음)은 모두 명시 필드로 올린다.
4. **외부 형식은 가져오기(import)로만 받는다.** IIDX·BMS는 가져오기 도구가 중간 형식으로 바꾸고, 그 과정의 가정·손실·오차를 보고서로 남긴다.

## 1. 세 형식 비교

| 항목 | IIDX `.1` + 곡 DB | BMS | 중간 형식 |
|---|---|---|---|
| 시간 원본 | 없음 (ms 결과만) | 소절 + 분할 칸 | **악보 위치(유리수 박)** + 템포 맵 |
| 실행 시간 | ms 정수 | 플레이어가 계산 | **정규 ns 정수**. 컴파일러 버전·반올림 규칙 명시 |
| 시간 원점 | 암묵적 0 ms | 암묵적 소절 0 | **"반주 트랙 첫 샘플 = 0"으로 명시** |
| 소리 연결 | 레인 소리칸(type 2) + 무음 노트 | 노트마다 WAV ID | **곡 공통 음악 이벤트**를 노트가 1개 이상 묶음 + 빈 레인 소리 이벤트 (6-1) |
| 노트당 소리 | 1개 (레인 소리칸 하나) | 1개 (WAV ID 하나) | **1개 이상** (화음을 노트 하나로) |
| 자동재생 | 차분마다 따로 작성 (type 7) | 차분마다 따로 작성 (채널 01) | 작성하지 않음. 노트에 묶이지 않은 음악 이벤트를 컴파일러가 계산 |
| 소리 ID | u16 | 36진 2글자 (1,295) | u32 |
| 소리 형식 | `.2dx` MS-ADPCM, `.s3p` WMA 묶음 | ogg·wav 낱개 | 샘플 정확성이 보장된 코덱 + 메타데이터 |
| 반주 | 긴 트랙 1개 + 키음 | 대부분 키음 조각 | 둘 다 허용, 역할 표시 |
| 판정 | type 8 (1/60초 단위, +1 오프셋) | `#RANK` 4단계 | ns 단위 판정 창 |
| 노트 수 | 저장 (type 16) | 플레이어가 셈 | 컴파일 결과로 저장, 검증용 |
| 메타데이터 | 중앙 DB (UTF-16LE) | 차분 헤더 (인코딩 선언 없음) | 패키지 매니페스트, UTF-8 고정, 읽는 법 포함 |
| 난이도 묶음 | 파일 하나에 칸 12개 | 난이도별 파일 | 패키지 하나, 소리 뱅크 공유 |
| 분기 | 없음 | `#RANDOM` | 이름 붙은 변형(variant) |
| 화면 연출 | 템포·박자 이벤트, 영상 + 레이어 | BMP 교체, 스크롤 채널 | 타이밍과 분리된 시각 트랙 |
| 장치 정보 | 없음 | 없음 | 넣지 않음 |

## 2. 패키지 구성

```
<곡 ID>/
├── manifest.toml        곡 정보, 파일 목록·해시, 형식 버전
├── timing.toml          템포 맵, 박자, STOP, 원점
├── sounds.toml          소리 테이블
├── music.toml           음악 레이어: 곡의 모든 소리 이벤트 (난이도 공통, 6-1)
├── charts/
│   ├── SPN.toml         차분 (노트가 묶는 음악 이벤트, 빈 레인 소리, 판정, 게이지)
│   └── SPA.toml …
├── visual/              시각 트랙 (스크롤 변화, BGA 신호, 연출)
├── audio/               FLAC·Opus 파일
└── .compiled/           컴파일 캐시 (작성하지 않음, 지워도 됨)
```

원본은 텍스트(사람이 편집·비교 가능), 컴파일 캐시는 고정 레코드 바이너리입니다. 캐시는 원본 해시 + 컴파일러 버전이 같을 때만 재사용합니다.

## 4. 소리

### 4-1. 시작점 문제

"정규 시각 t에 소리 X를 시작한다"가 진실이려면 **소리 파일의 첫 샘플이 정확히 정의**돼야 합니다.

- 압축 코덱은 디코딩 결과 앞에 샘플이 붙는 경우가 많습니다. MP3는 인코더 지연·패딩 때문에 별도 메타데이터 없이는 정확한 시작을 알 수 없습니다. Opus는 헤더의 pre-skip 값만큼 건너뛰어야 합니다. FLAC·WAV는 정확합니다. Ogg Vorbis는 디코더 동작에 따라 확인이 필요합니다(추정).
- **정책**: 키음은 FLAC. 긴 반주는 FLAC 또는 Opus. 모든 소리에 **디코딩 후 총 프레임 수**를 기록하고 로드할 때 검증합니다.

### 4-2. 소리 테이블

| 필드 | 이유 |
|---|---|
| `id` (u32), 파일, 해시 | |
| 코덱, 샘플레이트, 채널, 총 프레임 수, pre-skip | 정확한 시작·길이 검증 |
| 역할: `backing` / `keysound` / `sfx` | 보이스 우선순위 (반주 > 플레이어 키음 > 자동재생 키음). 소리의 기본 성격일 뿐이고, 칠지 자동으로 울릴지는 차분의 배분이 정함 (6-1). 같은 소리가 난이도에 따라 노트도 되고 자동재생도 됨 |
| 게인 | 음량 균형. IIDX `.2dx` 항목 헤더에도 볼륨으로 보이는 값이 있음(추정) |
| choke 그룹 | 같은 그룹의 새 소리가 나면 이전 소리를 끊음 |
| 재발음 정책 | 같은 소리가 다시 울릴 때 겹칠지, 이전 것을 끊을지 |

## 5. 시간

### 5-1. 원본 (BMS 계승)

```toml
[timing]
origin = "backing:0"                    # 정규 시각 0 = 반주 트랙 첫 샘플
tempo  = [{ beat = "0", bpm = "190" }]  # 모든 수는 유리수 문자열
meter  = [{ measure = 0, sig = "6/4" }, { measure = 1, sig = "4/4" }]
stops  = []                             # { beat = "...", beats = "..." }
```

- 위치 표기: `"소절:박"`(예: `"1:2"`) 또는 전체 박 수 유리수(`"8"`, `"33/4"`). BMS의 "N칸 중 k번째"와 같은 정보이지만, 칸 수 제한과 긴 줄 문제가 없습니다.
- 반주 트랙이 없는 곡(BMS식 키음 조각 곡)은 원점을 `"beat:0"`으로 둡니다.

### 5-2. 실행 (IIDX 계승, 컴파일 결과)

- 이벤트마다 `time_ns: i64`(정규 시각)와 `scroll: 고정소수점 박`(화면 위치)을 둘 다 가집니다. IIDX가 ms와 별도로 템포 이벤트를 남겨 화면에 쓰는 구조를 명시 필드로 바꾼 것입니다.
- 반올림 규칙(정책): 유리수로 정확히 누적 → ns로 **한 번** 반올림(짝수 쪽). 컴파일러 버전과 함께 기록합니다.
- 오디오 프레임 변환은 재생할 때만 합니다(최대 반 프레임 오차).

## 6. 차분

### 6-1. 음악 레이어와 난이도 배분

**근거 (확인, 2026-10-12 조사)**: IIDX에서 같은 곡의 SP 난이도들은 "자동재생 + 노트" 소리 이벤트의 합계가 2,612곡 중 2,017곡(77%)에서 **완전히 같고**, 453곡(17%)은 2% 안에서 같습니다. 나머지 142곡은 주로 난이도마다 소리 묶음이나 편곡이 다른 옛 작품입니다.

| 28098 BEMANI PRO LEAGUE Theme | 자동재생 | 노트 | 합계 |
|---|---|---|---|
| SP NORMAL | 865 | 394 | 1,259 |
| SP HYPER | 546 | 713 | 1,259 |
| SP ANOTHER | 262 | 997 | 1,259 |

ANOTHER에서 노트로 치는 소리 중 중앙값 65%가 NORMAL에서는 자동재생입니다(2,540곡, 확인). **음악은 하나이고, 난이도는 그 음악의 소리 이벤트를 "플레이어가 칠 것"과 "자동으로 울릴 것"으로 나누는 배분**입니다. 기존 형식은 이 배분 결과만 차분마다 따로 저장해서, 배분이 어긋나도 알아챌 방법이 없습니다.

**구조 (정책)**

- `music.toml`에 곡의 모든 소리 이벤트를 둡니다: `(id, 위치, 소리, 게인)`. 긴 반주 트랙도 이벤트 하나입니다.
- 차분의 노트는 음악 이벤트를 **하나 이상** 묶습니다(`plays`). 기존 형식의 "노트 하나 = 소리 하나" 제한을 없앤 것입니다.
- 어느 노트에도 묶이지 않은 음악 이벤트는 그 차분에서 자동재생됩니다. **자동재생 목록은 작성하지 않고 컴파일러가 계산**합니다. 그래서 "어떤 난이도든 들리는 음악은 같다"가 형식 차원에서 보장됩니다.
- 검증: 한 차분 안에서 음악 이벤트는 최대 한 노트에만 묶입니다. 노트 위치와 묶인 이벤트 위치의 차이가 상한(예: 1/8박)을 넘으면 경고합니다.

**예: 피아노 화음 C+E**

```toml
# music.toml
[[event]]
id = "m120"; at = "12:0"; sound = 301   # 피아노 C
[[event]]
id = "m121"; at = "12:0"; sound = 302   # 피아노 E

# charts/SPA.toml: 두 노트 동시치기로 화음
[[notes]]
at = "12:0"; lane = "K3"; plays = ["m120"]
[[notes]]
at = "12:0"; lane = "K5"; plays = ["m121"]

# charts/SPN.toml: 노트 하나로 화음 전체
[[notes]]
at = "12:0"; lane = "K4"; plays = ["m120", "m121"]

# charts/SPB.toml: 묶지 않음 → 화음은 자동재생
```

**재생 규칙 (정책, 설정으로 바꿀 수 있게)**

| 상황 | 기본 규칙 | 다른 선택지 |
|---|---|---|
| 누름 | 묶인 이벤트를 모두 울림. 각 이벤트는 `누른 시각 + (이벤트 위치 − 노트 위치)`에 시작. 위치가 조금씩 다른 이벤트(아르페지오, 꾸밈음)도 한 노트에 묶을 수 있음 | — |
| 미스 | 묶인 소리를 모두 울리지 않음. 음악이 플레이에 반응함 | 그대로 울림 (IIDX식 보험), 작게 울림 |
| 빈 레인 치기 | 그 레인의 다음 노트 묶음을 통째로 | 첫 소리만 |
| 같은 소리 재발음 | 소리 테이블의 재발음 정책을 이벤트마다 따름 | — |

비용: 누름 한 번에 보이스가 여러 개 생기므로 보이스 예산(8장)에 반영합니다. 믹싱 연산은 무시할 수 있는 수준입니다(추정: 동시 1,000 보이스도 CPU 한 코어의 몇 %).

| 이벤트 | 내용 | 비교 |
|---|---|---|
| 노트 | 레인, 위치, 종류(단타·롱노트 시작/끝·지뢰), **묶는 음악 이벤트 (1개 이상)** | IIDX·BMS는 소리 1개 |
| 롱노트 규칙 | 차분 단위로 명시 (끝 판정 여부, 떼기 판정 등) | BMS는 `#LNTYPE`·`#LNMODE`·플레이어 해석이 섞임. IIDX는 CN·HCN·BSS가 게임 규칙 |
| 빈 레인 소리 | `(레인, 위치, 소리)`: 그 뒤 같은 레인에 노트가 오기 전까지 빈 레인을 치면 이 소리 | IIDX type 2 중 노트 없이 바뀐 것만 남김 |
| 빈 레인 기본 규칙 | 지정이 없으면 그 레인의 직전 노트 소리 (정책) | IIDX 동작을 명시 규칙으로. BMS는 플레이어마다 다름 |
| 자동재생 | 작성하지 않음. 묶이지 않은 음악 이벤트를 컴파일러가 계산 (6-1) | IIDX type 7, BMS 채널 01은 차분마다 직접 작성 |
| 판정 창 | 등급별 빠름·늦음 경계 (ns) | IIDX type 8을 단위가 명확한 값으로 |
| 게이지 | 회복·감소 규칙 | BMS `#TOTAL` 대응 |
| 모드, 레벨, 이름 | SP7, DP14, 5K 등 | |
| 변형 | 이름 붙은 대체 구간 + 선택 규칙 | BMS `#RANDOM`을 재현 가능한 형태로 (선택 결과는 리플레이에 기록) |

### 예: 33131 SP ANOTHER의 5번 건반 노트 하나

**IIDX `.1` (실제 바이트, 확인)**
```
t=2368 type 2 (교체) lane 4 value 701   ← 소리칸에 701
t=2526 type 0 (노트) lane 4 value 0     ← 소리 정보 없음
```

**BMS (같은 곡이라면)**
```
#BPM 190
#00002:1.5
#00115:0000000000000000JH00000000000000   ← 16칸 중 8번째, WAV JH
```

**중간 형식 원본**
```toml
[[notes]]
at    = "1:2"      # 소절 1의 2박째 = 전체 8박
lane  = "K5"
sound = 701
```

**컴파일 결과**
```
time_ns = 2_526_315_789   (8박 × 60/190 초, 한 번 반올림)
scroll  = 8.0 박,  lane = K5,  kind = tap,  sound = 701
```

IIDX는 반올림 결과(2526 ms)와 158 ms 앞의 교체 이벤트로, BMS는 칸 위치와 2글자 ID로, 중간 형식은 악보 위치와 소리를 한 레코드에 담고 정확한 ns를 계산합니다.

## 7. 시각 트랙

- 스크롤 속도 변화, 소절선 표시 여부, BGA 신호(영상 파일과 시작 위치, 이미지 교체), 연출 이벤트.

- 채보를 장면 속 행동으로 보여 주는 **장면 트랙**은 `세미 게임 레이어.md` 6장에 정의합니다.

## 9. 가져오기: IIDX와 BMS → 중간 형식

가져오기 도구는 중간 형식과 함께 **가져오기 보고서**(가정, 손실, 오차, 경고)를 만듭니다. 보고서 없는 가져오기는 하지 않습니다.

### 9-1. IIDX `.1` + 곡 DB + 소리 묶음

| 원본 | 중간 형식 | 판단이 필요한 점 |
|---|---|---|
| `music_data.bin` 제목·아티스트·장르 (UTF-16LE), 난이도 바이트 | manifest, 차분 레벨 | 읽는 법은 `music_title_yomi.xml` 등에서 |
| 칸 표 (slot 0~11) | 차분 파일 | 칸 ↔ 난이도 대응은 커뮤니티 기준 (추정) |
| type 4 (템포), type 5 (박자), type 12 (소절선) | 템포 맵, 박자 | 아래 "악보 위치 복원" 참고 |
| type 0/1 (노트) + 직전 type 2 (레인 소리칸) | 노트 + 소리 ID | 노트마다 그 레인의 마지막 교체 값을 붙임 (`../cp0/iidx/tools/scene_export.py`와 같은 방식) |
| 노트 없이 끝난 type 2 | 빈 레인 소리 이벤트 | 33131 첫 4소절에 1개 (확인) |
| type 0 value ≠ 0 | 롱노트 길이 | 커뮤니티 기준, 미확인 |
| type 7 + 노트의 소리 (모든 차분) | 음악 레이어 이벤트 | 차분마다 `(시각, 소리)` 다중집합을 만들어 비교. 같으면 하나의 음악 레이어로 합치고(77%가 완전히 같음, 확인), 다르면 차이를 보고서에 남기고 차분별 레이어로 둠. value 1은 반주 트랙(`backing`) 역할 (추정). 시작 시각이 0 ms가 아닌 차분이 31% (확인) |
| type 8 | 판정 창 | 값을 s8로 읽고 1을 빼서 1/60초 단위로 해석 → ns (확인: `bm2dx.dll`의 처리). 게임 내장 표(±2/±4)를 쓰는 두 번째 창은 용도 미확인 |
| type 16 | 노트 수 검증값 | 컴파일 결과와 다르면 경고 |
| `.2dx` 항목 (MS-ADPCM WAV) | FLAC으로 디코딩 | 손실 없음 (ADPCM을 디코딩한 PCM 그대로) |
| `.s3p` 항목 (WMA) | FLAC으로 디코딩 | **WMA 디코딩의 앞쪽 처리**가 게임의 발음 위치와 같은지 확인 필요. 반주 트랙으로 정렬 검증 |
| 소리 번호 (type 2·7 value) ↔ 묶음 항목 | 소리 ID | **0부터인지 1부터인지 미확인.** 렌더링해서 귀로 맞춰 보며 확정 |
| `.2dx` 항목 헤더의 볼륨으로 보이는 값 | 게인 | 의미 미확인 (추정) |
| BGA mp4, 레이어 ifs | 시각 트랙 | 영상 시작 위치 규칙 미확인 |

**악보 위치 복원**: `.1`은 ms만 있으므로, 템포·박자·소절선 이벤트로 박 위치를 다시 계산하고 가장 단순한 분수로 맞춥니다. `../cp0/iidx/tools/scene_export.py`로 33131 첫 4소절을 해 보니 3·16·16·48분할로 모두 떨어졌고, 최대 오차는 0.75 ms였습니다(확인). 맞춘 위치와 원래 ms의 차이를 보고서에 남기고, 허용 오차(정책, 예: 1 ms)를 넘으면 그 노트는 원래 ms를 그대로 쓰는 "고정 시각 노트"로 표시합니다.

### 9-2. BMS

| 원본 | 중간 형식 | 판단이 필요한 점 |
|---|---|---|
| 인코딩 (선언 없음) | UTF-8 | cp932·UTF-8·cp949를 판별하고, 판별 근거를 보고서에 기록. 이 PC 팩은 cp932 1,536개, UTF-8 1,444개 (확인) |
| `#TITLE` 등 헤더 | manifest | 차분마다 다르면 패키지 단위로 합칠 규칙 필요 |
| `#BPM`, 채널 03·08, `#STOP`·채널 09, 채널 02 | 템포 맵, STOP, 박자 | 채널 02 배율을 분수 박자로 (1.5 → 6/4) |

| 채널 11~19 / 21~29 | 노트 + 소리 ID | 키 모드 판별 (`#4K`·`#8K` 같은 비표준 힌트 포함) |
| `#LNTYPE`, 채널 51~59, `#LNOBJ`, `#LNMODE` | 롱노트 + 롱노트 규칙 | 플레이어마다 해석이 다르므로 기준 플레이어를 정해 보고서에 명시 |
| 채널 31~39 (투명 노트) | 빈 레인 소리 이벤트 | |
| 채널 01 (여러 줄) + 노트의 WAV | 음악 레이어 이벤트 | 난이도별 파일이 독립이라 IIDX처럼 비교해서 합칠 수 있을 때만 합침. 줄 겹침은 그냥 여러 이벤트 |
| `#RANK`, `#DEFEXRANK`, `#TOTAL` | 판정 창, 게이지 | **4단계를 ns로 바꾸는 대응표가 필요** (정책). 기준 플레이어의 값을 쓰고 명시 |
| `#RANDOM`·`#IF` | 변형 | 분기마다 변형으로, 선택은 리플레이에 기록 |
| `#BMPxx`, 채널 04·06·07, `#SCROLL`·채널 SC | 시각 트랙 | |
| 빈 레인 소리 (규정 없음) | 기본 규칙 적용 | 원본 동작이 플레이어 의존이었음을 보고서에 기록 |

### 9-3. 옛 형식으로 내보낼 때: 노트 하나에 소리 여러 개

BMS·IIDX는 노트 하나에 소리 하나만 붙일 수 있습니다. 여러 이벤트를 묶은 노트는 둘 중 하나로 바꾸고, 어느 쪽을 썼는지 보고서에 남깁니다.

| 방법 | 내용 | 잃는 것 |
|---|---|---|
| 대표 소리 + 자동재생 | 첫 이벤트만 노트에, 나머지는 같은 시각의 자동재생으로 | 미스해도 나머지 소리가 남음. 누른 시각이 아니라 노트 시각에 울림 |
| 미리 섞기 | 묶인 소리를 섞은 새 소리 파일을 만들어 노트에 | 파일이 늘어남. 게인 합산으로 클리핑 주의. 위치가 다른 이벤트는 오프셋까지 섞어야 함 |

### 9-4. 가져오기 보고서에 남길 것

- 원본 파일 해시, 가져오기 도구 버전
- 판별한 인코딩과 근거, 키 모드 판단
- 악보 위치 복원 오차의 분포와 고정 시각 노트 목록
- 소리 번호 대응 방식, 코덱 시작점 처리
- 판정·게이지·롱노트 해석에 쓴 기준 (기준 플레이어 또는 IIDX 규칙)
- 지원하지 않아 버린 기능

## 11. 첫 구현 순서 (제안)

1. 중간 형식의 원본 스키마와 컴파일러 (유리수 → ns, 반올림 규칙, 해시)
2. BMS 가져오기 (이 PC 팩 2,984개로 회귀 시험: 인코딩, 채널, LN, `#RANDOM` 통계와 대조)
3. IIDX `.1` 가져오기 (33131로 시작: 악보 위치 복원 오차, 노트 수 type 16 대조)
4. 소리 디코딩과 시작점 검증 (`.2dx` → FLAC, `.s3p` → FLAC은 ffmpeg 필요. 반주 트랙과 키음 합성 결과를 원곡 미리듣기와 비교)
5. 소리 번호 0/1 기준 확정 (렌더링 청취)
6. 오프라인 렌더러: 중간 형식 → 완성 곡 오디오. 형식 전체가 맞는지 귀로 확인하는 가장 빠른 방법
