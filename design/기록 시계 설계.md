# 기록 시계 설계: 렉이 와도 키음과 반주가 갈라지지 않는 엔진

> 작성 2026-10-15. CP2 1차 시도(브랜치 `cp2-attempt1`)를 되돌린 뒤 복기한 결론이다.
> 관련 문서: [만약 리듬게임을 개발한다면.md](만약%20리듬게임을%20개발한다면.md) (타이밍 설계 원안), `../cp0/` (IIDX·DJMAX·BMS 분석).

## 0. 게임의 본질

**리듬게임은 키음이 반주에 맞아야 PERFECT인 게임이다.** 플레이어는 출력 지연을 몸으로 예상해 미리 누르고, 그 결과 키음이 반주와 같은 순간에 울리게 친다.
화면은 그 타이밍을 알려 주는 안내일 뿐이다. 화면이 소리보다 상시 조금 앞서는 것은 문제가 아니다.

## 1. 기존 설계들이 놓친 것

### 1-1. 앞선 세 게임 (IIDX·DJMAX·BMS)

- 판정의 기준은 **게임 시계**다. 게임 시계는 프레임에서 나온다(IIDX 틱, DJMAX 프레임 시계, BMS 벽시계).
- 음악(자동재생 소리)과 키음을 둘 다 그 시계에서 "지금 울려"로 내보낸다. 그래서 오류가 없으면 둘이 같은 출력 지연을 거쳐 같이 나온다 → PERFECT면 키음이 음악에 맞는다.
- 하지만 이미 울리고 있는 반주는 오디오 장치가 따로 재생한다. 렉이 걸리면 **판정의 시계(프레임)와 반주의 시계(오디오)가 갈라진다.**
  - 키음을 반주에 맞춰 치면 → 틀린 판정.
  - 게임이 맞다고 하는 타이밍에 치면 → 키음이 반주와 어긋나는데도 PERFECT.
  - IIDX는 따라잡는 동안(300 ms 렉이면 약 0.6초), DJMAX·BMS는 그 긴 소리가 끝날 때까지 이 상태가 이어진다.
  - 렉 동안 프레임에서 내보내지 못한 새 소리는 렉이 끝나는 순간 몰려서 난다.
- 원인: **맞다고 생각하는 판정을 게임 시계(프레임)에 의존한다.**

### 1-2. CP2 1차 시도 ("우리 방식")

- 판정·화면의 기준을 **출력 위치**(지금 스피커로 나가는 음악의 위치)로 잡았다.
- 음악은 미리 알 수 있으니 출력 지연만큼 앞서 써 두어 기준 시각에 정확히 나온다. 키음은 누른 뒤에야 알 수 있으니 버퍼 끝(쓰기 위치)에만 놓을 수 있다.
- 그래서 **PERFECT로 친 키음이 음악보다 상시 출력 지연만큼 늦었다**(공유 모드 실측 약 38~42 ms). 음악만 지연을 피하고 키음만 지연을 치르는 비대칭 구조다.
- 설계 문서에 "PERFECT로 친 키음은 음악과 같은 순간에 나와야 한다"는 요구 조건이 없었다. 측정 봇도 "음악이 들리는 순간에 누름"이라는 같은 잘못된 기준으로 쳐서 "전부 PERFECT"가 문제를 가렸다.
- 측정도 WASAPI 공유 모드 하나에 묶여 있어서, 구조적 오류와 경로 특성(지연 크기, 언더런 때 스트림이 밀리는 동작)을 구분하지 못했다.

## 2. 설계: 기록 시계 C

게임의 "현재"를 **지금 결정한 소리가 놓이는 가장 이른 샘플**(기록 시점)로 정의한다.

```
C(q) = 오디오 장치 시계(q) + D
```

- 오디오 장치 시계: QPC ↔ 장치 샘플 위치를 잇는 직선 (CP1 `SharedClock`). 오디오 발진기를 따라간다.
- D: 그 장치·경로에서 잰 "요청이 쓰기 위치에 닿기까지의 최대 지연" + 여유. 경로마다 측정하고 플레이 중에는 바꾸지 않는다. 고정 상수가 아니다(필요 이상으로 크면 누름 → 소리 간격이 쓸데없이 벌어진다).

모든 것이 이 하나의 시간축 위에 있다.

| 대상 | C 위에서의 위치 |
|---|---|
| 반주 (긴 소리) | 채보 시각 T → C = T인 샘플에 예약 |
| 짧은 자동재생 소리 | 같음. 오디오 스레드의 믹서가 채보를 직접 훑는다 (프레임이 내보내지 않음) |
| 키음 | 누른 순간의 C 값인 샘플에 예약 |
| 판정 | 누른 시각(OS 입력 시각, QPC)을 C로 바꿔서 매긴다 |
| 화면 | C를 그린다 (디스플레이 지연 보정) |

**"게임이 PERFECT라고 하는 것"과 "키음이 반주와 같은 샘플에 놓이는 것"이 정의상 같은 일이 된다.** 갈라질 두 번째 시계가 없다.
음악은 화면보다 상시 D + 출력 지연만큼 늦게 들린다. 플레이어는 키음을 음악에 맞추는 감각으로 친다.

## 3. 렉별 동작

| 렉 | 세 게임 | 기록 시계 설계 |
|---|---|---|
| **화면이 멈춤** | 게임 시계가 멈춰서 반주와 갈라짐. 따라잡기(IIDX)나 시간 손실(DJMAX) | C는 오디오 시계라 화면과 무관하게 흐른다. 소리도 오디오 스레드가 내므로 몰리지 않는다. 화면은 재개하면 맞는 위치를 그릴 뿐 — **복원할 것이 없다** |
| **판정·입력 스레드가 멈춤** | 입력이 프레임에 묶여 판정이 늦게·틀리게 남 | 누른 시각이 보존되므로 **판정은 정확**. 키음 요청이 예약 샘플 전에 도착하면 정확히, 이미 지난 뒤면 인과적으로 불가능 → 정책(늦으면 버림)으로 처리 |
| **오디오가 멈춤** | 이미 울리던 반주와 새 소리가 갈라짐 | 시간축 C를 끊지 않고 멈춘 만큼 콘텐츠를 **건너뛴다**(빠지기, CP1-2 ASIO "장치 고정"과 같은 선택). 그 구간 음악은 무음으로 빠지지만 재개 후 반주·키음·판정이 정확히 같은 위치에서 이어진다 — **싱크가 깨지지 않으니 복원이 필요 없다** |
| **화면·오디오 클럭 드리프트** | 쌓임 (IIDX는 곡 끝에 Hz 재측정) | C가 오디오 발진기 자체라 생기지 않는다 |

## 4. 남는 한계

물리적으로 피할 수 없는 손실:

1. **누름 → 소리 = D + 출력 지연.** 오디오 경로로만 줄어든다(공유 모드 약 45 ms, ASIO 약 10 ms). 음악과 키음이 똑같이 치르므로 싱크에는 영향이 없다.
2. **오디오가 멈춘 동안의 음악**은 들리지 않는다. 시간은 어긋나지 않는다.
3. **스레드가 멈춰 예약 시각을 지나 도착한 키음**은 제자리에 낼 수 없다. 판정은 정확하다.

설계가 보장하지 못하는 오차 원천 (측정·보정 대상):

4. **접점 → OS 수신 지터**(USB 폴링, 키보드 스캔). 엔진이 보는 입력 시각 자체의 오차다.
5. **D를 넘는 순간 지연.** 경로 지연이 측정한 최대치를 넘으면 그 키음은 늦는다. 믹서가 "늦음"으로 기록하므로 감지할 수 있다.
6. **장치 시계 모델의 오차**(위치 보고의 편향·잡음). 키음과 반주가 같은 C를 쓰므로 둘 사이 싱크에는 영향이 없고, 판정의 절대 시각에만 영향을 준다.
7. **화면 시각**은 디스플레이 지연 보정에 달려 있다. 본질(키음 = 반주)과는 무관하지만 플레이 감각에는 영향을 준다.

## 5. 범위와 검증

- **범위: CP1(Synchronizer).** "게임의 현재 = C"라는 정의, 경로별 D 측정, 오디오가 멈췄을 때 콘텐츠를 건너뛰는 처리는 시계를 읽는 유일한 층의 계약이다. CP1에서 만든 장치 시계·샘플 예약·입력 도장은 그대로 쓰고, 바뀌는 것은 "현재"의 정의와 오디오 정지 정책이다.
- **검증 지표 (모든 오디오 경로: 공유, 공유 저지연, 배타, ASIO):**
  - PERFECT로 친 키음 vs 반주 = **0 샘플**.
  - 어떤 렉(화면·판정·입력·오디오 정지)에서도 **C가 튀지 않음**.
  - D보다 늦게 도착한 키음 요청 비율 (D가 충분한지).
  - 누름 → 소리 = D + 출력 지연이 그 경로의 물리적 최소에 가까운지.
