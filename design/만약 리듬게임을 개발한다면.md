# 만약 리듬게임을 개발한다면 — 하드웨어가 제각각인 PC용 타이밍 설계

> 작성 2026-10-09. Claude 초안을 OpenAI Codex(gpt-6-astra)가 비판 검토했고, Codex가 직접 쓴 설계(`Codex가 쓴 리듬게임 설계.md`, 원문 보존)를 뼈대로 두 문서를 합쳤습니다.
> 근거 문서: `../cp0/IIDX_timing_policy.md` (IIDX `bm2dx.dll` 정적 분석), `../cp0/IIDX_vs_BMS.md` (채보 형식).
> 표기: **(실측)** 이 PC에서 관측한 값, **(보고값)** 드라이버나 OS가 알려 준 값(물리 측정 아님), **(추정)** 검증하지 않은 판단, **(정책)** 검증 후 조정할 초기값.

## 0. 요약

- 오디오 장치를 기준으로 삼는 이유는, 음악과 게임 사이의 어긋남을 줄이는 데 가장 유리하기 때문입니다. 그렇다고 **귀에 도달한 시각이 자동으로 알려지지는 않습니다.** 소프트웨어가 아는 것은 장치와 OS의 보고값이고, 귀 도달 시각은 외부 교정값을 더한 **추정**입니다.
- 그래서 **정확한 예약**(소리를 어느 프레임에 넣었나)과 **정확한 관측**(그 프레임이 언제 나갔나)을 분리합니다. 제출·재생·콘텐츠·청취 위치를 서로 다른 커서로 다루고(3장), 백엔드는 epoch·유효기간·불확실성을 붙인 시간 모델을 내놓습니다(4장).
- "언제나 진실로 돌아온다"고 주장하지 않습니다. 대응이 깨지면 **감지하고, 그 구간을 정상으로 취급하지 않으며, 새 대응을 검증한 뒤 재개**합니다(9장, 11장). 이미 들리지 않은 소리와 놓친 입력은 복구됐다고 기록하지 않습니다.
- 판정·리플레이는 장치와 무관한 정규 시간(ns)으로 하고, 오디오 프레임 변환은 예약할 때만 합니다. 판정 확정에는 입력 watermark를 씁니다(7장).
- 노트와 판정선은 항상 최선 추정을 즉시 반영합니다. 부드러운 보정은 장식에만 씁니다(10장). IIDX식 "따라잡기"를 판정 화면에 쓰지 않습니다.
- 완료 기준은 "시계가 계속 증가한다"가 아닙니다. **정상 구간의 물리 오차를 측정했고, 불확실 구간을 정상으로 처리하지 않으며, 실패 뒤 새 대응을 검증하고 재개하는 것**입니다.

## 1. 목표, 보장 범위, 비목표

**우선순위**
1. 실제 청취 위치와 다른 시각을 정상으로 취급할 가능성을 낮춘다.
2. 대응 관계가 깨지면 감지하고, 검증 가능한 상태로 재동기화한다.
3. 입력→발음 지연과 지터를 줄인다.
4. 구현·CPU·유지보수 비용을 제한한다.

**비목표**
- 임의의 Windows PC에서 100 µs 종단 정확도를 보장하기. (100 µs는 별도 실험 등급, 12장)
- 유한한 최악 스케줄링 지연 보장. Windows는 하드 실시간 OS가 아닙니다.
- 이미 누락된 음이나 접점 이벤트를 사후에 복원하기.
- Bluetooth를 유선 저지연 장치와 같은 등급으로 취급하기.
- 프레임 정지를 부드러운 노트 추격으로 감추기.

**PC에서 보장되지 않는 것**

| 변수 | 범위 | 설계가 감당할 것 |
|---|---|---|
| 화면 | 60~360 Hz, VRR, 창 모드, 멀티 모니터 | 주사율을 시간 계산에 쓰지 않음. 표시 모델은 바뀔 때마다 재검증 |
| 오디오 | WASAPI 공유·배타, ASIO, USB 오인페, Bluetooth | 백엔드별 시간 계약(4장). 경로·설정별 교정 |
| 입력 | 키보드(폴링 주기 제각각), HID 컨트롤러, 게임패드 | 수신 시각의 한계를 명시(7장) |
| CPU/GPU, OS | 사양 차이, 백그라운드 부하, 전원 관리, DPC 지연 | 렌더가 늦어도 판정과 자동재생은 영향 없음. 마감 실패는 감지 |

## 2. 진실과 지연

### 2-1. 진실의 순간

| 감각 | 진실 | 컴퓨터가 아는 것 |
|---|---|---|
| 소리 | 고막에 음압이 닿는 순간 | 백엔드 기준점을 프레임이 통과하는 시각의 추정 |
| 화면 | 판정선 위치의 픽셀이 빛나는 순간 | present 통계, 표시 예측 |
| 입력 | 스위치 접점이 닫히는 순간 | 입력 이벤트를 받은 순간의 QPC |

### 2-2. 지연의 네 종류 (섞어서 비교하지 않음)

| 종류 | 예 | 다루는 법 |
|---|---|---|
| 발진기 잡음 | 오디오 수정 발진기의 위상 잡음 (ns 이하) | 무시 가능 |
| 타임스탬프 오차 | 관측 시각과 실제 사건의 차이, 콜백 깨움 지연에 묶인 시각 | 상관된 위치·시각 관측을 우선, 편향은 물리 측정으로 확인 |
| 큐 지연 변화 | 콜백 주기, 입력 폴링, 스레드 깨움, present 대기열 | 측정하고, 필요하면 예약으로 일부 고정 |
| 신호 처리 지연 | DAC 필터, 장치 DSP, 패널 처리, Bluetooth 코덱, 공기(1 m당 2.9 ms) | 경로·설정별로 측정. **고정이라는 가정은 검증된 경로에만** 적용 (Bluetooth·DSP·패널은 바뀔 수 있음) |

### 2-3. 반응 지연과 정렬 오차는 다른 지표

- **반응 지연**: 누른 뒤 소리가 날 때까지. 보정으로 줄일 수 없습니다(물리적으로 존재).
- **정렬 오차**: 감각들이 서로, 그리고 채보와 얼마나 어긋나는가. 보정으로 줄일 수 있습니다.
- 감각들을 정렬하려면 공통 목표 도착 시각 `T`를 정하고, 각 경로 지연만큼 **앞서 제출**합니다. 각자 최대 지연을 더하는 방식은 서로 다른 시각에 도착하게 만들 수 있습니다. 예측 불가능한 입력(플레이어 키음)에는 인과적 하한이 있습니다.

## 3. 시간축과 커서

| 이름 | 정의 | 용도 |
|---|---|---|
| QPC 시간 `q` | `QueryPerformanceCounter`를 `QueryPerformanceFrequency`로 해석한 호스트 시간 | 입력 수신·장치 관측·진단의 공통 시간축 |
| 정규 곡 시간 `c` | 장치와 독립적인 정수 시간, i64 ns | 채보·판정·리플레이 |
| 스트림 프레임 `f` | 한 오디오 epoch 안의 출력 프레임 좌표 | 버퍼 배치, 장치 위치 대응 |
| 제출 커서 `W` | 백엔드에 넘긴 구간의 다음 프레임 | **제출 이력.** 재생 완료를 뜻하지 않음 |
| 재생 커서 `R(q)` | 시각 `q`에 백엔드 기준점을 통과하는 프레임의 추정 | 현재 출력 위치 |
| 콘텐츠 대응 `C(f)` | 출력 프레임에 배치한 곡 위치. 무음·불명 구간도 표현 | 재생 위치를 곡 시간으로 변환 |
| 청취 곡 시간 `H(q)` | 시각 `q`에 귀에 도달한다고 추정되는 프레임의 `C(f)` | 판정, 화면 예측 |
| 쓰기 가능 구간 | 지금 안전하게 채울 수 있는 프레임 범위 | 자동재생 믹싱, 키음 예약 |

- `W`, `R`, `C`는 합치지 않습니다. 정상 연속 재생에서만 단순한 관계이고, 선행 버퍼링·무음 삽입·재시작 뒤에는 달라집니다.
- **직접 센 제출 프레임 수는 콘텐츠 배치의 기준이지 물리 출력의 증거가 아닙니다.** (초안의 "내가 센 샘플 수 = 진실"은 틀린 주장이라 삭제)
- 장치의 명목 샘플레이트(예: 48 kHz)와 QPC 기준 실제 진행률은 구분합니다. 진행률 추정으로 채보를 다시 컴파일하지 않습니다.
- 채보 시각은 BPM·STOP·소절 길이를 유리수로 누적한 뒤 정규 시간으로 **한 번** 반올림합니다. 오디오 프레임으로 바꿀 때 또 한 번 반올림이 생깁니다(최대 반 프레임). 두 오차를 "0"이라고 부르지 않습니다.

## 4. 오디오 백엔드 시간 계약

```rust
struct Epoch(u64);
struct QpcTicks(i64);
struct StreamFrame(i64);
struct SongNs(i64);

enum ClockState { Acquiring, Tracking, Stale, Discontinuous }

enum Uncertainty {
    Unknown,
    // 명시한 운용 조건에서 검증한 경험적 오차 범위. 하드 실시간 상한이 아님.
    Empirical { ns: u64, profile_id: u64 },
}

struct PresentationModel {
    epoch: Epoch,
    frame0: StreamFrame,
    qpc0: QpcTicks,
    qpc_ticks_per_frame: f64,
    observed_at: QpcTicks,
    valid_until: QpcTicks,
    state: ClockState,
    uncertainty: Uncertainty,
}

struct RenderBlock {
    epoch: Epoch,
    frames: Range<StreamFrame>,
    deadline_estimate: Option<QpcTicks>,
    // PCM 버퍼는 콜백 수명에 한정된 별도 참조
}

struct ContentSegment {
    epoch: Epoch,
    frames: Range<StreamFrame>,
    content: ContentMapping, // Song / Silence / Unknown
}
```

- `PresentationModel`은 **프레임이 백엔드가 정의한 출력 기준점을 통과할 QPC**를 돌려줍니다. 기준점의 의미는 백엔드마다 문서로 고정합니다.
- 귀 도달 모델: `ear_qpc(frame) = presentation_qpc(frame) + residual_path_delay`
  `residual_path_delay`는 API 기준점에 **이미 포함되지 않은 경로만** 보정합니다. 보고된 전체 지연을 무조건 다시 빼면 이중 보정이 됩니다.

### 4-1. 백엔드별 기준점과 함정

| 백엔드 | 위치 관측 | 주의 |
|---|---|---|
| WASAPI | `IAudioClock::GetPosition(&pos, &qpcPos)` | `pos`는 프레임이 아니라 `GetFrequency` 단위. `qpcPos`는 원시 QPC tick이 아니라 **100 ns 단위**. `S_FALSE`는 품질 낮은 관측으로 처리. `GetStreamLatency`는 순간 지연이 아니라 스트림의 **최대** 지연 보고값 |
| WASAPI 배타 | 위와 같음 | 항상 가장 짧은 경로라는 보장 없음. 지원 포맷·주기·버퍼 정렬 제약이 있고 정렬 실패 시 클라이언트 재생성이 필요할 수 있음. 실제 초기화 결과를 기록하고 실측으로 경로 선택 |
| WASAPI 공유 저지연 | `IAudioClient3::InitializeSharedAudioStream` | 저지연 주기는 드라이버 지원에 달림. 지원 주기를 질의 |
| ASIO | `bufferSwitchTimeInfo` 우선, `ASIOGetSamplePosition` | 버퍼 인덱스는 **호스트가 채울 버퍼**를 가리킬 뿐, "방금 들렸다"는 통지가 아님. 위치·시각은 현재 블록 시작에 대응. `outputLatency`는 버퍼 스위치부터 그 출력 버퍼 발음 시작까지. 시스템 시각(ns)의 단위와 QPC 대응을 검증. 위치는 `ASIOStart`에서 재설정 |

- 백엔드가 위치 품질을 제공하지 못하면 `Uncertainty::Unknown`으로 공개합니다.
- 공유·배타 모드의 버퍼 계약이 같다고 가정하지 않습니다. 명목 샘플레이트가 같다고 해서 장치 안에서 샘플레이트 변환이 없다고 보장하지도 않습니다.
- 근거: [GetPosition](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclock-getposition), [GetStreamLatency](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclient-getstreamlatency), [IAudioClient::Initialize](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclient-initialize), [저지연 오디오](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/low-latency-audio), [ASIO SDK `asio.h`](https://raw.githubusercontent.com/audiosdk/asio/master/common/asio.h)

### 4-2. ASIO는 무엇이고, 드라이버를 직접 만들 필요가 있나

이 PC의 실제 경로 (부록 A):
```
게임 프로세스 (믹서)
  │ COM으로 ASIO DLL을 게임 프로세스 안에 로드 (HKLM\SOFTWARE\ASIO → CLSID → DLL)
  ▼
toppingprousbaudioasio_x64.dll  (원래 이름 tusbaudioasio.dll = Thesycon USB 오디오 드라이버 기반)
  │ 커널 드라이버와 버퍼 교환 (DeviceIoControl로 추정)
  ▼
ToppingProUsbAudio.sys → USB 호스트 드라이버 → USB → 장치 → DAC (장치 발진기가 샘플 클럭)
```

- 드라이버는 게임 연산에 영향을 줍니다. **게임 프로세스 안에서 돌고, 게임의 믹싱이 드라이버 스레드에서 실행되며, 마감 주기·출력 지연·클럭 속도를 정합니다.**
- 그래도 **드라이버를 직접 만들지 않습니다.** 실용적인 최적화 범위는 드라이버 내부가 아니라 경계 계약(4장 계약, 5장 추정, 9장 재동기화)과 물리 측정(12장)입니다.
- 드라이버 수준이 문제가 되는 유일한 신호: 물리 측정에서 같은 설정인데 경로 지연이 실행 중에 바뀌는 경우(적응형 버퍼 등). 그때도 설정 고정이나 장치 교체가 먼저입니다.

## 5. 시계 추정과 유효성

상관된 장치 위치·시각 관측으로 프레임→QPC 직선을 추정합니다.

- 위상과 진행률을 따로 추적합니다. 진행률은 느리게 갱신하고 이상치는 분리합니다.
- 큰 절대 카운터 대신 기준점과의 차이로 계산합니다.
- **콜백 진입 QPC는 주로 깨움 지연 진단에 씁니다.** 콜백 지연은 평균 0인 독립 잡음이 아니라 양의 편향, 장기 상관, 부하 의존성이 있습니다. 관측을 늘려도 평균 편향(예: 300 µs)은 남습니다. 작은 회귀 잔차는 작은 물리 오차의 증거가 아닙니다.
- 콜백 시각만 쓸 수 있는 장치는 낮은 신뢰 등급으로 분류합니다.
- QPC: Windows가 시간원을 고르며, 해상도·호출 비용은 시스템마다 다릅니다. 지원되는 시스템에서는 CPU 주파수 변화 보정이나 코어 고정이 필요 없습니다. **절전 중에도 QPC는 진행하므로**, 멈춘 오디오에 그대로 외삽하면 안 됩니다. ([QPC 설명](https://learn.microsoft.com/en-us/windows/win32/sysinfo/acquiring-high-resolution-time-stamps))

**초기 정책** (정책)
- 새 epoch에서 최소 100 ms, 8개 이상의 일관된 관측을 확보한 뒤 시작을 허용.
- 명목 진행률로 시작하고, 진행률 적응은 2초 이상의 유효 관측 후 활성화.
- 관측이 `max(3 × 서비스 주기, 10 ms)`보다 오래되면 `Stale` → 외삽 중단, 새 판정 확정 금지.
- 정상 재생 중 설명되지 않는 2 ms 이상의 모델 점프는 재검증.

**프레임 정지를 진행률 오차로 학습하지 않기.** IIDX는 곡 끝에 누적 보정량으로 주사율을 다시 추정하는데, 일시적 렉이 섞이면 다음 곡의 틱 길이를 오염시킬 수 있습니다(13장 계산). 진행률은 정지·누락 구간을 제외한 상관 관측으로만 추정합니다.

과거 입력을 최신 직선으로 계속 재해석하지 않습니다. 입력을 처리할 때 쓴 epoch·모델 버전·정규 곡 시각을 기록하고, 나중에 모델 오류가 드러나면 그 구간을 무효로 표시합니다.

## 6. 스레드, 소유권, 경계

| 실행 경로 | 소유 상태 | 제한 |
|---|---|---|
| 오디오 콜백 | 보이스, 믹서, 자동재생 커서, 예약 키음 | 할당·해제·블로킹·파일 작업 금지 |
| 입력/판정 스레드 | 입력 순서, 레인 상태, 판정, watermark | 렌더·오디오 완료를 기다리지 않음 |
| 렌더 스레드 | GPU 자원, 표시 예측 | 최신 스냅샷만 소비 |
| 제어/로딩 경로 | 디코딩, 장치 재구성, 로그 저장 | 실시간 경로가 기다리지 않게 함 |

- 판정은 작으므로 **입력과 같은 스레드**에 둡니다. 입력/판정 스레드가 레인 규칙에 따라 키음을 고르고 즉시 오디오 SPSC로 요청합니다. MISS 확정처럼 유예가 필요한 처리는 뒤에서 합니다. (초안의 "입력·로직 스레드 분리"를 단순화)
- 입력 스레드는 이벤트 기반으로 대기합니다. 무조건 최고 우선순위나 busy loop는 쓰지 않습니다.

### 6-1. 실시간 경로의 안전 조건

- **실행 시간이 짧다고 마감을 지킨 것이 아닙니다.** 50 µs 만에 끝난 콜백도 3 ms 늦게 시작했으면 실패입니다. 예정 서비스 시각 대비 **진입 지연**, 남은 버퍼 여유, 마감 초과를 잽니다. MMCSS나 높은 우선순위는 ISR/DPC 지연을 없애지 못하며 하드 실시간 계약도 아닙니다. ([MMCSS](https://learn.microsoft.com/en-us/windows/win32/procthread/multimedia-class-scheduler-service))
- 할당이 없다고 안전한 것도 아닙니다. 남는 위험: PCM 최초 접근·페이지 아웃, 스택 확장, 마지막 `Arc` 해제, 라이브러리의 숨은 잠금, lazy 초기화, 스트리밍 고갈, denormal 연산.
  - 대책: 재생 전에 코드·스택·PCM을 워밍업하고 필요한 페이지를 미리 접근합니다. 큰 객체 해제는 제어 경로로 넘깁니다. DSP의 FTZ/DAZ 정책을 고정합니다.
  - "시스템 호출 전면 금지"보다 "블로킹·무제한 작업 금지, 필수 API는 비용 검증"이 정확한 규칙입니다.

### 6-2. 경계 전달 규칙 (CDC는 비유로만)

반도체의 클럭 도메인 교차(CDC)는 "비동기 경계에서 일관된 전달이 필요하다"는 직관을 주는 비유입니다. 그 이상으로 대응시키지 않습니다. 스레드마다 독립 발진기가 있는 것도 아니고, 데이터 경쟁은 메타스테이빌리티가 아니며, 원자 플래그는 2-FF 동기화기가 아닙니다. **실제 클럭 대응이 필요한 곳은 오디오 장치, QPC, 타임스탬프를 가진 입력 장치, 디스플레이뿐입니다.**

- 이벤트 큐와 최신 상태 스냅샷을 구분합니다.
- 큐는 고정 용량이고, 생산자는 소비자 인덱스를 임의로 바꾸지 않습니다. (SPSC에서 생산자가 "오래된 항목을 버리는" 것은 구조상 불가능)
- **입력 overflow는 이벤트 손실로 기록하고 버튼 상태를 재동기화합니다.** 오래된 입력을 버리면 release 유실(눌림 고착)이나 press 유실(판정 손실)이 생깁니다. 로그·렌더 스냅샷·입력 이벤트에 같은 폐기 정책을 쓰지 않습니다.
- 다중 필드 스냅샷(시계 모델 등)은 Rust 메모리 모델을 만족하는 검증된 수단으로 넘깁니다. 일반 필드를 경쟁 상태로 읽고 sequence만 재검사하는 자작 seqlock은 데이터 경쟁입니다. 재시도 횟수를 제한하고, 실패하면 이전 유효 스냅샷을 씁니다. 128비트 원자 연산이 lock-free라고 가정하지 않습니다. ([Rust 데이터 경쟁](https://doc.rust-lang.org/nomicon/races.html))
- lock-free를 "무제한 대기 없음"과 같은 뜻으로 쓰지 않습니다.

## 7. 입력 시각과 판정 watermark

```rust
enum InputTimeSource { HostReceipt, DeviceMapped { clock_epoch: u64 } }

struct InputEvent {
    sequence: u64,
    device: DeviceId,
    control: ControlId,
    edge: Edge,
    qpc: QpcTicks,
    source: InputTimeSource,
    uncertainty: Uncertainty,
}

struct InputWatermark {
    // 이 시각 이전으로 배치할 수 있는 이벤트를 모두 게시했다는 생산자 계약.
    // 물리 접점 전체를 관측했다는 뜻은 아님.
    qpc: QpcTicks,
    sequence: u64,
}
```

**일반 Raw Input**
- 가능한 이른 수신 지점에서 QPC를 기록하고, 배치 안의 이벤트 순서를 보존합니다.
- `RAWINPUT`에는 접점 발생 시각이나 이벤트별 QPC 필드가 없습니다. **OS가 주지 않은 과거 시각을 만들어내지 않습니다.** 수신 지연에는 스캔·디바운스·USB·OS 지연이 남습니다. ([RAWINPUT](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-rawinput))
- 입력 간격 히스토그램은 "관측된 이벤트 전달 간격"으로 표시합니다. USB 폴링 주기나 접점 정확도라고 부르지 않습니다.

**장치 타임스탬프가 있는 입력** (전용 컨트롤러)
- 장치 클럭→QPC 대응을 따로 추정하고, wrap·reset·역순·누락을 검사합니다. watermark는 장치 시간과 전송 계약까지 반영합니다.

**판정**
```text
input_song_time = H(input_qpc)
MISS 확정 조건: input watermark > 그 노트의 늦은 판정 창 끝
```
- 여러 입력원이 있으면 유효한 watermark의 최솟값을 씁니다. 멈춘 입력원이 판정을 무한히 막지 않도록 연결 상실 또는 입력 불확실 상태로 전환합니다.
- watermark 이전 시각의 이벤트가 뒤늦게 오면 계약 위반입니다. 조용히 점수를 바꾸지 않고 그 구간을 무효 처리합니다.
- 판정은 순수 함수이고 판정 창은 정수 ns입니다.
- 리플레이에는 판정 창, 동시각 이벤트 순서, 레인 배치, 난수 시드, 엔진 버전, 채보 해시를 넣습니다. **리플레이 재현 가능성과 입력의 물리 정확성은 별개입니다.**

## 8. 자동재생, 키음, 보이스 예산

### 8-1. 콘텐츠 준비
- 곡 시작 전에 키음 전부를 장치 샘플레이트 PCM으로 디코딩·리샘플링해 둡니다. 긴 반주만 스트리밍하고, 스트리밍 고갈은 명시적 실패로 기록합니다.
- **보이스 예산은 콘텐츠에서 계산합니다.** IIDX식 키음 곡은 소리가 많습니다. 33131 SP ANOTHER는 노트 790개에 자동재생 1,365개, 키음 파일 1,677개였고, BMS 팩은 한 소절의 BGM 줄이 최대 100개였습니다 (`IIDX_vs_BMS.md`). 채보 컴파일러가 최대 동시 발음 수를 계산해 보이스 풀을 고정 크기로 잡습니다.
- 보이스 초과 정책: 반주를 무조건 "가장 오래된 보이스"로 취급해 끄지 않습니다. 우선순위(반주 > 플레이어 키음 > 자동재생 키음)와 짧은 감쇠를 적용하고 초과를 기록합니다.

### 8-2. 자동재생
오디오 콜백이 출력 프레임 구간에 해당하는 콘텐츠를 **직접 믹싱**합니다. 렌더·로직 진행을 기다리지 않습니다. IIDX에서 렉 때 자동재생이 늦는 원인(틱에서 발음, 추정)을 구조적으로 없앱니다.

### 8-3. 플레이어 키음
- **기본: 최소 지연 모드.** 요청을 받은 뒤 가장 이른 안전한 출력 프레임에 배치합니다. 서비스 주기와 전달 지연에 따른 지터가 남습니다.
- **선택: 일정 지연 모드.**
  ```text
  target_ear_qpc = input_qpc + chosen_delay
  target_frame  = inverse_ear_model(target_ear_qpc)
  ```
  `chosen_delay`는 실제 요청 경로의 높은 분위수와 출력 선행량으로 정합니다. 플레이 도중 조용히 바꾸지 않습니다.
  - 이 모드가 없애는 것은 **관측된 입력 시각 이후**의 예약 지터뿐입니다. 접점→수신 지터는 그대로 남습니다. (초안의 "지터를 고정 지연으로 바꾼다"는 과장이라 정정)

| 요청 상태 | 오디오 콜백의 처리 |
|---|---|
| 목표가 현재 쓰기 가능 구간 안 | 해당 프레임 오프셋에 믹싱 |
| 목표가 미래 | 고정 용량 예약 큐에 보관 |
| 목표가 이미 지남 | 가장 이른 안전한 프레임에 발음하고 지각량 기록 |
| 목표보다 20 ms 이상 늦음 (정책) | 폐기하고 실패 기록 |
| 다른 epoch의 요청 | 폐기 |

늦은 요청 때문에 과거 판정 시각을 옮기지 않습니다.

## 9. 상태 머신과 콘텐츠 재동기화

```text
Stopped → Priming → Acquiring → Running → Suspect → Resyncing → Priming
Running → Paused → Priming
어느 상태든 장치 오류 → Unavailable → Priming
```

| 상태 | 의미 |
|---|---|
| Priming | 버퍼·보이스·콘텐츠 대응 준비 |
| Acquiring | 장치 위치·시각·버퍼 관계 확인 (5장 초기 정책) |
| Running | 유효한 시간 계약으로 판정·발음 |
| Suspect | 새 판정 확정을 보류하고 불확실 구간 기록 |
| Resyncing | 정지·플러시·새 epoch·콘텐츠 재배치 |
| Paused | 곡 시간 정지. QPC 외삽도 정지 |
| Unavailable | 장치가 준비될 때까지 대기 |

**시계 복구와 콘텐츠 복구는 다릅니다.** 언더런 때 장치 카운터는 정상 진행하면서 무음이나 이전 버퍼를 낼 수 있고, 위치 점프 없이 언더런이 날 수도 있습니다. 언더런 검출이 완전하다고 가정하지 않습니다.

- **대응이 확실할 때**: 현재 위치로 전진합니다. 지나간 자동재생 이벤트를 몰아서 발음하지 않습니다. 그 시각에 살아 있어야 할 긴 음은 PCM 오프셋에서 복원하고 짧게 페이드인합니다.
- **대응이 불확실할 때**: 정지·플러시 후 새 epoch를 만듭니다. 연습 모드는 체크포인트에서 판정·보이스 상태를 함께 복원합니다. 연속 정확성이 필요한 기록은 중단하거나 무효 처리합니다.
- ASIO 메시지(리셋 요청, 재동기화 요청 `kAsioResyncRequest`, 샘플레이트·지연 변경, 외부 클럭 상실, 유효하지 않은 time info)는 콜백에서 **요청만 전달**하고, 제어 스레드가 정지·재구성합니다. 초기 버퍼와 첫 위치 관측을 맞춘 뒤 게임 시간을 시작합니다.
- 점수 상태는 유지한 채 음악만 과거로 돌리지 않습니다. 이미 들리지 않은 소리는 복구됐다고 기록하지 않습니다.

## 10. 화면 정책

노트와 판정선은 **예상 광학 표시 시각의 최선 청취 곡 시간**을 씁니다.
```text
estimated_photon_qpc = predicted_display_time + calibrated_line_offset
note_position        = chart_position(H(estimated_photon_qpc))
```

- 프레임 대기가 풀린 뒤 가능한 늦게 시계를 읽습니다 (대기 가능한 스왑체인, `SetMaximumFrameLatency(1)`; 이것이 전체 광학 경로를 한 프레임으로 제한하는 보장은 아님).
- **노트 진행 속도를 0.5~1.5배로 바꿔 가며 오차를 천천히 따라잡지 않습니다.** 큰 오차나 프레임 누락 뒤에는 현재 추정 위치로 즉시 복귀합니다. 부드러운 보정(smoothing)은 배경·장식에만 씁니다. (초안의 표시 보정 의사코드는 정상 진행 항이 빠져 최대 0.5배로만 움직이는 버그가 있었고, 방향 자체가 판정선과 어긋나게 만들어 폐기)
- `calibrated_line_offset`에는 판정선 높이에 따른 주사(scanout) 오프셋이 들어갑니다. 실제 모드 기준으로 계산합니다.
- DXGI 프레임 통계(`SyncQPCTime` 등)는 refresh에 연결된 QPC이지 **픽셀이 빛난 시각이 아닙니다.** present ID별로 연결하고, 모드 변경·통계 불연속 때 추정기를 초기화합니다. 통계 기반 추정과 광센서 측정값을 구분합니다. ([DXGI 통계](https://learn.microsoft.com/en-us/windows/win32/api/dxgi/ns-dxgi-dxgi_frame_statistics), [flip 모델](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/dxgi-flip-model))
- VRR 범위 이탈, 반복 표시, 컴포지터 경로 변경, 출력 모니터 변경 시 표시 모델을 재검증합니다.
- 화면 보정은 오디오·입력 보정과 분리합니다.

## 11. 실패 처리

| 실패 | 감지 | 행동 | 복구 가능 / 불가능 |
|---|---|---|---|
| 렌더 정지 | 프레임·present 간격 | 다음 프레임에 현재 상태 표시 | 현재 표시 / 놓친 화면 |
| 입력/판정 지연 | 수신·처리 시각, watermark 지연 | 보존된 이벤트 순서대로 처리 | 보존된 타임스탬프 판정 / 관측 못한 접점 시각 |
| 입력 큐 손실 | sequence 틈, overflow | 상태 재동기화, 구간 무효 | 버튼 현재 상태 / 유실된 edge |
| 키음 지각 | 목표 프레임과 쓰기 가능 구간 비교 | 즉시 발음 또는 폐기 | 이후 예약 / 원래 발음 시각 |
| 오디오 마감 실패 | 진입 지연, 완료 여유, 드라이버 통지 | 콘텐츠 대응 검증, 필요 시 재동기화 | 이후 재생 / 누락된 음 |
| 위치 보고 정지·불연속 | 관측 나이, 위치, 잔차, 알림 | 외삽 중단, 새 epoch | 새 대응 / 불확실 구간의 사실 확정 |
| 장치·주기·포맷 변경 | 백엔드 이벤트·오류 | 정지·재구성·교정 유효성 재확인 | 새 스트림 / 무중단 연속성 |
| 절전·휴면 복귀 | 전원 알림, 긴 관측 공백 | 기존 모델 폐기, 재획득 | 재개 / 공백 중 연속성 |
| 스트리밍 고갈 | 준비된 PCM 부족 | 명시적 무음·실패 기록, 반복 시 정지 | 이후 콘텐츠 / 누락 콘텐츠 |
| 외부 DSP·패널 경로 변경 | 내부에서 감지 못할 수 있음 | 교정 무효화 또는 외부 재측정 | 재교정 / 자동 탐지 보장 |

## 12. 측정과 승인 기준

### 12-1. 소프트웨어 측정 (장치 없이)

스레드별로 미리 할당한 링에 고정 크기 이진 레코드를 남기고, 낮은 우선순위 스레드가 파일로 옮깁니다.

- 콜백 진입 지연, 실행 시간, 추정 마감 여유
- 제출 구간, 장치 위치, epoch, 콘텐츠 대응
- 모델 잔차, 관측 나이, 불확실 상태
- 입력 수신·처리 시각, 키음 목표 프레임, 실제 배치 프레임
- watermark, 큐 overflow, 늦은 요청
- present ID, 표시 추정과 실제 통계의 차이

로깅에도 비용(QPC 호출, 캐시, 메모리 대역폭)이 있습니다. **로그를 켰을 때와 껐을 때의 마감 실패 분포를 비교**하고, 필요하면 샘플링·집계합니다. 평균이 아니라 편향, p99, p99.9, 관측 최대값, 실패율을 보고합니다.

보조 도구 (소프트웨어, 오버헤드는 측정해서 판단):

| 도구 | 보는 것 |
|---|---|
| Tracy (`tracy-client`) | 스레드별 구간, 프레임, 사용자 지표 |
| PresentMon | ETW 기반 present → 표시, 프레임 누락 |
| Windows Performance Recorder/Analyzer | 스레드 스케줄링, DPC·인터럽트, GPU 대기열 |
| LatencyMon | DPC 지연이 큰 드라이버 (언더런 원인 진단) |

게임 안에 **타이밍 상태 화면**을 둬서 경계별 현재 상태(시계 상태, 관측 나이, 마감 여유, 입력 전달 간격, 표시 모델 상태)를 보여 주면 사용자 환경 문제를 바로 진단할 수 있습니다.

### 12-2. 물리 측정 (PC가 볼 수 없는 부분)

이 PC의 TOPPING 오인페는 입력이 10채널이라(보고값) 측정용 ADC로 쓸 수 있습니다.

- 접점 기준 신호, 마이크, 광센서를 **가능하면 같은 ADC로 동시에** 기록합니다. 상대 도착 시각이 같은 시계로 나옵니다.
- 광센서는 실제 판정선 위치에 둡니다. 마이크는 귀 위치에 둬서 스피커·공기 경로까지 포함합니다.
- 스위치 신호는 입력 허용 전압·바이어스·절연을 맞춘 측정 회로로 연결합니다.
- **출력→입력 루프백은 왕복(출력 + 입력) 지연입니다.** 순수 출력 지연과 같다고 보지 않습니다. 같은 발진기라 상대 드리프트는 줄지만 ADC 지연·필터·검출 오차는 남습니다. 서브샘플 추정 정밀도가 서브샘플 절대 정확도는 아닙니다.
- 신호 시작 검출 기준과 필터 지연을 기록하고, 장치·포맷·주기·DSP·화면 모드별로 반복 측정합니다.
- **사용자 탭 보정은 개인 선호 보정**으로 분류합니다. 예상 동작과 감각 편향은 100번 평균해도 사라지지 않으므로 객관적 하드웨어 교정이라고 부르지 않습니다.
- 교정값은 장치뿐 아니라 경로·포맷·버퍼·DSP·화면 모드별 유효 조건과 함께 저장합니다. 내부 로그만으로 외부 상수가 그대로라고 증명할 수 없습니다.

### 12-3. 초기 승인 문턱 (정책. 검증한 구성의 기준이지 모든 PC의 보장이 아님)

| 대상 | 기준 |
|---|---|
| 채보·판정 결정성 | 같은 정규 이벤트와 설정에서 완전히 같은 결과 |
| 정상 연속 믹싱 | 예정 프레임 배치 오차 최대 1프레임 |
| 유선 오디오 시간 모델 | 교정 후 물리 측정 절대 오차 p99.9 ≤ 0.5 ms, 관측 최대 ≤ 2 ms |
| 일정 지연 키음 모드 | 유효 타임스탬프·마감 충족 요청에서 목표 도달 오차 p99.9 ≤ 0.5 ms |
| 100 µs 목표 | 별도 실험 등급. 측정계 불확실성부터 검증하며 기본 승인에 쓰지 않음 |
| 판정 지연 주입 | 입력 시각 보존·큐 무손실 조건에서 500 ms 처리 정지 후 결과 동일 |
| 장시간 안정성 | 구성별 2시간 부하 시험에서 언더런·입력 손실 0 (향후 무발생 보장으로 해석하지 않음) |
| 시계 관측 만료 | 유효기간이 지난 모델로 새 판정 확정 0건 |
| epoch 변경 | 이전 epoch 키음 발음 0건 |
| 불연속 복귀 | 조건 회복 후 2초 안에 Running 또는 명시적 실패 상태 |
| 고정 주사율 표시 | 판정선 광학 예측 오차 p99 ≤ 1 ms 목표. 실패 구성은 측정된 오차 등급 표시 |

입력 접점→수신 지연과 접점→음압 지연은 따로 보고합니다. 일반 키보드에 0.5 ms 입력 정확도를 요구하거나 암시하지 않습니다. 부하 시험에는 CPU·GPU 경쟁, 메모리 압박, USB 활동, 드라이버 지연, 렌더 정지, 오디오 마감 실패, 장치 재시작, 절전 복귀를 넣습니다. **프로세스 전체 정지와 렌더만 멈추는 실험은 다른 실패**이므로 따로 주입합니다.

## 13. IIDX에서 배울 것과 피할 것

증거 수준은 `IIDX_timing_policy.md`를 따릅니다. 판정 입력의 시간축은 미확인입니다.

### 13-1. 배울 것

| 메커니즘 | 증거 | 배울 점과 한계 |
|---|---|---|
| 반주 위치와 채보 시각을 반복 비교 | 비교는 확인, 커서 의미는 일부 추정 | 독립 경로와 위상차를 관측. 다만 믹서 커서는 귀 도달 시각이 아님 |
| `틱 수 × 틱 길이`로 시각 계산 | 확인 | 반올림 누적을 피함. 틱 길이 오류나 프레임 정지는 해결 못함 |
| 밀린 틱을 순서대로 실행 | 확인 | 상태 전이를 건너뛰지 않는 복구 수단. 목표 틱의 전진 속도가 제한된 것이 약점 |
| 보정 문턱과 속도 제한 | 확인 | 잡음 반응과 화면 점프를 줄임. PC에서는 장식에만 |
| 위상 보정과 진행률 조정의 분리 | 두 경로 확인, 플래그 연결 일부 추정 | 발상은 가져올 만함. 정지를 주파수 오차로 학습하면 안 됨 |
| 보정량·누락·프레임 오차의 서버 기록 | 필드 확인, 일부 출처 추정 | 현장 오차 재구성의 기반. 물리 오차 측정은 아님 |
| 주사율과 독립적인 판정 창 단위 | 확인 | 화면 모드가 판정 폭을 바꾸지 않음 |

핵심 교훈은 "프레임 시계를 쓰자"가 아니라 **외부 진행 경로와 비교하고, 보정 결과를 기록하고, 상태 전이를 명시적으로 처리하라**입니다.

### 13-2. 피할 것

1. **프레임 진행이 콘텐츠 진행을 지배함.** 프레임마다 목표 틱이 하나씩 올라가서, 프레임이 멈추면 반주가 흘러도 채보가 뒤처집니다. → 오디오 콘텐츠 위치에서 채보 시각을 계산하고, 자동재생은 오디오 경로에서 예약.
2. **복구 능력에 FPS 하한.** 프레임당 최대 평균 1.5틱이라 측정 Hz 120에서 80 FPS 미만이면 수렴 실패(계산). → 프레임 수와 복구 속도를 분리.
3. **앞선 채보를 실시간으로 되돌리지 않음** (`chart > audio + 34`는 기록만). → 검증된 관측으로 양방향 처리, 불연속은 재동기화.
4. **17 ms는 정확도가 아니라 보정 시작 문턱.** 비교 주기, 8.33 ms 틱 양자화, 정수 ms 변환이 더해지므로 "항상 17 ms 이내"는 보장되지 않습니다. 300 ms 지연은 120 FPS 복귀 조건에서 약 0.57초 만에 문턱 근처까지 줄 뿐입니다. → 문턱과 실제 오차 분포를 따로 측정.
5. **곡 끝 Hz 추정이 일시적 렉을 학습할 수 있음 (계산).** 2분 곡에서 300 ms 렉이 한 번 나고 `fix_realtime` 누적이 켜져 있으면, 누적 보정 약 300 ms, 검사 수 약 14,400으로 새 Hz = 120 ÷ (1 + 120 × 300 ÷ 14,400,000) ≈ **119.70 Hz**가 됩니다. 허용 범위(118.5~121.5) 안이라 그대로 적용되고, 다음 곡은 초당 약 2.5 ms씩 뒤처져 7초마다 따라잡기가 반복됩니다. 미확인 조건 함수(`0x1808fe330`)가 이를 막는지는 모릅니다. → 진행률은 정지 구간을 제외하고 추정.
6. **틱에서 발음하면 늦게 처리한 과거 소리를 지금 냄 (추정 경로).** 따라잡는 동안 자동재생과 키음이 압축·지연됩니다. → 자동재생의 시간 소유권을 오디오 스케줄러에 둠.
7. **판정까지 틀어진다고 단정하지 않기.** 입력이 장치 타임스탬프를 보존하는지 미확인입니다.

**공정한 평가**: 고정 120 Hz, 고정 오디오 장치라면 저비용의 제한된 보정이 운영상 충분했을 수 있습니다. 그래도 위 1~4는 고정 하드웨어에서도 남습니다. IIDX는 "좁은 정상 운용 범위를 전제로 한 제한적 복구 설계"이고, 임의의 PC로 그대로 옮길 근거는 약합니다.

**평가를 가장 크게 바꿀 미확인 항목**: ① 판정에 쓰는 입력 시각, ② Voice 커서의 갱신 지점과 기준점, ③ 키음·자동재생의 실제 예약 경로, ④ 언더런·리셋 처리, ⑤ Hz 보정 활성 조건과 실제 값. 정적 추적과, 렌더만 지연시키는 런타임 실험으로 확인할 수 있습니다(`IIDX_timing_policy.md` 10장).

## 14. 의도적으로 만들지 않는 것

- 스레드마다 PLL을 두는 CDC 모사
- 자체 제출 카운터를 물리 시계로 승격하는 구조
- 전역 busy-spin, 무조건적인 최고 우선순위
- 측정 없이 적용하는 코어 고정·타이머 해상도 변경
- 초기부터의 128비트 원자 연산, 자작 seqlock
- 노트 오차를 숨기는 긴 smoothing
- 초기부터의 자체 드라이버, 직접 DX12/Vulkan 백엔드 (타이밍 문제를 측정하기 전에는 `wgpu` 교체 근거가 없음)
- 데이터 배치(SoA 등)·수십 ns 시계 읽기 같은 미세 최적화 (수백 µs 관측 오류가 남아 있는 동안은 기준 1~3에 기여하지 않음)
- 일반 입력 히스토그램으로 USB 폴링·접점 정확도를 추정하는 UI
- 탭 평균을 객관적 하드웨어 교정이라고 부르는 기능

## 15. 구현 순서

1. 정규 채보 시간·판정·리플레이 코어. 동시각 순서와 버전 규칙 확정. (BMS·`.1` 가져오기 → 정규 ns 이벤트. 곡 데이터 형식과 가져오기 규칙은 `곡 데이터 형식.md`)
2. 오프라인 믹서와 콘텐츠 대응. 프레임 배치, 긴 음 복원, 보이스 초과 정책 검증.
3. WASAPI 공유 이벤트 경로 하나로 시간 계약 구현. 지원 시 저지연 주기 사용.
4. 아날로그 출력 측정으로 위치·지연 기준점 검증. 그 전에는 정확성 등급을 부여하지 않음.
5. 입력/판정 스레드, watermark, 최소 지연 키음, 지각 정책.
6. 최소 렌더와 present 기록. 광센서로 표시 예측 검증.
7. 마감 실패·장치 변경·절전·overflow 주입 시험과 상태 머신 완성.
8. WASAPI 배타·ASIO 어댑터 추가. 같은 계약 시험을 각각 통과.
9. 일정 지연 키음 모드, 장치 타임스탬프 입력 지원.
10. 측정에서 드러난 병목만 최적화.

| 버퍼 | 64프레임 = 1.451 ms (지원 범위 8~2048) → 콜백 초당 약 689회 | 보고값 |
| 출력 지연 | 154프레임 = 3.492 ms | **보고값. 물리 측정 아님** |
| 채널 | 출력 8, 입력 10, 32비트 정수 `ASIOSTInt32LSB` | 보고값 |

"입력 폴링 1 ms + 콜백 대기 최대 1.45 ms + 출력 3.49 ms ≈ 5.9 ms"는 가정한 구간들을 더한 **상단 쪽 계산**입니다. 하한이 아니고, 물리 측정값도 아닙니다(초안의 "하한" 표기를 정정).
