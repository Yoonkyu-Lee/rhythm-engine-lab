# Codex 검토 #3: 선곡 화면 채보 미리보기의 소리 메모리 정책 (2026-10-16)

> 요청문: `2026-10-16_codex_미리보기메모리_요청.md`. 대상: cp3/README.md 4-3. 원문 그대로 보관 (링크 경로만 저장소 기준이 아닐 수 있음).

> **우리 확인 (2026-10-16)**: 6절의 보이스 예산 반례는 코드로 확인함 — `Mixer::admit`이 `voices.len()`으로 예산을 검사하는데, 블록 안에서 이미 끝난 보이스는 `fill` 끝의 `retain`에서야 빠진다. 그래서 예산이 찬 상황에서만 블록 크기에 따라 결과가 달라진다. CP2 실행 기록 53개 중 넘침은 bms 프로필 두 번(3회, 44회)뿐이고 우리 방식 결과에는 영향 없음.

**제 추천은 1·2·5·7·8의 방향은 유지하고, 3·4·6의 계약을 보강하는 것입니다.** **확인함:** [4-3](/D:/Engineering/rhythm-engine-lab/cp3/README.md)의 요구는 키음까지 전부 자동 연주이지만, 준비되지 않은 소리를 건너뛰면 그 요구와 “미리보기 = PERFECT 플레이”가 성립하지 않습니다. 현재 믹서에도 보이스 예산이 부족할 때 블록 경계에 따라 결과가 달라질 여지가 있습니다. **추정·추천:** f32를 기본으로 쓰되 메모리 예산을 명시하고, 시작 구간의 모든 소리가 준비된 뒤 재생하며, 준비 부족 시에는 버퍼링 후 같은 위치에서 다시 시작하겠습니다. 탐색은 플레이와 공유하는 보이스 상태 전이로 구현하고, 짧은 소리는 전체 디코딩, 긴 소리의 부분 디코딩은 전체 디코딩 결과와의 일치를 입증한 다음 추가하겠습니다.

아래에서 **확인함**은 지정 문서·코드를 읽어 확인했다는 뜻입니다. 기존 측정은 재측정하지 않았고, Qwilight도 분석 문서만 검토했습니다. **추정**에는 추천·예상 위험·측정 제안이 포함됩니다. 파일 수정, 비공개 자산 접근·반출, 테스트 실행은 하지 않았습니다.

**1. 미정 (가): W·디바운스·긴 소리**

**확인함**

- 4-3은 시작점부터 W초에 쓰는 소리를 먼저 준비하지만 W는 미정입니다.
- [Qwilight 분석](/D:/Engineering/rhythm-engine-lab/cp0/Qwilight_preview.md)은 전체 디코딩 완료 후 시작하며, 디바운스는 OS 더블클릭 시간에 연결되어 있습니다. 이것이 미리보기의 최적 대기시간이라는 실측 근거는 없습니다.
- [리샘플러](/D:/Engineering/rhythm-engine-lab/cp2/crates/rcore/src/resample.rs)는 소리마다 64탭 필터를 적용하고, 소리 경계 밖을 0으로 취급합니다. 현재 함수는 전체 뱅크 변환용입니다.

**추정 — 추천안과 이유**

초기 실험값은 **W=2초, 곡 선택 디바운스=150ms**로 두겠습니다. 확정값이 아니라 비교 실험의 출발점입니다.

- 명시적인 구간 클릭은 추가 디바운스 없이 처리합니다. 드래그 중에는 최신 위치만 남기고, 손을 놓으면 즉시 실행합니다.
- 준비 집합은 **시작점에 이미 울리고 있어야 하는 보이스 + 앞으로 W초 안에 시작하는 소리**입니다. 시작점 이전에 시작한 긴 키음도 포함합니다.
- 이후 작업은 **현재 위치 이후 다음 사용 시각** 순으로 배정합니다. 곡 전체에서의 최초 사용 시각 순이면, 후반 탐색 때 이미 지나간 구간이 우선될 수 있습니다.
- 재생 중에도 W초 준비 범위를 계속 갱신합니다. “처음에 앞섰으니 끝까지 안전하다”는 가정은 두지 않습니다.

첫 구현은 전체 소리 디코딩으로 정확성 기준을 세우겠습니다. 긴 소리가 시작 지연을 지배한다면, 그 소리만 **장치 레이트 기준 0.5~1초 블록**으로 나누어 시작점 주변부터 준비하는 경로를 추가하겠습니다.

**추정 — 위험**

부분 디코딩한 조각을 독립된 소리처럼 리샘플링하면 경계와 위상이 달라집니다. 각 블록은 **원래 소리의 절대 출력 샘플 번호**를 기준으로 변환하고, 필터에 필요한 앞뒤 입력과 코덱 복원 상태를 확보해야 합니다. 중간 블록 경계에 0 패딩을 넣으면 안 됩니다.

Vorbis에는 샘플 위치 탐색 API가 있지만, 이것이 현재 계획한 패킷 묶음에서 곧바로 가능한 것은 아닙니다. 별도의 탐색 색인과 상태 복원 설계가 필요합니다. [Xiph 탐색 문서](https://www.xiph.org/vorbis/doc/vorbisfile/seeking.html)

**추정 — 정하기 위한 측정**

W는 0.5·1·2·4초, 디바운스는 75·150·250ms를 비교합니다. 짧은 소리 다수, 긴 스템 다수, 곡 후반 탐색, 연속 드래그를 나누어 다음을 잽니다.

- 선택 확정→**누락 없는 첫 출력**까지 p50·p95·p99
- 준비 범위가 바닥나는 횟수와 버퍼링 시간
- 취소 후 낭비한 CPU 시간·읽기량·최고 메모리
- 부분 디코딩 결과와 전체 디코딩 결과의 해당 구간 해시

목표는 첫 비영 샘플 하나가 빨리 나오는 것이 아니라, **필요한 소리가 모두 갖춰진 재생이 빨리 시작되는 것**입니다.

**2. 미정 (나): f32와 메모리 초과 대비책**

**확인함**

- 321 MB는 [4-1의 Python+libsndfile 표본 측정](/D:/Engineering/rhythm-engine-lab/cp3/README.md)입니다. BMS 최대 곡이나 여러 차분의 합집합에 대한 상한은 아닙니다.
- `resample_bank`는 입력 뱅크를 참조하면서 출력 PCM을 별도 할당합니다. 따라서 최종 PCM 크기와 로딩 중 최고 메모리는 다릅니다.
- 현재 보존 계약은 무손실 경로와 손실 경로를 구분합니다. [지난 검토](</D:/Engineering/rhythm-engine-lab/cp3/reviews/2026-10-16_codex_소리저장.md>)에서 지적한 구분이 반영되어 있습니다.

**추정 — 추천안과 이유**

**자동 i16 전환보다 메모리 예산과 할당 전 검사를 먼저 넣겠습니다.**

최종 PCM 예상량은 소리 표만으로 계산할 수 있습니다.

`Σ(장치 레이트 변환 후 프레임 수 × 채널 수 × 4바이트)`

여기에 압축 입력, 디코더 작업 버퍼, 리샘플링 입력·출력 중복, 이전 저장소, 취소 중 작업을 더한 **최고 사용량 예산**을 따로 둡니다.

예산이 부족하면 다음 순서로 대응하겠습니다.

1. 이전 곡의 참조와 취소 작업을 회수한 뒤 다음 곡을 올립니다.
2. 같은 Track에서 이전 차분만 사용하는 PCM을 해제합니다.
3. 검증된 긴 소리 부분 디코딩 경로를 사용합니다.
4. 그래도 플레이 전체 준비가 불가능하면 명시적으로 시작을 막습니다.

마지막 조치는 현재의 “플레이는 전부 준비돼야 시작”을 유지할 경우의 결론입니다. 초대형 곡 플레이까지 지원하려면 별도로 플레이 스트리밍 계약을 설계해야 합니다.

**추정 — 위험**

- “같은 Track은 추가분만”을 무제한 적용하면 차분을 돌아보는 동안 합집합이 계속 커집니다.
- f32 사용 자체가 플랫폼 간 비트 동일성을 보장하지는 않습니다.
- 장치 레이트가 높아지면 PCM도 커집니다. 원본 레이트 측정값을 그대로 예산으로 쓰면 안 됩니다.
- 손실 없는 정수 PCM을 정수로 보관했다가 믹싱 시 f32로 바꾸는 특수 경로는 가능하지만, 리샘플링 결과나 Vorbis 실수 출력까지 일반화할 수 없습니다.

**추정 — 정하기 위한 측정**

BMS의 큰 곡뿐 아니라 **최대 소리 수·최장 소리·차분 합집합·최대 지원 출력 레이트**로 층화합니다. 실제 Rust 로더에서 최종 PCM, 프로세스 커밋, 작업 집합, 임시 버퍼, 취소 회수 시간을 분리해 측정합니다. 650 MB는 예산이 아니라 비교할 표본값으로만 사용하겠습니다.

**3. 미정 (다): 선곡과 플레이의 출력 스트림**

**확인함**

- [기록 시계 설계](</D:/Engineering/rhythm-engine-lab/design/기록 시계 설계.md>)와 [CP2 결론](/D:/Engineering/rhythm-engine-lab/cp2/README.md)은 D를 경로별로 측정하고 플레이 중 고정합니다.
- WASAPI 공유 모드는 여러 애플리케이션의 출력을 공유하고, 배타 모드는 해당 엔드포인트를 독점합니다. [Microsoft 문서](https://learn.microsoft.com/en-us/windows/win32/coreaudio/exclusive-mode-streams)
- 현재 인계 키는 Track 해시와 장치 레이트입니다.

**추정 — 추천안과 이유**

기본은 **선곡에서 공유 모드**, 플레이가 공유 모드이고 장치·형식도 같으면 스트림을 유지하겠습니다. 플레이가 배타·ASIO이면 진입 시 재개방하고, 선곡 복귀 시 공유 모드로 돌아옵니다. 선곡부터 플레이 경로를 유지하는 것은 별도 선택지로 둡니다.

인계 절차는 다음처럼 구체화하겠습니다.

1. 플레이 장치를 열어 실제 형식을 확정합니다.
2. 호환되는 준비 완료 PCM을 재사용합니다.
3. 부족하거나 레이트가 다른 PCM을 준비합니다.
4. 새 경로의 시계와 D를 확정하고 플레이 원점을 설정합니다.
5. 플레이에 필요한 전체 집합이 준비되면 시작합니다.

**PCM 저장소 재사용과 실행 상태 재사용은 분리**해야 합니다. 레이트가 같아도 미리보기 보이스·대기열·재생 위치·D까지 넘기지는 않습니다.

**추정 — 위험**

재개방 지연과 실패, 장치 제거, 실제 레이트 변경을 처리해야 합니다. ASIO에서 다른 프로그램의 소리가 막히는 범위는 드라이버별로 확인해야 하며 일괄 가정하지 않겠습니다.

레이트가 달라졌을 때 이전 장치용 PCM을 다시 리샘플링하는 것은 기본으로 삼지 않겠습니다. 원본 기준 PCM에서 새 레이트로 직접 변환한 결과와 달라질 수 있기 때문입니다.

**추정 — 정하기 위한 측정**

공유→공유·배타·ASIO 전환에서 개방 시간, 전체 플레이 진입 시간, PCM 재사용률, 최고 메모리, D 재측정값을 잽니다. 장치 제거·레이트 변경·개방 실패도 포함합니다. 스트림 유지의 이득이 재디코딩보다 큰지 별도로 비교해야 합니다.

**4. 미정 (라): 구간 통계**

**확인함**

- [Track 모델](/D:/Engineering/rhythm-engine-lab/cp3/README.md)은 음악 이벤트와 노트 배분을 구분합니다. 노트 하나가 여러 소리를 가질 수 있습니다.
- 레인에는 역할과 묶음이 있고, 시간 지도와 스크롤 지도가 분리됩니다.
- 4-3은 차분별 통계와 하이라이트를 라이브러리 색인에 저장하도록 합니다.

**추정 — 추천안과 이유**

**250ms 고정 시간 구간을 기본으로 저장하고, 기본 표시에서는 1초 단위로 합산**하겠습니다. 마디는 별도 경계 정보로 제공합니다. 시간 진행 바에 마디별 노트 수만 그리면 BPM·STOP·변박에 따라 밀도 비교가 왜곡되기 쉽습니다.

첫 통계 집합은 다음 정도면 충분합니다.

| 통계 | 권장 정의 |
|---|---|
| 노트 밀도 | 구간 내 입력 노트 시작 수 ÷ 실제 구간 길이 |
| 동시치기 | 동일 정규 시각의 노트 수 분포·최댓값 |
| 롱노트 | 시작 수, 유지 시간 적분, 최대 동시 유지 수 |
| 레인 분리 | 전체 + 레인별 원시 집계, 선언된 묶음별 합산 |
| 역할 분리 | 건반·스크래치·사이드 등 |
| 하이라이트 | 작성자 지정 우선, 없으면 일정 길이의 밀집 구간에서 결정적으로 선택 |

노트 하나가 소리 세 개를 내도 노트 수는 하나입니다. 롱노트 끝 판정·틱 판정은 시작 수와 섞지 않고 별도 항목으로 정의합니다.

**추정 — 위험**

250ms 경계에 걸친 짧은 폭발 구간이 둘로 나뉠 수 있습니다. 따라서 “최대 NPS”를 고정 칸의 최대값으로 부르지 말고, 필요하면 **이동하는 1초 창의 최대치**를 별도로 계산해야 합니다. 중첩된 레인 묶음의 합을 전체 합계로 취급해서도 안 됩니다.

**추정 — 정하기 위한 측정**

0.1·0.25·0.5·1초 저장 간격에서 색인 크기·첫 화면 로딩 시간·짧은 밀집 구간 보존 정도를 비교합니다. STOP·변박·곡 끝의 짧은 구간·롱노트 경계·변형 시드별 결과는 독립 집계와 대조합니다.

**6. 특히 중요한 두 문제: 탐색 정확성과 준비 부족**

**확인함 — 현재 믹서의 보이스 예산 처리**

[`Mixer::admit`와 `fill`](/D:/Engineering/rhythm-engine-lab/cp2/crates/rcore/src/mixer.rs)는 다음 순서로 움직입니다.

- 블록 안에서 발생하는 이벤트들을 보이스에 올립니다.
- `voices.len()`으로 예산을 검사합니다.
- PCM을 섞습니다.
- 블록 끝에 끝났거나 끊긴 보이스를 제거합니다.

**추정 — 코드에서 도출되는 반례, 실행 미검증**

예산 1, 첫 소리가 프레임 0~10, 다음 소리가 프레임 20에 시작한다고 가정하십시오.

- 0~64를 한 블록으로 처리하면 두 번째 등록 시 첫 보이스가 아직 벡터에 남아 거부될 수 있습니다.
- 작은 블록으로 처리하면 첫 보이스가 먼저 제거되어 두 번째가 받아들여집니다.

`cut_same`도 기존 보이스의 끝을 바꾼 뒤 길이를 검사하므로, 끊긴 슬롯 때문에 새 소리가 거부될 수 있습니다. 기존 블록 크기 테스트의 존재만으로 예산 부족 조건까지 검증되었다고 볼 수 없습니다.

**추정 — 추천 구현**

논리적인 보이스 점유는 **이벤트 시각**을 기준으로 만료·끊기·등록하고, 이미 출력할 과거 구간은 별도 렌더 구간으로 보존하겠습니다. 이 상태 전이를 플레이와 탐색이 공유해야 합니다.

탐색에는 다음 조건도 필요합니다.

- 같은 시각 이벤트의 순서와 보이스 합산 순서를 고정합니다.
- 목표 시각 이전 이벤트를 처리하고, 목표 시각 이벤트는 정확히 한 번 처리합니다.
- 샘플 오프셋은 일반적으로  
  **`목표 프레임 − 이벤트 시작 프레임`**으로 계산합니다.  
  `ns_to_frame(목표 시각 − 이벤트 시각)`은 개별 반올림 때문에 1프레임 다를 수 있습니다.
- 과거 이벤트를 현재 믹서에 늦게 들어온 요청으로 넣지 않습니다. 현재 `PlayWhole` 정책이면 키음이 처음부터 다시 나올 수 있습니다.
- 복원 완료 뒤 미래 출력 프레임에 상태 전체를 한 번에 설치합니다.

비용은 단순 구현에서 대략 **이전 이벤트 수 E × 보이스 예산 V**입니다. 현재 `pending`은 최솟값 선형 탐색과 `remove`를 반복하므로, 모든 이벤트를 미리 넣는 방식은 최악에 이차 비용이 됩니다. 정렬된 이벤트 커서로 순회하고, 측정 후 필요하면 2~5초 간격 상태 스냅샷을 추가하겠습니다.

검증 기준은 같은 정책의 **처음부터 PERFECT 렌더한 결과를 잘라낸 구간 = 탐색 후 렌더 구간**입니다. 작은 예산, 같은 ID 연타, 동일 시각 이벤트, 긴 꼬리, 블록 경계 직전·직후를 반드시 포함합니다.

**확인함 — 준비 부족의 영향**

4-3은 준비되지 않은 소리를 건너뛰지만, 그 소리가 기존 보이스를 끊거나 예산을 차지해야 하는 경우의 상태 처리는 명시하지 않습니다.

**추정 — 추천 처리**

누락은 해당 소리 하나의 무음으로 끝나지 않을 수 있습니다. 재트리거 끊기를 생략하면 이전 소리가 더 오래 울리고, 예산 점유를 생략하면 원래 거부될 다른 소리가 살아남을 수 있습니다.

따라서 **보이스 상태 계산과 PCM 준비 여부를 분리**하십시오. 비상 누락 시에도 논리 상태는 유지하고, 출력 누락을 별도로 기록해야 합니다.

정상 경로에서는 부족을 미리 발견해 버퍼링합니다. 장치 시계 C는 계속 흐르게 두고, 준비 후 **콘텐츠 원점을 새로 잡아** 해당 위치에서 재개합니다. 이미 지나간 짧은 키음을 뒤늦게 처음부터 내는 것은 금지하겠습니다. 준비 시점에 따라 출력이 달라진 실행은 결정적 PERFECT 재생 성공으로 집계하면 안 됩니다.
