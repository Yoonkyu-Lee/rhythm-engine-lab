# Checkpoint 3 — 칠 수 있는 게임

> 상태: **스펙 초안 (2026-10-16)**. 결정이 필요한 곳은 ⚑로 표시.
> 앞 단계: CP1(시계·동기 부품), CP2(건반 하나 시험장 — 기록 시계로 렉에도 PERFECT 키음 = 반주, `../cp2/README.md`).
> 근거 문서: `../design/곡 데이터 형식.md`(곡 형식 구상), `../design/기록 시계 설계.md`, `../design/설정 체계.md`, CP0 분석(`../cp0/`), CP2 "CP3로 넘기는 것".
> CP4 = 보이는 게임(기어·노트·스킨·에셋 연결·시각 트랙·연출·wgpu 렌더러·프론트 설정). 그래픽 에셋이 어디로 연결되는지는 CP4 범위이고, CP3 형식에는 그 **자리만** 둔다.

## CP3가 답할 질문

> IIDX·DJMAX·BMS 곡을 **우리 형식으로 변환**해, **레인 구성을 채보가 정하는** 엔진에서 원래 게임처럼(같은 소리, 같은 판정 규칙) 칠 수 있는가 — 기록 시계의 약속(PERFECT 키음 = 반주)을 지키면서, 선곡부터 플레이 시작까지 BMS 구동기보다 압도적으로 빠르게.

그리고 CP3가 끝나면 아래가 완전히 답해져 있어야 한다.

1. **우리 리듬게임 엔진의 이름은?** ⚑
2. **엔진이 다루는 "곡" 객체는 어떻게 생겼나** — 채보, 키음이 재생되는 형식 (그래픽 연결은 CP4).
3. **그 "곡" 객체의 이름은?** ⚑
4. **채보 형식은 BMS처럼 레인이 하드코딩된 것이 아니라 매개변수로 자유롭게 만들 수 있고, 엔진이 그걸 인식하는가.**

## 1. 이름

| 대상 | 결정 (2026-10-16) | 비고 |
|---|---|---|
| 엔진 | **Unison (임시 이름)** | 문서에서만 쓴다. **코드·파일 이름·확장자·식별자에는 쓰지 않는다** (사용자 결정). 정식 이름은 나중에 정한다 ⚑ |
| 곡 객체 | **Track** | 음악 플레이어의 "트랙"처럼 오디오만이 아니라 이미지·메타데이터·가사 등을 함께 담은 객체. 우리 Track = 정보 + 음악 레이어 + 차분들 + 소리 묶음 (+ CP4에서 그래픽 에셋 연결) |
| 파일 확장자 | ⚑ | 엔진 정식 이름이 정해진 뒤 |

용어 규칙:
- "곡" = Track. **차분**(난이도별 채보)은 Track 안의 구성 요소다.
- "트랙"이라는 말은 이제 Track(곡 객체)에만 쓴다. 지금까지 "반주 트랙"이라 부르던 긴 자동재생 소리는 **반주 스템**(stem)으로, DJMAX 채보 형식의 "트랙"(이벤트 채널)은 **채널**로 부른다.

## 2. 곡 객체 (작성 형식 → 실행 형식)

`../design/곡 데이터 형식.md`의 구상을 바탕으로 정한다. 두 층으로 나뉜다.

채보 형식은 두 층이다. **플레이에 쓰는 것은 바이너리**(IIDX `.1`·DJMAX `.bytes`처럼 — 해석 없이 바로 읽는 고정 레코드), **사람이 쓰고 고치는 것은 텍스트**(BMS처럼 — 읽고 비교하고 버전 관리할 수 있음). 둘을 버전이 정해진 컴파일러가 잇는다.

| 층 | 누가 쓰나 | 내용 | 형태 |
|---|---|---|---|
| **작성 형식** (source) | 사람·컨버터 | 정보(manifest), 템포 맵(박 단위), 소리 테이블, **음악 레이어**(곡의 모든 소리 이벤트), **차분**(노트가 음악 이벤트를 묶음), 시각 트랙 자리(CP4) | 텍스트(TOML) + 원본 오디오 |
| **실행 형식** (compiled) | 컴파일러 | 정규 ns 시각의 소비자별 배열(자동재생·레인별 노트·화음·스크롤 지도), 디코딩이 빠른 소리 묶음, 색인 | 고정 레코드 바이너리 (CP2 `.rtc`의 확장) |

곡 객체가 가져야 할 것 (CP2·CP0 교훈 포함):

- **곡에는 곡의 진실만**: 장치 지연·사용자 보정은 넣지 않음. 곡 오프셋을 고치면 패키지 버전을 올림.
- **음악은 하나, 차분은 배분**: 차분의 노트는 음악 이벤트를 하나 이상 묶고, 묶이지 않은 이벤트는 컴파일러가 자동재생으로 계산 (IIDX 77% 곡에서 차분 간 소리 합계가 완전히 같음, 확인).
- **암묵 규칙을 명시 필드로**: 빈 레인 소리, 롱노트 규칙, 같은 소리 재트리거 정책, 변형(#RANDOM 대체, 선택 결과는 리플레이에 기록).
- **명시 필드**: 기준 BPM(하이스피드 기준), 여러 값 태그(팩·출처·콜라보), 레인 레이아웃(아래 3), UTF-8 고정, 시간 원점("반주 첫 샘플 = 0").
- **출처**: 변환으로 만들었으면 원본 형식·원본 해시·컨버터 버전, 변환 보고서.

## 3. 레인 모델 — 채보가 정하는 레인

BMS는 채널 번호가 곧 레인(11~19 = 1P 건반)이고, 키 모드는 쓰인 채널로 추정한다. Qwilight는 그 추정 때문에 순수 10K를 못 만든다(`#4K`·`#6K`만 헤더 인식, CP0 DJMAX 변환에서 확인). 우리 형식은 **차분이 자기 레인 구성을 선언**한다.

```toml
# 차분 안: 레인 레이아웃 선언 (예: DJMAX 6B)
[layout]
name = "6B"                    # 표시·키 배치 저장의 열쇠
[[layout.lane]]  id = "L1" ; role = "key"
[[layout.lane]]  id = "L2" ; role = "key"
... (L3~L6)
[[layout.lane]]  id = "SL" ; role = "side"     # 사이드 트랙
[[layout.lane]]  id = "SR" ; role = "side"
[[layout.group]] id = "main"; lanes = ["L1","L2","L3","L4","L5","L6"]   # 변형(랜덤 등)이 섞는 단위

[[notes]]
at = "12:0"; lane = "L3"; plays = ["m120"]
```

- **레인 = 이름 붙은 입력 채널.** 수·이름·역할(key / scratch / side / trigger / pedal …)을 차분이 정한다. 엔진에 "7K" 같은 고정 모드가 없다 — 프리셋 레이아웃(IIDX SP 7+1, DP 14+2, DJMAX 4B~8B, BMS 5K·7K·9K …)은 편의일 뿐.
- **레인 묶음(group)**: 랜덤·미러 같은 변형이 어느 레인끼리 섞는지, 1P/2P가 무엇인지.
- **키 배치**는 레이아웃 이름별로 저장: 레인 → 물리 입력(여러 개 가능).
- **화면 배치**(레인이 화면 어디에 어떤 모양으로 — DJMAX 사이드·트리거처럼 공간을 공유하는 표기 포함)는 CP4. CP3 단순 화면은 레인을 선언 순서대로 같은 폭으로 그린다.
- **노트 고르기 규칙**(같은 레인 연타·겹친 창)은 레인 모델 위의 엔진 규칙으로 명시하고, 판정과 키음이 같은 함수를 쓴다 (CP2).

## 3-1. 변속과 스크롤 — 시간과 화면 위치를 분리한다

**배운 것 (CP0 0-7·0-8·0-9, 정적 분석)**

| | 노트 간격(화면) | 화면 속도 | 정지 | 기준 BPM (사용자 속도를 맞추는 값) |
|---|---|---|---|---|
| IIDX | 박 위치 비례 | 현재 BPM(**정수 반올림**) × HS | `.1`에 정지 이벤트 없음 (BPM 최소 3) | FHS: HS를 계산하는 순간의 현재 BPM (곡 시작 = 시작 BPM) |
| DJMAX | tick 위치 비례 | 현재 템포 ÷ **곡 정보 BPM** × 배속 | 스크롤 이벤트 없음 (낮은 템포로 대신) | 곡 정보 BPM (정수, 곡마다 정해 둠) |
| Qwilight (BMS) | 마디 위치 비례 | BPM × SCROLL ÷ 기준 BPM × 설정값 | STOP = BPM 0 구간, 음수 BPM = 역스크롤, #SPEED 미지원 | 사용자 전역 옵션 (기본: 가장 오래 유지된 BPM) |

- 세 게임 모두 **스크롤이 템포에 묶여 있다**(화면 위치 = 템포를 시간에 대해 적분). 변속 비율은 같게 보인다.
- 다른 것은 **기준 BPM**이다. DJMAX → BMS 변환에서 변속 연출이 달라진 원인이 이것이다: BLACK SWAN은 DJMAX 기준 174, Qwilight 기준 116 → Qwilight에서 곡 전체가 1.5배 빠름 (기준이 다른 곡 13곡, 체감 0.83–1.5배). BMS에는 기준 필드가 없어 변환으로는 못 맞춘다.
- 세부 차이도 연출을 바꾼다: IIDX는 BPM을 **정수로 반올림**해 스크롤한다 (叙情의 채보 BPM 179.94 → 180). BMS 마디·STOP 단위로 옮기면 반올림·격자 오차가 생긴다.

**Unison의 방식 (결정, 2026-10-16)**

1. **시간 지도와 스크롤 지도를 따로 둔다.**
   - 시간 지도(박 → ns): 판정·소리가 쓰는 진실. 원본 시각을 그대로 (IIDX는 ms, DJMAX는 tick + 템포, BMS는 마디·BPM·STOP).
   - 스크롤 지도(곡 시각 → 화면 위치): 구간마다 (시작 시각, 시작 위치, 속도). 속도 0 = 정지, 음수 = 역스크롤, 위치 불연속 = 순간 이동. **템포에서 자동 계산되는 기본값이 있지만, 채보가 따로 적을 수 있다**(osu!의 SV처럼 템포와 무관한 속도 변화 가능).
2. **컨버터가 원작의 스크롤 규칙을 그대로 계산해 스크롤 지도로 적는다.** IIDX는 정수 반올림 BPM 적분, DJMAX는 tick 비례 ÷ 곡 정보 BPM(tick/마디 384 곡 보정 포함), BMS는 BPM × SCROLL 적분 + STOP 정지 + 음수 BPM 역스크롤(+ #SPEED는 beatoraja 의미로).
3. **기준 스크롤 속도를 차분의 명시 필드로 둔다** (소수 허용, 정수로 자르지 않음). 원작의 값을 그대로: IIDX = 시작 BPM, DJMAX = 곡 정보 BPM, BMS = 가져오기 보고서에 후보(시작·최빈·최고·최저)를 적고 기본은 최빈.
4. **사용자 설정은 노출 시간(ms)** — 기준 속도 구간에서 노트가 보이는 시간. 엔진이 속도를 연속값으로 계산한다 (속도 = 보이는 길이 ÷ 노출 시간). 녹숫자·배속 같은 원작 표시는 환산 표시로만.
   - **커버를 움직일 때 두 방식 중 고른다**:
     - **노출 유지**(기본): 커버를 내려 보이는 길이가 줄면 속도도 같은 비율로 줄여, 노트가 나타나서 판정선에 닿기까지의 시간이 그대로다. 노트는 더 낮은 곳에서 나타나 더 천천히 내려오고 화면에서 더 촘촘해 보인다. (IIDX FHS의 동작과 같음)
     - **속도 유지**: 속도는 그대로, 보이는 길이만 줄어 노출 시간이 짧아진다. (IIDX 클래식 HS·DJMAX에 커버를 단 것과 같음)
5. **검증**: 표본 셋(IIDX op.31 「叙情」 — 템포 이벤트 37개·BPM 100~350·3/4박 / DJMAX BLACK SWAN — 116↔174, 곡 정보 BPM 174 / BMS Aery Aleph-0 — BPM 변화 171회(0.24~65535.9999)·STOP 2,553회·마디 길이 변경 276회)에서, 원작의 노트 위치 식으로 계산한 위치 ↔ Unison 스크롤 지도로 계산한 위치를 노트마다 비교해 일치(오차 한도 안)를 확인한다. 화면 없이 숫자로 비교할 수 있다.

## 4. 빠른 파일 시스템 ⚑

BMS 구동기는 곡 폴더의 낱개 파일(채보 텍스트·소리 수백 개)을 선곡·로딩 때마다 날로 읽어서 프레임 드롭이 크다. 우리는 **개방성을 내주고 읽기 속도를 얻는다**.

| 구성 | 내용 | 얻는 것 |
|---|---|---|
| **곡 묶음 파일** (곡 하나 = 파일 하나) | 앞부분에 고정 크기 색인(구역 위치표), 그 뒤 정보·차분들(실행 형식)·소리 묶음·**작성 형식 원본**(결정 2026-10-16: 배포 묶음에 포함) | 파일 하나 열기 + 필요한 구역만 읽기. 원본 구역은 플레이 때 읽지 않음 — 받은 사람이 고쳐 다시 컴파일할 수 있음 |
| **라이브러리 색인** (전체 곡 = 파일 하나) | 곡마다 정보·태그·레벨·미리듣기 위치·묶음 해시 | 선곡 화면이 곡 묶음을 열지 않음. 시작 때 색인 하나만 읽음 |
| **작성 형식 → 묶음** | 컴파일러가 만들고, 원본 해시 + 컴파일러 버전이 같으면 다시 만들지 않음 | 편집은 작성 형식, 배포·플레이는 묶음 |

참고 — 원작들이 소리를 다루는 방식 (CP0 확인):
- IIDX: 곡마다 소리 묶음 하나(`.2dx` = MS-ADPCM WAV 묶음, 약 4:1 압축 / 새 곡은 `.s3p` = WMA 손실 압축 묶음, 차분별 묶음이 따로 있을 수 있음). 곡을 고르면 묶음을 통째로 읽어 디코딩.
- DJMAX: 곡마다 암호화된 묶음 하나 안에 키음 Ogg Vorbis가 낱개로 들어 있음. 곡을 시작할 때 FMOD가 메모리에서 소리마다 PCM으로 풀어 올리고(로드 때 디코딩), 곡을 나가면 해제. 로딩 화면(아이캐치)이 그 시간을 가린다.
- 둘 다 **"압축해 묶어 두고, 로딩 때 디코딩, 디코딩 결과는 남기지 않음"** = 아래 (b). 채보도 둘 다 **바이너리**(IIDX `.1`: 이벤트 8바이트 고정 레코드, ms 정수 / DJMAX `.bytes`: tick 단위 자체 바이너리)이고, 텍스트는 BMS뿐이다.

### 4-1. 소리 저장 (결정, 2026-10-16)

전체 자산 조사(BMS 4팩 약 185만 · IIDX 약 202만 · DJMAX 약 46.5만 파일)와 실측에서 정했다.

| 원본 | Track 묶음에 담는 것 | 근거 |
|---|---|---|
| Ogg Vorbis (DJMAX 전부, BMS 대부분) | **Vorbis 패킷 그대로** + 곡 안에서 공유하는 Vorbis 설정 머리 | 손실 원본을 다시 굽지 않음. 파일마다 반복되던 약 4 KB 머리(DJMAX 곡 크기의 약 30%)를 한 번만 담음 |
| FLAC | **그대로** | 무손실 |
| WAV PCM 정수 8·16·24비트 | **FLAC** (비트 깊이·샘플레이트 그대로) | 무손실, 크기 약 절반 |
| WAV 32비트 실수 | **FLAC 24비트** (−144 dB 아래만 잘림, 사실상 무손실) | FLAC은 실수를 못 담음, 대상 소수 |
| MS-ADPCM (IIDX 옛 곡) | **디코딩 → FLAC 16비트** (디코딩 결과가 16비트 정수라 완전 무손실) | 실측: 원본의 2.4배 |
| WMA (IIDX 새 곡), MP3, AAC | **디코딩 → FLAC 16비트**. ±1.0을 넘는 소리만 볼륨을 낮춰 저장하고 이득을 소리 표에 기록. **WMA는 ffmpeg 디코딩 결과의 앞 3샘플을 잘라 냄** | 실측: 원본의 1.3배. 앞쪽 지연: 같은 소리가 ADPCM·WMA 양쪽에 있는 유일한 곡(08520 HYPER BOUNDARY GATE)에서 내용으로 짝지은 189쌍 전부가 WMA +3샘플(0.07 ms) |
| 3채널 이상 | 스테레오로 다운믹스 | 보고서에 기록 |
| 판정 불가 | 건너뜀 | 보고서에 기록 |

- **샘플레이트는 원본 그대로** 담고, 로딩 때 출력 장치 레이트로 리샘플링한다(CP2의 결정적 리샘플러).
- **엔진 디코더는 Vorbis와 FLAC 둘.** 그 밖의 코덱 디코더는 컨버터에만 있다.
- **원본 보존 기준 = 디코딩한 소리가 샘플까지 같음.** Ogg 그릇 정보(페이지 구조·CRC·주석 머리·파일 시각)는 버린다. 정확한 길이(총 샘플 수)와 시작 위치 보정값은 소리 표에 옮긴다. 컨버터가 소리마다 원본 디코딩 해시 = 묶음 디코딩 해시를 확인하고, 원본 파일 해시를 보고서에 남긴다.
- **같은 소리는 해시로 찾아 한 번만** 담는다(곡 안).
- **로딩**: 소리 구역을 한 번에 순서대로 읽고 병렬 디코딩 → 메모리 상주(곡 단위로 올리고 해제).
- **실측 (Python + libsndfile, 16스레드 — 엔진 값의 상한으로 봄)**:

  | 곡 | 소리 | 압축 크기 | 디코딩 1스레드 / 16스레드 | 메모리 16비트 / f32 | PCM 캐시 읽기 16비트 / f32 |
  |---|---|---|---|---|---|
  | DJMAX D2 (Vorbis) | 358개 | 5.2 MB | 416 / 172 ms | 34 / 69 MB | 19 / 31 ms |
  | DJMAX 최대 곡 (Vorbis, 소리 길이 합 909초) | 1,465개 | 24.3 MB | 1,922 / 760 ms | 160 / 321 MB | 63 / 162 ms |
  | IIDX ANEMONE (FLAC 16비트로 바꾼 것) | 1,295개 | 37.8 MB | 386 / 226 ms | 82 / 163 MB | 34 / 68 ms |

  - **메모리 형식 = 16비트 정수** (결정 초안): Vorbis·FLAC 16비트 원본은 16비트로 충분하고 메모리가 절반. 원본이 24비트·실수인 소리(소수)만 f32. 믹서는 섞을 때 실수로 바꾼다.
  - **디코딩 캐시 = CP3에서는 두지 않음** (결정 초안): 최악의 곡도 1초 안. 엔진(Rust)에서 다시 재고, 넘으면 그때 캐시를 붙인다 (캐시 읽기는 디코딩의 3~5배 빠름).

### 4-2. Track 묶음 파일의 배치

```
[색인: 구역 위치·크기·해시]
[정보 · 태그 · 기준 스크롤 속도]      ← 라이브러리 색인 갱신용
[차분들 (실행 형식)] [시간 지도] [스크롤 지도]
[소리 표: 코덱 · 샘플레이트 · 채널 · 샘플 수 · 시작 보정 · 이득 · 데이터 위치]
[공유 디코딩 표 (Vorbis 설정 머리)]
[소리 데이터 (Vorbis 패킷 · FLAC 프레임, 빈틈없이)]
[작성 형식 원본 (텍스트) — 플레이 때 읽지 않음]
```

실측(낱개 파일의 숨은 낭비): 디스크 4 KB 칸 빈자리 2~19%, Ogg 머리 반복 4~32%. 예: DJMAX D2는 낱개로 디스크 약 5.9 MB → 묶음 약 3.1 MB (계산).

## 5. 컨버터 (변환기)

| 원본 | 읽는 것 | 근거 |
|---|---|---|
| IIDX | `.1` 채보(ms 시각) + 곡 DB + `.2dx`/`.s3p` 소리 묶음 | `cp2/tools/adapt_iidx.py`, `cp0/bms/converter/tools/iidx2bms.py` |
| DJMAX | 복호화한 원본 채보(`.bytes`, tick) + 원본 Ogg | `cp2/tools/adapt_djmax.py`, `cp0/DJMAX_chart_format.md` (비공개 데이터, 로컬 전용) |
| BMS / BMSON | 원본 텍스트·JSON + 소리 파일 | `cp2/tools/adapt_bms.py` (#RANDOM은 변형으로) |

- **원본에서 직접** 변환한다 (BMS를 거쳐 가지 않음 — 변환이 타이밍을 오염시킴).
- **원본 시각을 그대로 보존한다 (격자에 맞추지 않음).** BMS 변환의 시각 오차는 BMS가 시각을 "마디 + 정해진 분할 칸 + BPM"으로만 적을 수 있어, 원본 시각(IIDX ms, DJMAX tick)을 가장 가까운 칸에 맞추면서 생겼다(IIDX 변환의 약 11% 소리가 1 ms 차이, CP2 대조). 우리 작성 형식은 노트·소리 위치를 **임의의 유리수 박** 또는 **절대 시각**으로 적을 수 있게 하고, 컴파일러는 유리수로 계산해 **마지막에 한 번만 ns로 반올림**한다. IIDX의 ms 정수는 그대로 ns가 되고, DJMAX의 tick은 템포 지도로 유리수 계산되므로 오차는 반올림 0.5 ns 이하다(CP2 어댑터가 이미 이렇게 한다). 컨버터 검증 기준은 "원본 시각과 오차 0(ns 반올림 제외)".
- 출력은 **작성 형식**(사람이 읽을 수 있음) → 컴파일러 → 묶음. 컨버터는 실행 형식을 직접 만들지 않는다.
- **변환 보고서**: 가정, 손실(쓰지 않은 볼륨·팬 등), 시각 오차, 음악 레이어로 합칠 때 차분 간 불일치.
- **검증**: 원본을 독립적으로 읽은 발음 목록과 1:1 대조(CP2 방식), 정답 렌더 비교.

## 6. 게임 (여러 레인)

- 레인 레이아웃을 읽어 판정·키음·자동재생을 레인 수에 상관없이 처리 (CP2의 1레인 코어를 N레인으로).
- 롱노트 규칙(차분 기본 + 규칙 설정), 게이지·점수, 판정 창 프리셋, 빈 누름 규칙, 노트 고르기 규칙.

- 보정 도구: 오프셋 A(소리로 맞추기), B(화면으로 맞추기).

- 개발 도구 유지: 실시간 싱크 그래프, 실행 기록, 환경 기록, 고장 주입, 봇.
