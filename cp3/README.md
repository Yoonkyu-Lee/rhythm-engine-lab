# Checkpoint 3 — 칠 수 있는 게임

> 상태: **스펙 초안 (2026-10-16)**. 결정이 필요한 곳은 ⚑로 표시.
> 앞 단계: CP1(시계·동기 부품), CP2(건반 하나 시험장 — 기록 시계로 렉에도 PERFECT 키음 = 반주, `../cp2/README.md`).
> 근거 문서: `../design/곡 데이터 형식.md`(곡 형식 구상), `../design/기록 시계 설계.md`, `../design/설정 체계.md`, CP0 분석(`../cp0/`), CP2 "CP3로 넘기는 것".
> CP4 = 보이는 게임(기어·노트·스킨·에셋 연결·시각 트랙·연출·wgpu 렌더러·프론트 설정). 그래픽 에셋이 어디로 연결되는지는 CP4 범위이고, CP3 형식에는 그 **자리만** 둔다.

## CP3가 답할 질문

> IIDX·DJMAX·BMS 곡을 **우리 형식으로 변환**해, **레인 구성을 채보가 정하는** 엔진에서 원래 게임과 같은 소리로 칠 수 있는가 (판정 규칙은 모든 원작에 우리 기본값 — IIDX식 창·게이지 — 을 쓴다) — 기록 시계의 약속(PERFECT 키음 = 반주)을 지키면서, 선곡부터 플레이 시작까지 BMS 구동기보다 압도적으로 빠르게.

그리고 CP3가 끝나면 아래가 완전히 답해져 있어야 한다.

1. **우리 리듬게임 엔진의 이름은?** ⚑
2. **엔진이 다루는 "곡" 객체는 어떻게 생겼나** — 채보, 키음이 재생되는 형식 (그래픽 연결은 CP4).
3. **그 "곡" 객체의 이름은?** ⚑
4. **채보 형식은 BMS처럼 레인이 하드코딩된 것이 아니라 매개변수로 자유롭게 만들 수 있고, 엔진이 그걸 인식하는가.**

## 1. 이름

| 대상 | 결정 (2026-10-16) | 비고 |
|---|---|---|
| 엔진 | **Unison (임시 이름)** | 문서에서만 쓴다. **코드·파일 이름·확장자·식별자에는 쓰지 않는다** (사용자 결정). 정식 이름은 나중에 정한다 ⚑ |
| 곡 객체 | **Track** | 음악 플레이어의 "트랙"처럼 오디오만이 아니라 이미지·메타데이터·가사 등을 함께 담은 객체. 우리 Track = 정보 + 음악 레이어 + 차분들 + 소리 묶음 + 그래픽 **참조** (실체는 Track 밖, 2-1) |
| 파일 확장자 | ⚑ | 엔진 정식 이름이 정해진 뒤 |

용어 규칙:
- "곡" = Track. **차분**(난이도별 채보)은 Track 안의 구성 요소다.
- "트랙"이라는 말은 이제 Track(곡 객체)에만 쓴다. 지금까지 "반주 트랙"이라 부르던 긴 자동재생 소리는 **반주 스템**(stem)으로, DJMAX 채보 형식의 "트랙"(이벤트 채널)은 **채널**로 부른다.

## 2. 곡 객체 (작성 형식 → 실행 형식)

`../design/곡 데이터 형식.md`의 구상을 바탕으로 정한다. 두 층으로 나뉜다.

채보 형식은 두 층이다. **플레이에 쓰는 것은 바이너리**(IIDX `.1`·DJMAX `.bytes`처럼 — 해석 없이 바로 읽는 고정 레코드), **사람이 쓰고 고치는 것은 텍스트**(BMS처럼 — 읽고 비교하고 버전 관리할 수 있음). 둘을 버전이 정해진 컴파일러가 잇는다.

| 층 | 누가 쓰나 | 내용 | 형태 |
|---|---|---|---|
| **작성 형식** (source) | 사람·컨버터 | 정보(manifest), 템포 맵(박 단위), 소리 테이블, **음악 레이어**(곡의 모든 소리 이벤트), **차분**(노트가 음악 이벤트를 묶음), 시각 트랙 자리(CP4) | 텍스트(TOML) + 원본 오디오 |
| **실행 형식** (compiled) | 컴파일러 | 정규 ns 시각의 소비자별 배열(자동재생·레인별 노트·화음·스크롤 지도), 디코딩이 빠른 소리 묶음, 색인 | 고정 레코드 바이너리 (CP2 `.rtc`의 확장) |

곡 객체가 가져야 할 것 (CP2·CP0 교훈 포함):

- **곡에는 곡의 진실만**: 장치 지연·사용자 보정은 넣지 않음. 곡 오프셋을 고치면 패키지 버전을 올림.
- **차분은 자기 이벤트를 전부 직접 적는다 (순수 화이트리스트, 결정 2026-10-17)**: 차분 = 자기가 내는 모든 이벤트(시각, 소리) — 노트로 치는 것과 자동재생 모두. 음악 레이어는 사람이 적지 않고 **컴파일러가 차분들의 이벤트를 모아 계산**한다(같은 (시각, 소리)는 한 번, 소리 데이터는 Track 안에서 한 번). 편입은 차분 추가일 뿐이라 기존 차분을 건드리지 않는다.
  - 이전 원칙("자동재생은 작성하지 않고 묶이지 않은 음악 이벤트로 계산" → 모든 난이도의 음악이 같음을 구조로 보장, `../design/곡 데이터 형식.md` 6-1)은 **컴파일러 검사로 바뀐다**: 차분 사이에 소리가 다른 이벤트를 변환 보고서에 적는다. (IIDX는 77% 곡에서 차분 간 소리 합계가 완전히 같음, 확인 — 나머지 23%와 BMS는 원래 다르다.)
- **암묵 규칙을 명시 필드로**: 빈 레인 소리, 롱노트 규칙, 같은 소리 재트리거 정책, 변형(#RANDOM 대체, 선택 결과는 리플레이에 기록).
- **명시 필드**: 기준 BPM(하이스피드 기준), 여러 값 태그(팩·출처·콜라보), 레인 레이아웃(아래 3), UTF-8 고정, 시간 원점("반주 첫 샘플 = 0").
- **출처**: 변환으로 만들었으면 원본 형식·원본 해시·컨버터 버전, 변환 보고서.

### 2-1. 그래픽 자리 (결정, 2026-10-16)

그래픽 실체는 Track 묶음에 넣지 않고, **쓰임새별로 따로 둔 뒤 Track이 참조**한다. IIDX·DJMAX도 곡의 그래픽을 소리·채보 묶음과 다른 곳에 모아 두고 곡 ID·이름으로 잇는다 (확인: IIDX `sound/` 44 GB · `movie/` 81 GB · `graphic/NNNNN.ifs` 410곡 · 썸네일 폴더, DJMAX 키음 묶음 · DLC 단위 영상 팩 44개 · 곡 그림 공용 번들 · 미리듣기 번들 상주).

| 자리 | 담는 것 | 읽는 때 | 형태 |
|---|---|---|---|
| **Track 묶음** | 그래픽 **참조 표**: 미디어 해시, 종류, 역할, 곡 시각과의 대응(영상 시작 위치 등). 시각 트랙 자리 | 곡 로딩 | 4-2의 한 구역 |
| **미디어 저장소** (라이브러리 단위) | BGA 영상 | 플레이 중 **스트리밍** | 평범한 영상 파일 그대로, **내용 해시가 이름**. 여러 Track이 같은 영상을 공유(공용 BGA). 배포는 Track과 다른 팩 단위 |
| **Track 그래픽 묶음** (Track마다, 선택) | 채보 시각에 맞춰 바뀌는 그림: BMS 이미지 BGA, IIDX 곡 전용 레이어 그래픽 | 곡 로딩 (스트리밍 아님) | 형식은 CP4. CP3는 자리와 참조만 |
| **선곡 화면 자원** (라이브러리 색인 옆) | 썸네일 · 곡 그림 | 선곡 화면 (부팅 때, 또는 화면에 보일 때) | 라이브러리 단위로 모은 그림 묶음. 곡 묶음을 열지 않음 |

- 따로 두는 이유: 선곡 화면 자원은 **선곡 때 곡 묶음을 열지 않기 위해**, 영상은 **스트리밍 · 여러 곡의 공유 · 배포 단위 · 크기**(IIDX는 영상이 소리의 약 2배) 때문이다. Track 묶음은 빠른 로딩을 위해 작게 유지한다.
- **실체가 없어도 플레이할 수 있다.** 참조만 있고 미디어가 없으면(영상 팩을 받지 않음 등) 그리지 않고, 선곡 화면에 표시만 한다.
- 참조는 내용 해시로 하므로 같은 영상을 두 번 담지 않고, 영상이 바뀌면 해시가 바뀐다.
- CP3에서 할 일: Track 묶음의 참조 표, 미디어 저장소·선곡 화면 자원의 경로 규칙, 컨버터가 원본 그래픽을 찾아 참조를 채우고 실체를 옮기는 것까지. **영상 변환(재인코딩 여부) · 그림 묶음 형식 · 그리기는 CP4.**

## 3. 레인 모델 — 채보가 정하는 레인

BMS는 채널 번호가 곧 레인(11~19 = 1P 건반)이고, 키 모드는 쓰인 채널로 추정한다. Qwilight는 그 추정 때문에 순수 10K를 못 만든다(`#4K`·`#6K`만 헤더 인식, CP0 DJMAX 변환에서 확인). 우리 형식은 **차분이 자기 레인 구성을 선언**한다.

```toml
# 차분 안: 레인 레이아웃 선언 (예: DJMAX 6B)
[layout]
name = "6B"                    # 표시·키 배치 저장의 열쇠
[[layout.lane]]  id = "L1" ; role = "key"
[[layout.lane]]  id = "L2" ; role = "key"
... (L3~L6)
[[layout.lane]]  id = "SL" ; role = "side"     # 사이드 트랙
[[layout.lane]]  id = "SR" ; role = "side"
[[layout.group]] id = "main"; lanes = ["L1","L2","L3","L4","L5","L6"]   # 변형(랜덤 등)이 섞는 단위

[[notes]]
at = "12:0"; lane = "L3"; plays = ["m120"]
```

- **레인 = 이름 붙은 입력 채널.** 수·이름·역할(key / scratch / side / trigger / pedal …)을 차분이 정한다. 엔진에 "7K" 같은 고정 모드가 없다 — 프리셋 레이아웃(IIDX SP 7+1, DP 14+2, DJMAX 4B~8B, BMS 5K·7K·9K …)은 편의일 뿐.
- **레인 묶음(group)**: 랜덤·미러 같은 변형이 어느 레인끼리 섞는지, 1P/2P가 무엇인지.
- **키 배치**는 레이아웃 이름별로 저장: 레인 → 물리 입력(여러 개 가능).
- **화면 배치**(레인이 화면 어디에 어떤 모양으로 — DJMAX 사이드·트리거처럼 공간을 공유하는 표기 포함)는 CP4. CP3 단순 화면은 레인을 선언 순서대로 같은 폭으로 그린다.
- **노트 고르기 규칙**(같은 레인 연타·겹친 창)은 레인 모델 위의 엔진 규칙으로 명시하고, 판정과 키음이 같은 함수를 쓴다 (CP2).

## 3-1. 변속과 스크롤 — 시간과 화면 위치를 분리한다

**배운 것 (CP0 0-7·0-8·0-9, 정적 분석)**

| | 노트 간격(화면) | 화면 속도 | 정지 | 기준 BPM (사용자 속도를 맞추는 값) |
|---|---|---|---|---|
| IIDX | 박 위치 비례 | 현재 BPM(**정수 반올림**) × HS | `.1`에 정지 이벤트 없음 (BPM 최소 3) | FHS: HS를 계산하는 순간의 현재 BPM (곡 시작 = 시작 BPM) |
| DJMAX | tick 위치 비례 | 현재 템포 ÷ **곡 정보 BPM** × 배속 | 스크롤 이벤트 없음 (낮은 템포로 대신) | 곡 정보 BPM (정수, 곡마다 정해 둠) |
| Qwilight (BMS) | 마디 위치 비례 | BPM × SCROLL ÷ 기준 BPM × 설정값 | STOP = BPM 0 구간, 음수 BPM = 역스크롤, #SPEED 미지원 | 사용자 전역 옵션 (기본: 가장 오래 유지된 BPM) |

- 세 게임 모두 **스크롤이 템포에 묶여 있다**(화면 위치 = 템포를 시간에 대해 적분). 변속 비율은 같게 보인다.
- 다른 것은 **기준 BPM**이다. DJMAX → BMS 변환에서 변속 연출이 달라진 원인이 이것이다: BLACK SWAN은 DJMAX 기준 174, Qwilight 기준 116 → Qwilight에서 곡 전체가 1.5배 빠름 (기준이 다른 곡 13곡, 체감 0.83–1.5배). BMS에는 기준 필드가 없어 변환으로는 못 맞춘다.
- 세부 차이도 연출을 바꾼다: IIDX는 BPM을 **정수로 반올림**해 스크롤한다 (叙情의 채보 BPM 179.94 → 180). BMS 마디·STOP 단위로 옮기면 반올림·격자 오차가 생긴다.

**Unison의 방식 (결정, 2026-10-16)**

1. **시간 지도와 스크롤 지도를 따로 둔다.**
   - 시간 지도(박 → ns): 판정·소리가 쓰는 진실. 원본 시각을 그대로 (IIDX는 ms, DJMAX는 tick + 템포, BMS는 마디·BPM·STOP).
   - 스크롤 지도(곡 시각 → 화면 위치): 구간마다 (시작 시각, 시작 위치, 속도). 속도 0 = 정지, 음수 = 역스크롤, 위치 불연속 = 순간 이동. **템포에서 자동 계산되는 기본값이 있지만, 채보가 따로 적을 수 있다**(osu!의 SV처럼 템포와 무관한 속도 변화 가능).
2. **컨버터가 원작의 스크롤 규칙을 그대로 계산해 스크롤 지도로 적는다.** IIDX는 정수 반올림 BPM 적분, DJMAX는 tick 비례 ÷ 곡 정보 BPM(tick/마디 384 곡 보정 포함), BMS는 BPM × SCROLL 적분 + STOP 정지 + 음수 BPM 역스크롤(+ #SPEED는 beatoraja 의미로).
3. **기준 스크롤 속도를 차분의 명시 필드로 둔다** (소수 허용, 정수로 자르지 않음). 원작의 값을 그대로: IIDX = 시작 BPM, DJMAX = 곡 정보 BPM, BMS = 가져오기 보고서에 후보(시작·최빈·최고·최저)를 적고 기본은 최빈.
4. **사용자 설정은 노출 시간(ms)** — 기준 속도 구간에서 노트가 보이는 시간. 엔진이 속도를 연속값으로 계산한다 (속도 = 보이는 길이 ÷ 노출 시간). 녹숫자·배속 같은 원작 표시는 환산 표시로만.
   - **커버를 움직일 때 두 방식 중 고른다**:
     - **노출 유지**(기본): 커버를 내려 보이는 길이가 줄면 속도도 같은 비율로 줄여, 노트가 나타나서 판정선에 닿기까지의 시간이 그대로다. 노트는 더 낮은 곳에서 나타나 더 천천히 내려오고 화면에서 더 촘촘해 보인다. (IIDX FHS의 동작과 같음)
     - **속도 유지**: 속도는 그대로, 보이는 길이만 줄어 노출 시간이 짧아진다. (IIDX 클래식 HS·DJMAX에 커버를 단 것과 같음)
5. **검증**: 표본 셋(IIDX op.31 「叙情」 — 템포 이벤트 37개·BPM 100~350·3/4박 / DJMAX BLACK SWAN — 116↔174, 곡 정보 BPM 174 / BMS Aery Aleph-0 — BPM 변화 171회(0.24~65535.9999)·STOP 2,553회·마디 길이 변경 276회)에서, 원작의 노트 위치 식으로 계산한 위치 ↔ Unison 스크롤 지도로 계산한 위치를 노트마다 비교해 일치(오차 한도 안)를 확인한다. 화면 없이 숫자로 비교할 수 있다.

## 4. 빠른 파일 시스템 ⚑

BMS 구동기는 곡 폴더의 낱개 파일(채보 텍스트·소리 수백 개)을 선곡·로딩 때마다 날로 읽어서 프레임 드롭이 크다. 우리는 **개방성을 내주고 읽기 속도를 얻는다**.

| 구성 | 내용 | 얻는 것 |
|---|---|---|
| **곡 묶음 파일** (곡 하나 = 파일 하나) | 앞부분에 고정 크기 색인(구역 위치표), 그 뒤 정보·차분들(실행 형식)·소리 묶음·**작성 형식 원본**(결정 2026-10-16: 배포 묶음에 포함) | 파일 하나 열기 + 필요한 구역만 읽기. 원본 구역은 플레이 때 읽지 않음 — 받은 사람이 고쳐 다시 컴파일할 수 있음 |
| **선곡 화면 자원** (라이브러리 단위) | 썸네일·곡 그림을 모은 묶음 (2-1) | 선곡 화면이 곡 묶음을 열지 않고 그림을 보임 |
| **미디어 저장소** (라이브러리 단위) | BGA 영상, 내용 해시가 이름 (2-1) | 스트리밍, 여러 Track이 공유, Track과 다른 단위로 배포 |
| **라이브러리 색인** (전체 곡 = 파일 하나) | 곡마다 정보·태그·레벨·미리듣기 위치(하이라이트)·**차분별 구간 통계**(4-3)·묶음 해시 | 선곡 화면이 곡 묶음을 열지 않음. 시작 때 색인 하나만 읽음 |
| **작성 형식 → 묶음** | 컴파일러가 만들고, 원본 해시 + 컴파일러 버전이 같으면 다시 만들지 않음 | 편집은 작성 형식, 배포·플레이는 묶음 |

참고 — 원작들이 소리를 다루는 방식 (CP0 확인):
- IIDX: 곡마다 소리 묶음 하나(`.2dx` = MS-ADPCM WAV 묶음, 약 4:1 압축 / 새 곡은 `.s3p` = WMA 손실 압축 묶음, 차분별 묶음이 따로 있을 수 있음). 곡을 고르면 묶음을 통째로 읽어 디코딩.
- DJMAX: 곡마다 암호화된 묶음 하나 안에 키음 Ogg Vorbis가 낱개로 들어 있음. 곡을 시작할 때 FMOD가 메모리에서 소리마다 PCM으로 풀어 올리고(로드 때 디코딩), 곡을 나가면 해제. 로딩 화면(아이캐치)이 그 시간을 가린다.
- 둘 다 **"압축해 묶어 두고, 로딩 때 디코딩, 디코딩 결과는 남기지 않음"** = 아래 (b). 채보도 둘 다 **바이너리**(IIDX `.1`: 이벤트 8바이트 고정 레코드, ms 정수 / DJMAX `.bytes`: tick 단위 자체 바이너리)이고, 텍스트는 BMS뿐이다.

### 4-1. 소리 저장 (결정, 2026-10-16)

전체 자산 조사(BMS 4팩 약 185만 · IIDX 약 202만 · DJMAX 약 46.5만 파일)와 실측에서 정했다.

| 원본 | Track 묶음에 담는 것 | 근거 |
|---|---|---|
| Ogg Vorbis (DJMAX 전부, BMS 대부분) | **Vorbis 패킷 그대로** + 곡 안에서 공유하는 Vorbis 설정 머리 | 손실 원본을 다시 굽지 않음. 파일마다 반복되던 약 4 KB 머리(DJMAX 곡 크기의 약 30%)를 한 번만 담음 |
| FLAC | **그대로** | 무손실 |
| WAV PCM 정수 8·16·24비트 | **FLAC** (비트 깊이·샘플레이트 그대로) | 무손실, 크기 약 절반 |
| WAV 32비트 실수 | **FLAC 24비트** (모든 값을 24비트 간격으로 양자화하는 작은 손실 — 손실 경로) | FLAC은 실수를 못 담음, 대상 소수 |
| MS-ADPCM (IIDX 옛 곡) | **원본 ADPCM 블록 그대로** (결정, 2026-10-16: 엔진 디코더 셋째) | 정수 연산 디코더라 결정적·무손실. FLAC으로 풀면 2.4배(IIDX ADPCM 22.3 GB → 약 53 GB) — 그대로 두면 약 31 GB 절약 |
| WMA (IIDX 새 곡), MP3, AAC | **디코딩 → FLAC 16비트**. ±1.0을 넘는 소리만 볼륨을 낮춰 저장하고 이득을 소리 표에 기록. **WMA는 ffmpeg 디코딩 결과의 앞 3샘플을 잘라 냄** | 실측: 원본의 1.3배. 앞쪽 지연: 같은 소리가 ADPCM·WMA 양쪽에 있는 유일한 곡(08520 HYPER BOUNDARY GATE)에서 내용으로 짝지은 189쌍 전부가 WMA +3샘플(0.07 ms) |
| 3채널 이상 | 스테레오로 다운믹스 (⚑ 다운믹스 행렬·채널 배치 해석·적용 순서를 정해야 함 — 손실 경로) | 보고서에 기록 |
| 판정 불가 | 채보가 참조하지 않으면 건너뜀. **참조하면 그 Track을 '불완전 변환'으로 표시** | 보고서에 기록 |

- **샘플레이트는 원본 그대로** 담고, 로딩 때 출력 장치 레이트로 리샘플링한다. ⚑ **CP2 리샘플러는 그대로는 부족하다**: 위상 수 `L = 출력 / gcd(입력, 출력)`이 8192를 넘으면 거부하는데, 자산에 있는 30,697 Hz(→44,100은 L = 44,100) 같은 비표준 레이트가 걸린다. 필요한 위상만 계수를 만드는 방식 등으로 고쳐야 한다. 시작 보정값이 어느 레이트의 샘플 단위인지, 트림 전후 어느 단계에서 적용하는지도 고정한다.
- **엔진 디코더는 Vorbis, FLAC, MS-ADPCM 셋** (결정, 2026-10-16). 기준: 엔진이 디코딩하는 형식은 단순하고 결정적인 것만. 복잡하거나 앞쪽 지연이 애매한 손실 코덱(WMA·MP3·AAC)은 변환 때 한 번 풀어 FLAC으로 고정한다 — WMA를 엔진에 넣으면 큰 의존성(ffmpeg 또는 Windows 디코더)과 실수 연산 결정성 문제를 지고 얻는 것은 6.6 GB뿐. IIDX 크기(계산): 디코더 2개 약 82 GB, 3개 약 51 GB, 4개 약 45 GB.
- **보존 계약은 경로마다 다르다** (2026-10-16 외부 검토 반영):
  - **무손실 경로** — Vorbis 패킷 보존, FLAC 그대로, WAV 정수 → FLAC, MS-ADPCM 블록 보존: 기준 디코더로 디코딩한 PCM의 **해시가 같아야** 통과.
  - **손실 경로** — WMA·MP3·AAC → FLAC16, 실수 WAV → FLAC24, 다운믹스, ±1 넘침 감쇠: 해시 대신 **최대 오차·RMS 오차·클리핑 수**를 보고서에 기록.
  - 메모리 형식은 소리마다 손실 없는 쪽을 고르므로 메모리에서 다시 양자화하지 않는다 (4-3).
  - 기준 디코더(Vorbis·FLAC·ADPCM)는 종류·버전을 고정하고 해시와 함께 기록한다.
- **(이전 문장, 위 계약으로 대체) 원본 보존 기준 = 디코딩한 소리가 샘플까지 같음.** Ogg 그릇 정보(페이지 구조·CRC·주석 머리·파일 시각)는 버린다. 정확한 길이(총 샘플 수)와 시작 위치 보정값은 소리 표에 옮긴다. 컨버터가 소리마다 원본 디코딩 해시 = 묶음 디코딩 해시를 확인하고, 원본 파일 해시를 보고서에 남긴다.
- **같은 소리는 해시로 찾아 데이터를 한 번만** 담는다(곡 안). **논리 소리 ID는 그대로 두고 데이터 위치만 공유**한다 — 같은 소리 재트리거 끊기(cut_same)는 소리 ID로 판단하므로, ID를 합치면 원래 함께 울리던 소리끼리 끊긴다(외부 검토 지적, CP2 `Mixer::admit`). 동일성 판정에는 레이트·채널·트림·이득도 포함.
- **로딩**: 소리 구역을 한 번에 순서대로 읽고 병렬 디코딩 → 메모리 상주(곡 단위로 올리고 해제).
- **실측 (Python + libsndfile, 16스레드 — 엔진 값의 상한으로 봄)**:

  | 곡 | 소리 | 압축 크기 | 디코딩 1스레드 / 16스레드 | 메모리 16비트 / f32 | PCM 캐시 읽기 16비트 / f32 |
  |---|---|---|---|---|---|
  | DJMAX D2 (Vorbis) | 358개 | 5.2 MB | 416 / 172 ms | 34 / 69 MB | 19 / 31 ms |
  | DJMAX 최대 곡 (Vorbis, 소리 길이 합 909초) | 1,465개 | 24.3 MB | 1,922 / 760 ms | 160 / 321 MB | 63 / 162 ms |
  | IIDX ANEMONE (FLAC 16비트로 바꾼 것) | 1,295개 | 37.8 MB | 386 / 226 ms | 82 / 163 MB | 34 / 68 ms |

  - **메모리 형식 = 소리마다 16비트 정수 또는 f32** (손실 없는 쪽), 디코딩 순서·캐시·곡 전환은 4-3 (선곡 화면 채보 미리보기를 고려해 결정).

### 4-2. Track 묶음 파일의 배치

```
[색인: 구역 위치·크기·해시]
[정보 · 태그 · 기준 스크롤 속도]      ← 라이브러리 색인 갱신용
[차분들 (실행 형식)] [시간 지도] [스크롤 지도]
[그래픽 참조 표: 미디어 해시 · 종류 · 역할 · 곡 시각 대응]   ← 실체는 Track 밖 (2-1)
[소리 표: 코덱 · 샘플레이트 · 채널 · 샘플 수 · 시작 보정 · 이득 · 데이터 위치]
[공유 디코딩 표 (Vorbis 설정 머리)]
[소리 데이터 (Vorbis 패킷 · FLAC 프레임, 빈틈없이)]
[작성 형식 원본 (텍스트) — 플레이 때 읽지 않음]
```

실측(낱개 파일의 숨은 낭비): 디스크 4 KB 칸 빈자리 2~19%, Ogg 머리 반복 4~32%. 예: DJMAX D2는 낱개로 디스크 약 5.9 MB → 묶음 약 3.1 MB (계산).

### 4-3. 소리를 메모리에 올리고 버리기 (결정, 2026-10-16)

배경 요구사항(사용자): **선곡 화면 채보 미리보기.** 진행 바에서 아무 구간을 고르면 그 구간의 채보가 **키음까지 전부 자동 연주**로 재생되고, 구간별 노트 밀도 같은 통계가 함께 보인다. 노트는 그리지 않는다. 기준으로 Qwilight를 분석했다 (`../cp0/Qwilight_preview.md`: 실제 엔진을 자동 모드로 돌림, 정의된 소리 전부를 완전 디코딩한 뒤 시작, 탐색은 빨리 감기 + 중간부터 재생, 곡을 바꾸면 즉시 해제, 곡 사이 캐시 없음, 플레이 진입 때 디코딩 결과 이관).

**범위**: 미리보기 **화면**(진행 바·통계 그래프·클릭 탐색)은 CP4. 아래 **바탕**(소리 저장소·디코딩 순서·정확한 탐색·플레이 인계·색인 통계)은 CP3에서 만들고, CP3 단순 선곡 화면에서 키 조작으로 재생·탐색을 검증한다.

1. **메모리 형식 = 소리마다 손실 없는 쪽** (결정 2026-10-16).
   - **16비트 정수**: 디코딩 결과가 16비트 정수이고(FLAC 16비트 — WAV 16비트, MS-ADPCM, WMA 변환분 포함) **원본 레이트 = 장치 레이트**라 리샘플링이 필요 없는 소리. 값을 그대로 담으므로 손실이 없다.
   - **f32**: 그 밖의 모든 소리 — Vorbis(디코더 출력이 실수), 리샘플링한 소리(결과가 정수 사이 값), 24비트·실수 원본.
   - 소리 슬롯마다 형식 표시를 두고, 믹서는 보이스마다 읽는 방식을 고른다(섞기는 어느 쪽이든 실수). 샘플마다 분기하지 않는다.
   - 효과: 장치를 44.1 kHz로 열면 IIDX 곡 전부와 BMS WAV 16비트 대부분이 절반 크기 (예: ANEMONE 163 → 82 MB). DJMAX(Vorbis)는 그대로 f32 (최대 곡 321 MB).
   - 참고(`../cp0/REPORT.md` 0-11): IIDX·DJMAX·Qwilight·beatoraja는 대부분 16비트로 상주한다. DJMAX의 16비트는 FMOD가 Vorbis 실수 출력을 반올림한 것이다.
   - 16비트로 다시 깎는 일반 대비책은 두지 않는다. 메모리가 모자라면 9번(메모리 예산)으로 다룬다.
2. **소리 저장소 = Track 단위.**
   - 키는 (Track 묶음 해시, 장치 샘플레이트, 디코더·리샘플러 버전)이다. 리샘플링은 디코딩할 때 **원본에서** 한 번 한다(다른 레이트용으로 만든 PCM을 다시 변환하지 않는다).
   - 슬롯 상태: 미준비 · 작업 중 · 준비 · 실패. 작업 스레드가 다 만든 뒤에 게시하고, 믹서는 준비된 슬롯만 읽는다.
   - Track 안의 차분들은 소리를 공유하므로, 같은 곡의 차분을 바꾸면 다시 디코딩하지 않는다. 다른 차분에만 있는 소리만 더 올린다. 이 합집합에도 9번 예산을 적용한다(차분을 오가며 계속 커지지 않게).
   - 고른 차분이 쓰는 소리만 올린다(반주·자동재생·변형 결과 포함, 플레이에서는 빈 누름 소리도). Qwilight처럼 쓰지 않는 소리까지 올리지 않는다.
   - 데이터 공유와 논리 소리 ID는 분리한다(4-1, 같은 소리 끊기는 ID로 판단).
   - 해제: 믹서가 이전 저장소를 더 이상 읽지 않음을 확인한 뒤 작업 스레드에서 해제한다.
3. **디코딩 순서 = 들을 곳부터, 준비되기 전에는 소리를 내지 않는다.**
   - 준비 집합 = **시작 지점에 이미 울리고 있어야 하는 소리 + 앞으로 W초 안에 시작하는 소리.** 시작 지점 전에 시작한 긴 소리(반주 stem, 긴 키음)도 들어간다.
   - 준비 집합이 **전부** 준비된 뒤에 재생을 시작한다.
   - 나머지는 **현재 재생 위치 이후 다음에 쓰이는 시각** 순으로 채운다(곡 전체의 처음 사용 시각 순이면 후반 탐색 때 지나간 구간을 먼저 채우게 된다). 재생하는 동안에도 앞으로 W초 범위를 계속 갱신한다.
   - **준비 부족은 건너뛰지 않는다.** 앞으로 W초 범위에 준비 안 된 소리가 생기면 잠깐 멈춰(버퍼링) 채운 뒤, 장치 시계는 그대로 두고 **콘텐츠 원점을 다시 잡아 같은 위치에서** 재개한다. 이미 지나간 짧은 키음을 뒤늦게 처음부터 내지 않는다.
     - 이유(외부 검토 #3): 빠진 소리는 무음 하나로 끝나지 않는다. 그 소리가 앞 소리를 끊었어야 하면 앞 소리가 더 길게 울리고, 보이스 예산을 차지했어야 하면 원래 밀려날 소리가 살아남는다.
   - 그래도 믹서가 준비 안 된 소리를 만나면(비상): **보이스 상태(끊기·예산)는 그대로 계산하고 출력만 비운 뒤** 기록한다. 그런 실행은 "미리보기 = PERFECT 플레이"로 세지 않는다.
   - **플레이는 전부 준비돼야 시작한다.**
   - 긴 소리의 부분 디코딩(시작 지점 근처 블록부터): 처음에는 하지 않는다(전체 디코딩으로 정확성 기준을 먼저 세운다). 측정에서 긴 소리가 첫 소리를 좌우하면 추가한다. 조건: 장치 레이트 기준 0.5 ~ 1초 블록, 원래 소리의 절대 샘플 위치 기준으로 리샘플링(블록 경계에 0을 넣지 않고 필터에 필요한 앞뒤 입력 확보), Vorbis는 탐색 색인과 디코더 상태 복원 설계 필요, **전체 디코딩 결과와 그 구간 해시가 같아야** 채택.
   - ⚑ W와 디바운스는 측정으로 정한다. 출발점 W = 2초, 곡 선택 디바운스 = 150 ms. 비교: W 0.5 · 1 · 2 · 4초 × 디바운스 75 · 150 · 250 ms, 짧은 소리 다수 · 긴 stem 다수 · 곡 후반 탐색 · 연속 드래그로 나눠 **누락 없는 첫 출력까지 시간**(p50 · p95 · p99), 버퍼링 횟수·시간, 취소로 버린 CPU 시간·읽기량·최고 메모리.
   - 진행 바 클릭은 디바운스 없이 바로 처리한다. 드래그 중에는 최신 위치만 남기고 손을 놓으면 실행한다.
4. **취소**
   - 디코딩 작업은 소리 하나 단위로 쪼개고, **긴 소리는 디코더 블록·리샘플링 조각 사이에서도** 취소를 확인한다.
   - 요청마다 **세대 번호**를 붙인다. 취소된 뒤 늦게 끝난 작업은 세대가 다르면 게시하지 않는다(새 저장소를 오염시키지 않음).
   - 커서가 머문 뒤에만 시작한다.
5. **곡 사이 캐시는 두지 않는다.**
   - 곡을 바꾸면 이전 저장소를 해제한다. 최근 곡을 남기면 메모리가 두 배가 된다. OS 파일 캐시는 별개다.
   - A → B → A로 돌아오는 지연이 실제로 문제일 때만 크기 제한이 있는 캐시를 검토한다 (3-5 측정 항목).
6. **탐색은 플레이와 같은 소리로.**
   - 판정이 필요 없으므로 목표 시각까지 소리를 섞지 않고 **보이스 배정만 다시 돌린다**(같은 소리 끊기, 보이스 예산 포함). 이 상태 전이는 **플레이와 탐색이 같은 코드**를 쓴다.
   - **먼저 고칠 것 (확인됨, 외부 검토 #3):** CP2 `Mixer::admit`은 보이스 수(`voices.len()`)로 예산을 검사하는데, 블록 안에서 이미 끝났거나 끊긴 보이스는 `fill` 끝에서야 빠진다. 그래서 **예산이 찬 상황에서만** 블록 크기에 따라 새 소리가 들어가기도 하고 거부되기도 한다(CP2 실행 53개 중 넘침은 bms 프로필 두 번뿐, 우리 방식 결론에는 영향 없음). → 보이스 점유를 **이벤트 시각 기준**으로 판단하고, 이미 끝난 보이스의 남은 출력 구간은 그대로 섞는다.
   - 같은 시각 이벤트의 순서와 보이스 합산 순서를 고정한다. 목표 시각 이전 이벤트는 모두 처리하고, 목표 시각의 이벤트는 정확히 한 번 처리한다.
   - 중간부터 시작하는 위치 = **`목표 프레임 − 이벤트 시작 프레임`** (시간 차이를 따로 프레임으로 바꾸면 반올림 때문에 1프레임 어긋날 수 있다).
   - 과거 이벤트를 "늦게 들어온 요청"으로 믹서에 넣지 않는다(키음의 늦은 소리 정책이 "처음부터"라 다시 처음부터 난다). 복원한 상태를 미래 출력 프레임에 한 번에 설치한다.
   - 비용: 단순 구현은 이전 이벤트 수 × 보이스 예산. 정렬된 이벤트 커서로 훑고, 측정 후 필요하면 2 ~ 5초 간격 상태 스냅샷을 둔다. (CP2 `pending`의 최솟값 선형 탐색 + `remove`는 이벤트를 미리 다 넣으면 이차 비용이라 쓰지 않는다.)
   - 키음은 PERFECT 자리(노트 시각)에 둔다. 우리 엔진에서는 PERFECT 키음 = 반주이므로, 미리보기 = PERFECT 플레이의 소리다.
   - 탐색 순간의 짧은 페이드를 넣는다면 출력 끝단의 효과로 따로 두고, 검증은 효과를 뺀 원시 렌더로 한다. (CP4 이후 리버브 같은 상태 있는 효과가 생기면 효과 상태도 복원해야 한다.)
7. **플레이 인계.**
   - **소리 데이터만 넘기고 실행 상태(보이스·대기열·재생 위치·D)는 넘기지 않는다.**
   - 순서: ① 플레이 장치를 열어 실제 형식 확정 → ② 키(2번)가 맞는 준비된 PCM 재사용 → ③ 모자라거나 레이트가 다른 소리 준비 → ④ 새 경로의 시계와 D 확정, 플레이 원점 설정 → ⑤ 전부 준비되면 시작.
   - Qwilight는 이관할 때 같은 곡인지 검사하지 않는다(`../cp0/Qwilight_preview.md`).
   - **출력 스트림 (추천안, ⚑ 측정 후 확정)**: 선곡 화면은 공유 모드로 연다. 플레이도 공유 모드이고 장치·형식이 같으면 스트림을 유지한다. 플레이가 배타·ASIO면 진입 때 다시 열고, 선곡으로 돌아오면 공유 모드로 돌아온다. "선곡부터 플레이 경로 그대로"는 별도 선택지로 둔다.
     - 측정: 공유 → 공유 · 배타 · ASIO 전환별 여는 시간, 플레이 진입 전체 시간, PCM 재사용률, 최고 메모리, D 재측정값. 장치 제거 · 레이트 변경 · 열기 실패도 포함. ASIO에서 다른 프로그램 소리가 막히는 범위는 드라이버마다 확인한다.
8. **구간별 통계는 컴파일 때 라이브러리 색인에.**
   - **250 ms 고정 시간 칸**으로 저장하고, 기본 표시는 1초로 합친다. 마디는 경계 정보로 따로 둔다(마디 칸은 BPM·STOP·변박 곡에서 진행 바 위 밀도를 왜곡한다).
   - 첫 통계:

     | 통계 | 정의 |
     |---|---|
     | 노트 밀도 | 칸 안의 입력 노트 시작 수 ÷ 실제 칸 길이 |
     | 동시치기 | 같은 시각 노트 수의 분포·최댓값 |
     | 롱노트 | 시작 수, 누르고 있는 시간의 합, 동시에 누르는 최대 수 |
     | 레인·역할 | 레인별 원시 집계 + 선언된 묶음·역할(건반·스크래치·사이드 등)별 합 (겹치는 묶음의 합을 전체로 취급하지 않음) |
     | 하이라이트 | 작성자 지정 우선, 없으면 일정 길이의 가장 밀집한 구간을 결정적으로 고름 |

   - 노트 하나가 소리 여럿을 내도 노트 수는 1이다. 롱노트 끝 판정·틱 판정은 시작 수와 섞지 않는다.
   - 최대 NPS는 고정 칸의 최댓값이 아니라 **이동하는 1초 창**으로 따로 계산한다.
   - 무효화: 차분 해시 · 변형 · 통계 알고리즘 버전이 바뀌면 다시 계산한다.
   - ⚑ 저장 간격(0.1 · 0.25 · 0.5 · 1초)은 색인 크기·첫 화면 로딩·짧은 밀집 구간 보존을 비교해 확정한다. 선곡 화면이 곡 묶음을 열지 않아도 바로 보인다.
9. **메모리 예산 (할당 전 검사).**
   - 최종 PCM 크기는 소리 표만으로 미리 계산한다: Σ(장치 레이트로 바꾼 뒤 프레임 수 × 채널 × 형식 바이트(2 또는 4)).
   - 여기에 압축 입력, 디코더 작업 버퍼, 리샘플링 입출력 중복, 이전 저장소, 취소 중 작업을 더한 **최고 사용량**을 예산과 비교한다. 소리마다 붙는 고정 부가분도 넣는다(FMOD는 Ogg 소리마다 약 150 KB, `../cp0/REPORT.md` 0-11).
   - 모자라면: ① 이전 곡 참조·취소 작업 회수 후 올리기 → ② 같은 Track의 이전 차분만 쓰던 소리 해제 → ③ (검증된 경우) 긴 소리 부분 디코딩 → ④ 그래도 플레이 전체를 준비할 수 없으면 **시작을 명시적으로 막는다**(초대형 곡 플레이는 별도의 스트리밍 계약이 필요).
   - ⚑ 예산값: BMS를 큰 곡 · 최대 소리 수 · 최장 소리 · 차분 합집합 · 최대 장치 레이트로 나눠 Rust 로더로 재고 정한다(최종 PCM · 프로세스 커밋 · 작업 집합 · 임시 버퍼 · 취소 회수 시간). 650 MB는 비교용 표본값일 뿐 상한이 아니다.

**4-3 완료 조건** (3-5에서 검증, 외부 검토 #3 추천):
1. **탐색 렌더 일치**: 처음부터 PERFECT로 렌더해 잘라낸 구간 = 탐색 후 렌더한 구간. 작은 보이스 예산, 같은 소리 연타, 같은 시각 이벤트, 긴 꼬리, 블록 경계 직전·직후를 포함한다.
2. **준비 부족 주입**: 일부러 준비를 늦춰도 누락을 숨기지 않고, 버퍼링 후 정확한 위치에서 재개한다.
3. **메모리·취소**: 빠른 곡 전환 · 차분 순회 · 장치 변경 중에도 최고 메모리와 취소 회수 시간이 예산 안에 든다.

## 5. 컨버터 (변환기)

| 원본 | 읽는 것 | 근거 |
|---|---|---|
| IIDX | `.1` 채보(ms 시각) + 곡 DB + `.2dx`/`.s3p` 소리 묶음 | `cp2/tools/adapt_iidx.py`, `cp0/bms/converter/tools/iidx2bms.py` |
| DJMAX | 복호화한 원본 채보(`.bytes`, tick) + 원본 Ogg | `cp2/tools/adapt_djmax.py`, `cp0/DJMAX_chart_format.md` (비공개 데이터, 로컬 전용) |
| BMS / BMSON | 원본 텍스트·JSON + 소리 파일 | **`BMS_컨버터.md`** (같은 곡 판정·합치기·편입이 주 과제라 따로 계획), `cp2/tools/adapt_bms.py` |

- **BMS는 `BMS_컨버터.md`를 따른다.** 흩어진 같은 곡 폴더를 Track 하나로 합치고, 나중에 들어온 팩을 기존 Track에 편입하는 것(차분별 시간 이동·배속 변형·차분별 이벤트 목록(화이트리스트)·라이브러리 정체성 색인)은 그 문서에만 적는다.
- **원본에서 직접** 변환한다 (BMS를 거쳐 가지 않음 — 변환이 타이밍을 오염시킴).
- **원본 시각을 그대로 보존한다 (격자에 맞추지 않음).** BMS 변환의 시각 오차는 BMS가 시각을 "마디 + 정해진 분할 칸 + BPM"으로만 적을 수 있어, 원본 시각(IIDX ms, DJMAX tick)을 가장 가까운 칸에 맞추면서 생겼다(IIDX 변환의 약 11% 소리가 1 ms 차이, CP2 대조). 우리 작성 형식은 노트·소리 위치를 **임의의 유리수 박** 또는 **절대 시각**으로 적을 수 있게 하고, 컴파일러는 유리수로 계산해 **마지막에 한 번만 ns로 반올림**한다. IIDX의 ms 정수는 그대로 ns가 되고, DJMAX의 tick은 템포 지도로 유리수 계산되므로 오차는 반올림 0.5 ns 이하다(CP2 어댑터가 이미 이렇게 한다). 컨버터 검증 기준은 "원본 시각과 오차 0(ns 반올림 제외)".
- 출력은 **작성 형식**(사람이 읽을 수 있음) → 컴파일러 → 묶음. 컨버터는 실행 형식을 직접 만들지 않는다.
- **변환 보고서**: 가정, 손실(쓰지 않은 볼륨·팬 등), 시각 오차, 음악 레이어로 합칠 때 차분 간 불일치.
- **검증**: 원본을 독립적으로 읽은 발음 목록과 1:1 대조(CP2 방식), 정답 렌더 비교.

## 6. 게임 (여러 레인)

- 레인 레이아웃을 읽어 판정·키음·자동재생을 레인 수에 상관없이 처리 (CP2의 1레인 코어를 N레인으로).
- 롱노트 규칙(차분 기본), 게이지·점수, 빈 누름 규칙, 노트 고르기 규칙. **판정 창·게이지는 IIDX식 기본값 하나로 고정**하되, 엔진 안에서는 처음부터 데이터(등급별 빠름·늦음 경계 ns, 게이지 증감표)로 다룬다 — CP4의 규칙 커스텀·프리셋이 코드 수정 없이 얹히도록.
- 선곡 화면(단순): 라이브러리 색인 목록, 차분 고르기, 레이아웃별 키 배치. **채보 미리보기 바탕 검증**(4-3): 커서가 머물면 자동 연주, 키로 구간 이동, 플레이 진입 때 저장소 인계.
- 설정창(조작 가능): `../design/설정 체계.md`의 CP3 설정 — 규칙 / 장비와 몸 / 소리 / 입력 / 화면(스크롤 속도·방향) / 라이브러리 / 엔진(고급).
- 보정 도구: 오프셋 A(소리로 맞추기), B(화면으로 맞추기).
- 리플레이: 규칙·변형 시드·정책을 함께 기록.
- 개발 도구 유지: 실시간 싱크 그래프, 실행 기록, 환경 기록, 고장 주입, 봇.

## 7. 단계

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| 3-0 | 이름 결정, 곡 객체 스펙 문서 (작성 형식 + 실행 형식 + 레인 모델 + 묶음 파일) | 스펙 문서 확정, 예시 곡 하나를 손으로 작성 |
| 3-1 | 컴파일러: 작성 형식 → 실행 형식 → 묶음, 라이브러리 색인 | 같은 입력이면 비트 단위로 같은 묶음, 해시 캐시 |
| 3-2 | 컨버터 셋: IIDX, DJMAX, BMS/BMSON → 작성 형식 + 보고서 | 표본 곡들에서 원본 발음 목록과 1:1, 정답 렌더 일치 |
| 3-3 | 여러 레인 게임: 레이아웃·판정·롱노트·게이지·노트 고르기·선곡(단순) | IIDX 7+1, DJMAX 4B~8B, BMS 7K를 같은 엔진·같은 코드로 플레이, 레이아웃 하드코딩 없음 |
| 3-4 | 설정창 + 보정 도구 + 설정 저장(범위별) | 설정 체계의 CP3 설정을 화면에서 바꾸고 저장·복원, 규칙 해시가 결과에 기록 |
| 3-5 | 검증: 속도와 싱크 | 선곡 화면 열기·곡 로딩 시간 실측(같은 곡 수에서 Qwilight 대비), 미리보기 누락 없는 첫 출력까지 시간·4-3 완료 조건 셋(탐색 렌더 일치, 준비 부족 주입, 메모리·취소), 실제 여러 레인 곡으로 CP2 지표(PERFECT 키음 vs 반주, 판정·소리 불일치, 도장 − 실제 누름) |

## 8. CP3에 넣지 않는 것 (CP4)

**판정 규칙 커스텀과 프리셋 옵션 시스템** (사용자 결정 2026-10-17, Qwilight의 자유도처럼): 판정 창·게이지·롱노트 규칙·빈 누름 판정을 사용자가 바꾸고, 이름 붙은 프리셋(원작 재현 포함)으로 저장·선택한다. 설계 근거는 `../design/설정 체계.md` 1장.

기어·노트·판정선·이펙트의 모양과 스킨, 레인의 화면 배치(공간 공유 표기), 시각 트랙·BGA·연출(영상 변환·Track 그래픽 묶음 형식·그리기 — 자리와 참조는 CP3 2-1), 선곡 화면의 모양(채보 미리보기의 진행 바·구간 통계 그래프·클릭 탐색 포함 — 바탕은 CP3 4-3), 그래픽 설정(vsync·프레임 제한 등), 오디오 효과(EQ·리버브), 컨트롤러 진동, wgpu 렌더러, 세미 게임 레이어.
