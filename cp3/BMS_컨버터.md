# BMS → Track 컨버터 계획

> 작성일 2026-10-16. CP3 3-2(컨버터 셋) 중 BMS/BMSON 부분. cp3/README.md 5장은 BMS에 대해 이 문서만 참조한다.
> 1차 연구(4팩: 4K·6K·8K U_E, BMS-AERY 5K): `../design/BMS_to_Track.md`. 이 문서는 그 결론을 바탕으로 한 **계획**과, 7키 난이도표 묶음(SP Insane+)으로 한 **2차 연구**의 설계·결과(3-4, 2026-10-17)다.
> 표기: (확인) = 측정·코드로 확인, (계산) = 확인한 값에서 계산, (추정) = 해석, ⚑ = 아직 정하지 않음.

---

## 0. 왜 BMS만 따로 계획하나

| | IIDX · DJMAX | BMS |
|---|---|---|
| 곡의 정체성 | 게임 DB가 정한다 (곡 ID·이름) | **없다.** 팩·폴더를 만든 사람마다 따로 만든다 |
| 같은 곡이 여러 곳에 | 없음 | 흔하다. 4팩 폴더의 51%가 다른 폴더와 같은 곡(558곡 → 1,801 Track), SP Insane+ 폴더의 41%가 4팩 폴더와 같은 곡 (확인) |
| 관례 | 한 회사의 한 형식 | 폴더마다 다름: 시각 원점, 소리 판본(WAV 원본 / Ogg 재인코딩), 들어 있는 키음, 제목 표기, 키 수. 한 폴더에 다른 곡 채보나 같은 차분의 여러 판이 섞이기도 한다 (확인, 3-4) |
| 갱신 | 곡 추가, 기존 곡의 채보 갱신 | **팩이 계속 덧붙는다.** 이미 변환한 곡의 다른 키 수·다른 차분이 나중에 다른 팩으로 들어온다 |

그래서 BMS 컨버터의 주 과제는 파싱이 아니라 다음 셋이다.

1. **같은 정체성 판정**: 흩어진 폴더들이 같은 곡인지 정한다.
2. **합치기**: 같은 곡이면 Track 하나로 산출한다(음악 레이어 하나, 차분 여럿, 소리 한 번만).
3. **편입**: 이미 Track으로 변환된 곡에, 나중에 들어온 팩의 같은 곡 차분을 **기존 차분을 흔들지 않고** 덧붙인다.

## 1. 지금까지 정한 것

### 1-1. 사용자 결정 (2026-10-16)
- **배속 변형은 같은 Track의 차분**으로 둔다. `base = <차분>`, `time_scale = <유리수>`(BPM 비에서 정확히). 레거시 구동기에서 원하는 시간 배율로 치려고 만든 채보이므로, 그것만으로 다른 Track을 만들지 않는다.
  - 구동기는 BPM대로 시각만 바꾸고 **소리 길이·속도는 바꾸지 않는다.** `time_scale`도 소리를 늘이지 않는다(원작 동작 재현). 긴 stem이 있는 배속 변형은 원작에서도 소리가 겹치거나 비는데, 그대로 재현한다.
- **순수 화이트리스트 (2026-10-17)**: 소리는 Track 하나에 모으고, **차분마다 자기가 내는 이벤트(시각, 소리)를 전부 직접 적는다**(노트·자동재생 모두). 음악 레이어는 컴파일러가 차분들의 이벤트를 모아 계산한다. 차분마다 텍스트가 따로인 것은 BMS와 같고, 절약은 소리 데이터 공유에서 얻는다.
  - 이전안(안 씀 목록 = 블랙리스트)은 편입 때마다 기존 차분 전부를 고쳐야 하고, 빠뜨리면 기존 차분에서 새 소리가 조용히 나서 버렸다. 묶음 단위 화이트리스트(출처 묶음 + 예외)는 base 기준과 가져온 순서 의존이 생겨 버렸다.
- **차분별 시간 이동**: 차분의 원본 시각 → Track 시각의 상수(정확한 ns, 같은 소리 발음끼리 차이의 최빈값). 격자 맞춤이 아니라 덧셈이라 원본 시각이 보존된다.

### 1-2. Track 시각의 원점 — 결정 (2026-10-17): 고정 앵커 + 음수 허용 (2차 연구 3-4 Q3·Q6로 뒷받침)
- **문제**: 원점을 "모든 차분 중 가장 이른 이벤트"로 하면, 나중에 더 이른 이벤트를 가진 차분이 편입될 때 원점이 옮겨진다. 그러면 기존 차분 전부의 시각이 바뀌고, Track 해시 · 리플레이 · 기록 · 미리보기 하이라이트 · 구간 통계를 다시 계산하거나 무효화해야 한다.
  - 실측: SP Insane+를 4팩 Track에 편입할 때, 이 방식이면 편입의 6.6%(48건)에서 원점이 옮겨지고 기존 차분 123개를 다시 계산해야 한다. 검사를 끄고 더 많이 편입하면 14.1%(146건), 528개 (확인).
- **결정**: Track을 처음 만들 때 기준 차분(소리 이벤트가 가장 많은 것)의 원본 시각을 0으로 **고정하고 다시는 옮기지 않는다.** 새 차분은 자기 이동만 계산하고, 이동이 음수여도 된다.
  - 실측: 편입된 새 차분 중 이동이 음수 1.4%, Track 시각이 음수가 되는 차분 0.2% (검사 끔: 3.9%, 2.2%) (확인). 드물지만 0이 아니므로 음수 처리는 필요하다.
- **이동은 확실할 때만 적용한다** (2차 연구 추가): 이동이 0이 아닌 차분 3,755개 중 이동 후 기준 차분과 80% 이상 겹치는 확실한 경우는 735개뿐이고, 2,964개는 반복 구간 때문에 이동이 모호했다 (확인, 3-4 Q3). 화이트리스트에서는 이동이 틀려도 그 차분이 내는 소리는 바뀌지 않는다(차분 안 상대 시각이 그대로). 틀린 이동은 레이어 공유·보고서·구간 표시만 흐린다 (추정). 그래서:
  - 확실하지 않으면 이동 0(같은 폴더) 또는 이동 0 + "이동 불확실" 보고(다른 폴더).
  - **차분 해시는 이동을 빼고 계산한다** (결정 2026-10-17, 차분의 원본 시각 기준). 화이트리스트에서 이동은 차분 전체를 Track 시간축 위에서 통째로 미는 값일 뿐이라 플레이(노트·소리 간격, 판정, 소리)를 바꾸지 않는다. 그래서 이동을 나중에 고치거나 Track을 합치·나눠도 기록·리플레이가 같은 채보로 남는다.
  - 이를 위해 **기록·리플레이 안의 시각은 차분 자기 시각(Track 시각 − 이동)으로 저장**한다.
- **음수 시각 때문에 할 일** (작음):
  - 시각 필드는 전부 부호 있는 정수(i64). 부호 없는 필드가 없는지 컴파일러에서 점검.
  - 곡 시작 준비 시간 = "가장 이른 이벤트 − 준비 시간" (0 기준이 아님).
  - 진행 바·구간 통계의 시작이 음수일 수 있음(표시 변환).
  - `ns_to_frame`은 음수도 대칭 반올림이라 문제없음 (확인: `cp2/crates/rcore/src/runtime.rs`).
  - 판정·게이지·소리 정렬에는 영향 없음.
- 2차 연구 Q3에서 "편입 때 음수 이동이 얼마나 생기나"를 쟀다 (3-4).

### 1-3. 1차 연구에서 가져오는 것 (`../design/BMS_to_Track.md`)
- 같은 곡 판정 규칙 R1(소리 바이트 상호) · R2(이름 + 발음 시각 겹침) · R3(제목 + 이름 강함, 검토 표시). 애매하면 합치지 않는다.
  - **2차 연구로 고칠 것** (3-4 Q7): R1은 상호 0.5만으로는 같은 작곡가의 샘플 공유·리믹스를 합친다 → "상호 ≥ 0.8, 또는 시각 겹침 ≥ 0.8, 또는 작은 쪽이 거의 전부(≥ 0.98) 포함"을 더한다. R2는 음원 교체 곡(같은 채보·같은 소리 이름, 다른 소리)을 합친다 → 같은 이름 소리의 디코딩 길이가 80% 이상 일치해야 한다. 제목만으로 R2에 들어가는 길(이름 < 0.5)은 검토로 돌린다.
  - **판정 단위는 폴더가 아니라 채보 묶음**이다: 한 폴더에 다른 곡 채보가 섞인 경우가 있다 (3-4 Q7). 폴더 안 채보를 참조 소리 집합·제목으로 먼저 나눈 뒤 판정한다.
- 합친 뒤 검사: 합집합 ÷ 가장 큰 차분 > 1.5, 또는 합집합의 50% 미만만 쓰는 차분 → 떼어 별도 Track (⚑ 문턱은 표본 검토로).
  - **2차 연구 결과: 차분 단위 사용률 검사는 버린다.** SP처럼 폴더에 차분이 많으면(중앙 11개) 맞는 편입의 30%를 떼어 냈고, 떼어 낸 308건 중 223건은 소리 바이트를 90% 넘게 서로 공유하는 확실한 같은 곡이었다 (확인). 대신: 바이트 상호 ≥ 0.9면 검사를 건너뛰고, 나머지는 **새 폴더의 레이어 ↔ Track 레이어** 비교로 한다 ⚑ (문턱은 아직).
- 키 수가 다른 차분을 한 Track에(레이아웃마다 레인 묶음, 원본 채널 → 레인 대응을 출처로 남김).
- 소리 공유는 **Track 안에서만**(참조 소리만, 바이트 해시 + 디코딩 해시). 곡을 가로지르는 공유는 하지 않는다(0.045 GB뿐, "묶음 하나 = 곡 하나" 유지).
  - 2차 연구: 디코딩 해시를 전체(고유 참조 소리 2,307,914개)로 재 보니 Track 안 추가 절약은 0.39 GB(참조의 0.3%)뿐이다 (확인, 3-4 Q8). 바이트 해시가 거의 전부다. 디코딩 해시는 절약보다 **판정 보조**(소리 길이로 R2 확인)에 쓸모가 크다.
- 재인코딩 판본(같은 이름·같은 길이·PCM 다름)은 기본으로 둘 다 담는다(⚑ "판본 하나로" 옵션).
- 같은 소리가 1 ms 안에서 어긋난 것도 합치지 않고 별개 이벤트로 둔다(원본 시각 보존).

## 2. 편입 (덧붙이기) 설계

### 2-1. 라이브러리 정체성 색인
변환을 마친 Track마다 다음 지문을 라이브러리에 보관한다. 새 팩은 **새 폴더만 읽어** 이 색인과 맞춰 본다(기존 Track을 다시 읽지 않음).

| 지문 | 용도 |
|---|---|
| 소리 바이트 해시 집합 (역색인: 해시 → Track) | R1 후보 찾기 |
| 소리 디코딩 해시 집합 | 재인코딩이 아닌 같은 PCM |
| 정규화한 소리 이름 집합, 제목·아티스트 | R2·R3 후보 |
| 소리별 디코딩 길이(샘플 수 ÷ 샘플레이트) | R2·R3 확인: 같은 이름 소리의 길이가 맞는가 (음원 교체 곡 거르기, 2차 연구 추가) |
| 소리별 발음 시각 목록 (이동 허용 비교용) | R2 확인, 이동값 계산 |
| 이미 가져온 원본 채보 파일 해시 → (Track, 차분) | 같은 채보 파일을 다시 가져오지 않음. 단 실측에서는 드묾: SP 채보 33,810개 중 4팩 채보와 바이트가 같은 것 0개 (확인) — 팩마다 차분을 새로 만들기 때문 |
| 난이도표 md5 → 채보 | 출처·판 관계 기록용. 같은 곡 판정 근거로는 쓰지 않음 (3-4 표 정보) |

### 2-2. 새 팩을 가져오는 흐름
1. 새 폴더를 훑어 지문을 만든다.
2. 이미 가져온 채보 파일이면 건너뛰고 출처만 덧붙인다.
3. 역색인으로 후보 Track을 찾고 R1~R3를 적용한다 → **새 Track / 기존 Track에 편입 / 검토 대기** 중 하나.
   - **새 폴더가 기존 Track 둘 이상에 걸리면 자동으로 합치지 않고 검토 대기**로 한다. 기존 Track 둘을 합치면 한쪽의 원점이 옮겨지기 때문이다. 실측 8건 (확인, 3-4 Q6). 사람이 합치기로 하면 한쪽 Track의 차분들에 이동만 더한다(차분 해시는 이동을 빼고 계산하므로 기록 유지, 1-2).
   - R3만 걸리면 검토 대기 (실측 9건).
4. 편입이면:
   - 고정 원점에 대한 이동을 계산한다(음수 허용).
   - 새 차분을 자기 이벤트 목록 그대로 더한다(레이어는 컴파일러가 다시 계산). **기존 차분은 한 글자도 바뀌지 않는다.**
   - 새 소리만 소리 묶음에 더한다.
   - 다시 컴파일한다.
5. **검증**: 편입 전후로 기존 차분의 정답 렌더 해시가 같아야 한다(들리는 결과가 변하지 않음). 새 차분은 원본 발음 목록과 1:1.
   - 모의 실험: 채보마다 (Track 시각 ns, 소리 바이트 해시) 목록의 지문을 가져올 때 기록하고 끝에 다시 계산 → 38,712개 전부 같음 (확인, 3-4 Q6). 소리 번호(색인)가 아니라 **소리 내용 해시**로 비교해야 한다 — 새 소리가 들어오면 번호는 밀린다.
6. 합친 뒤 검사(1-3)에 걸리면 편입을 취소하고 별도 Track으로.
7. 같은 입력이면 가져오는 순서가 결과를 바꾸지 않아야 한다. 모의 실험에서 순서 셋(이름순·역순·무작위)의 Track 구성이 완전히 같았다 (확인). 단 4팩을 늘 먼저 넣었고, SP 폴더끼리 이어지는 경우가 거의 없어서 시험이 약하다 (추정).

### 2-3. 판단 기록
- 사람이 내린 "합침 / 나눔 / 같은 곡 아님" 판단과 규칙이 내린 판단을 라이브러리에 기록한다. 다시 돌려도(같은 입력, 같은 기록) 결과가 같아야 한다.
- Track 묶음 버전은 편입 때마다 오른다. 차분 ID는 바뀌지 않고, 기록·리플레이는 (차분 ID, 차분 해시)로 묶이므로 기존 차분의 기록이 깨지지 않는다.

### 2-4. 차분 표현 = 순수 화이트리스트 (결정 2026-10-17)
- 차분은 자기 이벤트를 전부 적는다. 이벤트 ID·출처 묶음·base가 필요 없고, 가져온 순서가 내부 정리를 바꾸지 않는다(원점만 처음 차분 기준).
- 대가: 작성 형식에 차분 간 중복 텍스트, 공통 음악을 한 곳에서 고칠 수 없음(편집 도구가 대신).

### 2-5. 같은 차분의 다른 판

### 4-1. B-1 구현 결정 (bms2track 0.2, Codex 3-2 리뷰 반영)
- **#RANDOM 해석**: BMS는 "값을 먼저 정하고 평범한 BMS로 읽는" 형식이므로, 줄마다 조건(변형 → 허용 선택지)을 붙여 읽은 뒤 **선택 조합마다 풀어** 같은 결과 객체를 모아 `when`으로 적는다. 한 AND로 안 되는 집합(여러 선택을 덮는 #ELSE 등)은 겹치지 않는 AND 여럿으로 복제. #SETRANDOM은 고정값, #ELSEIF·#ELSE는 앞 갈래를 뺀 나머지, #RANDOM 밖 #IF는 맞는 갈래 없음.
- **국소 풀이**: 조건이 노트·BGM·BGA 줄(과 플레이에 안 쓰는 정의·머리)에만 있으면 전체 조합을 펼치지 않고, 레인마다 서로 영향을 주는 객체(같은 위치, 롱노트 상태를 바꾸면 레인 전체)만 국소 조합으로 푼다 — 랜더마이저(변형 800~1,100개)도 변환된다. 조합 1024개 이하 차분은 전체 펼침과 결과가 같음을 자체 대조(`--selfcheck`).
- **시간 지도·스크롤·정의를 바꾸는 변형**: 그 변형들만으로 차분을 나누고(명세 2-4, 16개까지) 나머지 변형은 각 차분 안의 `when`으로 남긴다.
- **같은 위치**: 같은 채널·위치는 뒤 정의가 덮어씀(BMS 관례, 01 BGM은 쌓임). 다른 채널끼리 같은 레인·위치는 뒤 정의 하나.
- **소리 정체성**: 논리 소리 ID = `<원본 경로>@<WAV ID>`. 같은 파일을 가리키는 다른 #WAV는 다른 소리(재발음 끊기가 #WAV 번호 단위). 출력 파일 이름에 원본 바이트 해시.
- **손실은 드러낸다**: 롱노트 안 노트·페달·레이아웃 밖 채널의 노트는 소리만 자동재생으로 옮기고 차분 `losses`에 기록(불완전 변환, 명세 v1.5 `LOSSES` 구역). 손실 경로(실수·32비트 WAV, MP3 등)는 FLAC24 + gain 되돌림, 오차를 보고서에.
- **BMSON**: beatoraja와 같게 이어 재생(`c`)을 소리 조각(`start`·`length`)으로, 같은 레인·위치의 여러 채널 노트는 소리 여럿인 한 노트.
- **검증**: `check_bms.py`는 컨버터와 코드를 나누지 않는 "실제 플레이어처럼 읽는" 해석기로 조합마다 노트(소리를 묶어)·자동재생·빈 레인 소리·화면 위치·손실을 대조하고, 원본 차분 파일 전수(status.json)와 소리 PCM(엔진 디코더 ↔ 기준 디코더)까지 본다. 문법 경우는 `test_bms_cases.py`(합성 15파일).
