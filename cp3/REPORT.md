## 3-0. 이름·곡 객체 스펙·합성 예시 Track (2026-10-16 ~ 17)

- **무엇을**: 엔진 임시 이름(Unison, 문서 전용)과 곡 객체 이름(Track)을 정하고, 토론으로 정한 결정(화이트리스트 차분, 고정 원점 + 음수 허용, 이동을 뺀 차분 해시, 소리 저장·메모리 정책, 그래픽은 Track 밖)을 구현용 형식 명세 `Track_형식.md`로 옮겼다. 직접 합성한 소리(Vorbis·FLAC·MS-ADPCM, 44.1k·48k·22.05k·30,697 Hz)로 차분 4개(tick·박·ms 단위, 배속 변형, 8B·7+1 레이아웃)짜리 예시 Track을 손으로 쓰고, 명세대로 시각을 계산하는 검산기로 확인했다.
- **게임으로 치면**: 어떤 원작 곡을 바꿔 오더라도 담을 그릇이 빈틈없는지, 실제 컨버터를 만들기 전에 종이 위에서 확인한 것이다. 예시 Track은 앞으로 컴파일러·게임의 첫 정답 시험곡이 된다.
- **결과**: 검산 문제 0. DJMAX식 tick 1728과 IIDX식 13000/3 ms가 같은 4,333,333,333 ns로 만남. 음악 레이어 38개 중 9개를 차분들이 공유(반주 stem은 4개 차분 모두 Track 0). 음수 Track 시각은 의도한 픽업 2곳뿐. 쓰면서 막힌 곳 11개(스크롤 속도 단위, 변형 대안 노트의 겹침, 지뢰 효과, 빈 레인 소리의 유효 범위, 배속 변형이 물려받는 것, 같은 PCM·다른 시작 보정의 레이어 구분 등)를 찾아 명세 v1.1에 고쳤다.
- **결론**: 3-0 완료. 남은 ⚑(지뢰 기본 감소량, 중첩 #RANDOM, 측정으로 정할 값들)는 해당 단계에서 정한다. 다음은 3-1 컴파일러 — 예시 Track을 비트 단위로 같은 묶음으로 만드는 것부터.
- **Codex 리뷰** (`reviews/2026-10-17_codex_3-0.md`): 중대 7·보통 8. 중대 7(차분 해시의 논리 소리 ID, 아르페지오 반올림, STOP + 명시 스크롤, damage 유실, 바이트 배치·확장 규칙, 정규 해시·코덱 구역, 동시 발음 순서)은 명세 v1.2로, 검산기 거짓 성공·예시 불일치·재현성은 코드로 고치고 반례 9건으로 다시 검증. 시험 벡터와 기준 디코더 선택은 3-1로.

## 3-1. 컴파일러 (2026-10-17)

- **무엇을**: Rust 크레이트 `cp3/crates/track` — 작성 형식(TOML) 읽기·검사, 유리수 시각 계산(한 번 짝수 반올림), 배속 변형 펼치기, 정규 발음 순서·차분 안 소리 표, 스크롤(STOP 삽입)·마디선·보이스 예산·구간 통계, 엔진 디코더 셋(Vorbis 패킷 보존 + lewton, FLAC 프레임 보존 + claxon, MS-ADPCM 직접 구현), 소리·차분·묶음 해시(BLAKE3), 묶음 쓰기·읽기, 라이브러리 색인. 도구 `trackc`(compile·verify·dump·unpack·info·index·decode).
- **게임으로 치면**: 곡을 게임이 바로 읽는 파일 하나로 굳히는 단계다. 같은 곡이면 누가 언제 만들어도 바이트까지 같은 파일이 나오고, 파일이 깨졌는지 스스로 안다.
- **결과**: 예시 Track → 385 KB 묶음. 두 번 컴파일 바이트 같음, verify 통과(구역·묶음 해시, 소리 다시 디코딩 해시, 차분 읽고 다시 쓰기), 풀었다 다시 컴파일해도 묶음 바이트 같음(되살린 Ogg·FLAC·WAV의 소리 해시 같음). Rust ↔ Python 검산기가 4개 차분의 소리 시작·노트·빈 레인 소리·마디선·스크롤에서 ns까지 같음. 디코더: FLAC·MS-ADPCM은 libsndfile·ffmpeg와 비트까지 같음, Vorbis는 libvorbis와 최대 차 3×10⁻⁷. 반례 14건 모두 컴파일 거부. 시험 벡터 `example/golden/` + `cargo test`.
- **결론**: 짧은 Ogg 키음에서 첫 페이지 = 마지막 페이지(EOS)일 때 granule을 앞 자르기로 잘못 읽는 버그와, 명세의 레코드 크기 합산 오류(52 ≠ 56 B)를 구현 중에 찾아 고쳤다(명세 v1.3). 다음은 3-2 컨버터(DJMAX 8B부터).
- **Codex 리뷰** (`reviews/2026-10-17_codex_3-1.md`): 중대 8·보통 6·사소 1, 모두 처리 → 명세 v1.4. unpack 경로 탈출 차단, 묶음 읽기 크기·참조·의미 검사(`validate_chart`), 짧은 입력 패닉 제거, 변형 겹침을 조합 전개 대신 조건 호환 검사로, 모든 BPM 양수·마디선 상한, STOP + 스크롤을 이동 시간만 적분(리뷰 반례 단위 시험), 유리수 → f32/f64 한 번 반올림(이중 반올림 반례 시험), ADPCM 64비트·delta 상한·fact 손상 거부, Ogg CRC·순번·이어짐 검증과 큰 패킷 분할, **Vorbis 소리 해시를 보존 패킷으로**(디코더 f32가 플랫폼마다 다를 위험), 컴파일 캐시(머리 source_key), 레이어 비교를 유리수 이득·변형 조건으로. 반례 26건(작성 형식 19·묶음 7) 패닉 없이 거부, 회귀 시험(오디오 되살리기 왕복, Ogg 큰 패킷, ADPCM 극단 입력, 스크롤 속도 대조) 추가.

## 3-3. 여러 레인 게임 (2026-10-17)

- **무엇을**: CP2의 1레인 코어·시험장에서 엔진 크레이트(`crates/engine`)와 게임 크레이트(`crates/game`)를 갈라냈다. 엔진: Track 묶음 로더(계획 → 소리 슬롯 디코딩, i16/f32, 리샘플링), 믹서(이벤트 시각마다 나눠 섞기, 끊기·choke, 자동 연주 일정, 탐색, 미리보기 버퍼링), IIDX식 판정·게이지·EX 점수(데이터 `Rules`), 빈 누름 소리 규칙, 리플레이, 미리보기 소리 저장소(들을 곳부터, 세대 번호 취소). 게임: 레이아웃이 정하는 N레인 그리기·판정 스레드·봇, 레이아웃별 기본 키(좌우 Shift 구분), 변형 무작위 선택(기록), 선곡 화면(색인만 읽음, 구간 통계 막대, 디바운스 뒤 미리보기·탐색).
- **게임으로 치면**: 레인 수가 다른 세 게임의 곡을 같은 프로그램으로 고르고, 미리 듣고, 친다. 미리 듣기는 실제 플레이와 같은 소리이고, 곡 중간으로 건너뛰어도 처음부터 들은 것과 같은 소리다.
- **결과**: 엔진 정답 렌더 = 독립 Python 렌더(최대 차 6×10⁻⁷, DJMAX·IIDX·BMS 변형 포함). 탐색 렌더 = 처음부터 렌더(비트 일치, 실제 곡 3군데). 준비를 늦추면 쉰 만큼 밀린 것 외에 정답 렌더와 같음. 봇(직접 입력) 플레이 DJMAX 8B·4B, IIDX SP·DP, BMS 7K·랜더마이저(변형 803개)에서 리플레이 = 실시간 점수. 선곡 화면 미리보기 첫 소리(디바운스 뒤 ~ 첫 콘텐츠 프레임을 장치 버퍼에 씀) p50 695 ms · p95 990 ms(9곡, 실패 0), Track 870개 색인 15.6 MB.
- **결론**: 3-3 완료. 세 원작의 레이아웃을 같은 코드로 고르고·미리 듣고·친다. 판정·게이지는 데이터(`Rules`)라 CP4 커스텀이 그 위에 얹힌다. 봇 OS 입력(SendInput)이 한때 게임에 닿지 않았으나 일시적이었다(관리자 권한 문제 아님, `inputtest`로 Raw Input 10/10, 이후 DJMAX 8B OS 입력 봇 98 PG·리플레이 = 실시간). 기능 시험은 주로 직접 입력 모드로 했고, 실제 키 입력 경로 측정은 3-5에서.
- **Codex 리뷰** (`reviews/2026-10-17_codex_3-3.md`): 중대 6·보통 8·사소 1, 모두 처리. 키음을 누른 순간 곡 시각으로 보내 소리마다 한 번만 프레임으로(아르페지오 1프레임 어긋남 제거), 끊긴 보이스 슬롯 즉시 회수(예산 1 반례 시험), watermark를 입력보다 먼저 읽기, 판정을 여러 레인 판정기 `Judge`로 — 확정 결과를 "확정 가능해진 시각 → 레인 → 노트"로 정렬해 watermark를 어떻게 나눠도 같은 순서(리플레이 = 실시간, 시험), 판정 스레드 할당 제거, HARD·EX-HARD는 0 이하에서만 탈락, 등급별 빠름·늦음 경계와 게이지 정책을 데이터로, 탐색한 상태는 목표 프레임부터만 들림, 디코딩 실패는 무음 슬롯 + 표시, 요청 당시 세대로 취소 확인, 같은 데이터 한 번만 디코딩, 메모리 예산 검사, **Track 단위 소리 저장소**(차분 사이 공유, 미리보기 → 플레이 인계: 1,524개 넘겨받아 불러오기 33 ms), key_frame 기록, ASIO 미리보기 종료. 검증도 보강: 렌더 대조에 보이스 예산·발음 시작 프레임 비교, 탐색 뒤·재생 중 버퍼링 시험, 리플레이가 마지막 watermark까지·지뢰·FAST/SLOW·클리어까지 비교하고 다르면 실패, 첫 소리 = 첫 콘텐츠 프레임을 장치 버퍼에 쓴 시각(p50 695 ms · p95 990 ms).

## 3-4. 설정창·보정 도구·설정 저장 (2026-10-17)

- **무엇을**: `settings.toml` 하나에 범위별 표(전역 · 장치별 `"<경로>:<장치>"` · 키 모드별 `"<레인 id 서명>"` · 프리셋)로 설정을 저장하고, 플레이가 그 값을 쓰게 했다(명령줄 > 설정 > 기본값, 파일이 없으면 3-3과 같은 기본값). 선곡 화면 F1 = 설정 화면(탭 7개, 범위 꼬리표, 레이아웃별 키 묶기 — 여러 키, 겹치면 옮김, 좌우 Shift·Ctrl·Alt 구분, 봇 키 거부). 오프셋 A(판정 + 키음)·B(화면), D 자동/수동·여유, 음량(마스터·반주·친 키음 — 믹서가 반주와 키음에 따로 곱함), 늦은 키음 한도, 노출 시간, 게이지. 보정 도구 둘(소리로 맞추기 A: 클릭 120 BPM 40박, 실행은 A = 0으로 / 화면으로 맞추기 B: 클릭 없이 노트만) — 합성 차분을 같은 플레이 경로로 돌려 누름 오차 중앙값·MAD·히스토그램을 보여 주고 "적용"을 눌러야 값이 바뀐다. 규칙 해시(판정 창·게이지 표·빈 POOR·롱노트 규칙의 정규 바이트열 → BLAKE3)를 meta.json·결과 줄·HUD에 남기고, 리플레이는 해시가 다르면 비교에서 뺀다.
- **게임으로 치면**: 내 장비와 손에 맞춘 값(늦게 들리는 만큼, 늦게 보이는 만큼)을 한 번 재서 저장하면 다음에 켜도 그대로다. 점수에는 "어떤 판정 규칙으로 친 점수인지"가 붙어서, 규칙이 다른 점수끼리 섞이지 않는다.
- **결과**: 봇(직접 입력)이 +20 ms 늦게 치게 하고 보정 → 소리 보정 중앙값 +20.0 ms(MAD 0) → 제안 A −20, 화면 보정 → B + 20 (둘 다 ±1 ms 안). 선곡 → F1 → 소리 보정 → 적용 → 저장까지 화면 경로를 키 스크립트로 돌려 `offset_a_ms = -20` 저장 확인. 그 설정으로 20 ms 늦게 치는 봇 → 81 PG(오차 0), 키음 목표 자리 = 반주 자리(누른 시점엔 이미 지나 최대 18.8 ms 늦게 바로 울림 — 계획 4장 "음수 A는 D 여유까지만"대로). A만큼 늦게 맞춰 친 봇(소리 기준 정박)은 판정 오차 = A, 키음 = 반주 + A(+10·−8 ms, 0.1 ms 안). 저장·다시 열기·장치 바꾸기·레이아웃별 키·깨진 파일·범위 밖 값 시험, 반주·키음 음량 분리 시험. 리플레이 규칙 해시 같으면 비교(일치)·다르면 제외.
- **결론**: (Codex 리뷰 뒤 채움)

## 3-2. 컨버터 셋 — DJMAX · IIDX · BMS/BMSON (2026-10-17)

- **무엇을**: 원작 세 가지를 Track 작성 형식으로 옮기는 컨버터와, 원본을 따로 읽어 대조하는 검증기를 만들었다. DJMAX(곡 하나 = Track, 4B~8B × NM~SC, tick 그대로·볼륨 공식·기준 스크롤 보정), IIDX(.1 + 소리 묶음, SP·DP, ms 그대로·정수 반올림 스크롤·소리칸 교체 → 빈 레인 소리, WMA → FLAC), BMS/BMSON(폴더 하나 = Track, #RANDOM → 변형, 롱노트 셋, 투명 노트, 지뢰, 음수 BPM·#SCROLL, BMSON 이어 재생 조각). DJMAX·IIDX 컨버터는 게임 자료를 읽으므로 비공개.
- **게임으로 치면**: 세 게임의 곡이 우리 엔진에서 원래 게임과 같은 시각·같은 소리로 나오게 하는 번역기다. 번역이 틀리면 바로 드러나도록, 번역기와 코드를 나누지 않는 검사관이 원본을 직접 읽어 노트 하나·소리 하나까지 맞춰 본다.
